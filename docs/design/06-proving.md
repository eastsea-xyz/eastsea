## 운영 모드 — 실측 반영 (2026-09-26, `docs/research/spike-2026-10.md`)

**신뢰의 1차 근거는 ZK 증명이 아니다.** 체인·지갑은 이미 확정 인증서(BLS 임계 서명 1개) + EIP-7864 상태 증명으로 검증된다(검증자 정족수를 믿는 모델). ZK 증명은 그 위에 얹는 **추가 보증**(위원회가 정직하지 않아도 실행이 맞았음을 확인)이며, 체인을 멈추거나 느리게 하지 않는다.

실측(M1 Max 1대, Jolt): 설계 가정(>1,000만 사이클/s)과 달리 0.15~0.39 MHz. 최적화 후 tx당 약 2.7M 사이클 → **tx당 약 13초 증명, 맥 1대가 따라잡는 양은 시간당 약 270 tx.**

| 모드 | 조건 | 동작 |
|---|---|---|
| **지연 증명(기본)** | 증명기 1대 이상 | 체인은 1초 블록으로 계속 진행, 증명은 오래된 높이부터 뒤따라 채움(구현: 증명기는 메모리에 둔 최근 확정 블록 32개 중 가장 오래된 미증명 블록을 고른다, `chain.rs` `provable`). 지연 = 대기 tx 수 ÷ (증명기 수 × 270/시간) |
| **체크포인트 증명** | 부하가 증명 능력을 넘을 때 | 모든 블록 대신 N블록(예: 에포크 경계)마다 연속 구간을 증명. 빈 블록은 거의 비용 없음 |
| **실시간 증명(목표)** | 증명기 다수 | 청크(4~8 tx, 약 3분) 병렬 + 집계. 1초 블록·수백 TPS를 실시간 증명하려면 대략 수십~수백 대 |

- **증명기 1대여도 체인은 완전히 동작한다.** 증명기 0대면 증명만 없다(인증서 검증은 그대로).
- 처리량 상한은 두 개로 나눠 표기한다: **합의·실행 처리량**(맥 1대 검증자로도 병렬 실행 기준 수천 tx/s급)과 **증명된 처리량**(= 증명기 수 × 약 270 tx/시간/대).
- 지갑 UI(설계, 미구현): "확정됨(인증서 검증)"과 "ZK 증명됨(높이 H까지)"을 따로 표시. 증명 지연은 경고가 아니라 상태 정보. 지금 지갑은 확정 인증서만 표시하고, 증명 상태는 앱 메뉴 막대의 증명기 상태(마지막 증명, `lag`, 마지막 보상)로만 보인다.

## 청크 분담

미구현(설계). 프로토콜 2는 블록 하나를 증명기 한 대가 통째로 증명하고, 첫 유효 증명이 그 블록의 에스크로와 발행을 받는다(13-protocol-2.md, `crates/execution/src/proofs.rs`). `crates/proving/src/market.rs`의 청크 시장 코드는 노드에 연결되어 있지 않다. 청크 분할·집계는 프로토콜 3 후보.

```
BlockProof(H) 요청
  ├─ 청크 계획: BAL DAG 약한 연결 성분 → 청크 k개, 각 청크 예상 사이클 ≈ 균등 (Advisor 힌트 사용 가능)
  ├─ 분배: 위원회 증명기 목록 → 청크 할당 (가용 GPU, 최근 처리 속도 가중)
  ├─ 각 증명기: prove_chunk → ChunkProof → gossip
  ├─ 집계: 2-to-1 재귀 트리, 누구든 두 ChunkProof를 받으면 합칠 수 있음 (경쟁 허용, 중복 무해)
  └─ BlockProof → gossip → 지갑
```

- 청크 io 연결 조건: `chunk[i].post_root == chunk[i+1].pre_root`.
- 집계 회로는 `Pcs` trait 위에서 직접 작성(zkVM 안에서 Verifier 실행하는 재귀). leanVM 기준 2-to-1 약 200ms 목표.
- 증명기 0대일 때: 증명 없이 체인 진행(인증서 검증은 유지). 검증자가 여유 시간에 체크포인트부터 증명.

## 증명 검증기 (지갑용)

미구현(설계). 지금 증명을 검증하는 곳은 검증자 노드뿐이다: 노드가 `aether-prover serve` 사이드카를 띄워 검증을 맡긴다(13-protocol-2.md §2). FFI에 `verify_block`은 없다.

- `proving/src/verifier/` 는 `no_std`, alloc만. 의존성은 필드 연산·해시뿐.
- 빌드 타깃: macOS, iOS, wasm32. UniFFI로 `verify_block(proof_bytes, expected_io) -> bool` 노출.
- 목표: 검증 ≤100ms (M1), 메모리 ≤64MB, 증명 ≤300KiB.

## Metal 최적화 (2단계 기여)

우선순위는 스파이크 S5 프로파일로 정한다. 후보:
1. Poseidon2/Merkle 커밋 커널 (ICICLE Metal에 없음)
2. sumcheck 라운드 (메모리 대역폭 bound → 통합 메모리 이점)
3. 세그먼트 분할 제거: 트레이스를 통합 메모리에 상주, CUDA의 VRAM 분할 오버헤드 회피
4. NTT/DCCT (M31 Circle)
5. AMX 필드 연산 실험 (선례 없음)

업스트림 대상: Jolt `jolt-kernels/metal`, Stwo(ICICLE-Stwo 또는 자체 Metal 백엔드).

## 증명 대기열과 Advisor

- `ProofQueue`: (높이, 청크) 우선순위 큐. 기본 정책 = 오래된 높이 우선. (미구현. 지금은 위 `provable`이 같은 정책으로 한 블록씩 고른다.)
- Advisor 힌트: 청크 예상 시간, 증명기 가용성 예측. 힌트가 틀려도 정확성 무관.
- "증명 전 조기 경보": 증명 미도착 블록에 이상 점수 → 지갑 UI "대기 중" 표시 강도만 바꿈.

## 실패 처리

- 지금 동작: 사이드카가 거부한 증명은 증명 풀에 넣지 않고, 그런 증명이 든 블록에는 투표하지 않는다. 사이드카가 없거나 실패해도 증명이 든 블록에 투표하지 않는다. 아래는 설계.
- 증명 검증 실패: 해당 블록 격리, 위원회에 경보, 재증명 요청. BFT 인증서와 증명이 계속 불일치하면 체인 정지(수동 개입). 이 사건은 곧 "실행 버그 또는 위원회 담합"이라 자동 복구하지 않는다.
- 증명 지연은 정상 상태다(1대 기준 분~시간). 지갑은 "ZK 증명: 높이 H까지"만 표시. 사용자가 원하면 "ZK 증명된 높이 이후 받은 금액은 사용 전 대기" 같은 정책을 켤 수 있다(기본 끔). 고액 수신 시에만 권장.
