# 프로토콜 2: 증명 시장, 증명 발행, 레지스트라 상한

testnet 7780에 높이 기반으로 활성화하는 첫 실제 업그레이드입니다(12-launch-plan.md 결정 기록). 제네시스는 바꾸지 않습니다.

## 1. 블록 명제를 상태에 기록

- 블록 h를 실행하면 `BlockStatement`(aether_proving::block)의 커밋 C(h)가 정해집니다: 컨텍스트, 트랜잭션 해시, 활성화, 이전 루트, 다음 루트, 가스.
- 블록 h+1은 트랜잭션 전에 시스템 쓰기로 C(h)와 에스크로 몫 E(h)를 **상태 트리**에 남깁니다(EIP-2935의 블록 해시 저장과 같은 방식; 주소 `PROVER_ESCROW`의 저장소). 명제에는 다음 루트가 들어가므로 같은 블록 안에는 쓸 수 없습니다.
- 상태에 있으므로 체크포인트로 시작한 노드도 오래된 블록의 증명을 똑같이 검증합니다(합의 결정성).

## 2. 증명 제출

- payload에 `proofs: Vec<ProofClaim { height, prover, proof }>`(블록당 최대 2개, 각 128 KB 이하). 프로토콜 2부터만 허용.
- 유효 조건: 상태에 C(height)가 있고, 아직 증명되지 않았고, `EXPIRY`(30일) 안이며, 증명기가 C(height)를 출력했다고 검증됨.
- 검증은 `aether-prover serve`(사이드카)가 합니다. 프로그램 ID(내장 ELF의 SHA-256)는 프로토콜이 고정하고, 노드는 시작할 때 사이드카의 `info`와 대조합니다. 검증자마다 다른 증명기를 쓸 수 없습니다.
- 사이드카가 없거나 실패하면 그 검증자는 증명이 든 블록에 투표하지 않습니다(안전 쪽). 제안자는 자기 사이드카가 검증한 증명만 담습니다.

## 3. 지급과 발행

- 유효한 증명이 담긴 블록에서, 증명자 주소에 **E(height) + 발행(height)**을 지급합니다. 에스크로 잔액은 그만큼 줄고, 발행분은 새로 생깁니다.
- 발행: `ISSUE_0 >> (height / HALVING)`, `ISSUE_0 = 1 AETH`, `HALVING = 31,536,000`(R7′). 높이는 제네시스 기준입니다.
- 증명되지 않은 블록의 발행분은 생기지 않습니다(만료 후에도 소급 없음). 에스크로는 30일 뒤에도 남아 누구에게도 가지 않습니다(사실상 소각).
- 노드는 받은 보상을 로컬 색인에 기록하고 `aether_rewards(address)`로 내보냅니다(세무 기록; 합의와 무관).

## 4. 레지스트라 상한

- CommitteeRegistry v2(같은 저장소 배치): 에포크당 신규 등록 수 상한(기본 16). 활성화 블록에서 `forks::activate(2)`가 코드를 교체합니다.
- 업그레이드에 선택 필드 `registrar`를 둡니다. 서명된 업그레이드가 활성화되면 레지스트라 키가 바뀝니다(0이면 등록 중지). 위원회만 할 수 있습니다.
- 등록 기준을 `docs/design/14-registration.md`에 공개합니다.

## 5. 증명기 서비스

- `aether run`이 사이드카를 띄우고, 확정된 블록(상위 상태를 아직 가진 최근 블록)을 차례로 증명해 `aether_submitProof`로 검증자에게 보냅니다. 검증자는 증명 풀에 두었다가 제안할 때 담습니다.
- 앱 메뉴 막대: "방금 블록 #N을 증명했습니다 · 트랜잭션 수 · 걸린 시간 · 보상"(`aether_proverStatus`).

## 6. 순서

1. 상태 기록·지급·발행(체인 규칙, 모의 검증기로 테스트)
2. payload 필드와 검증기 트레이트, 사이드카 클라이언트
3. 증명기 서비스와 RPC, 증명 풀
4. 레지스트라 v2와 업그레이드 필드
5. 앱: 메뉴 막대, 보상 내보내기, 사이드카 번들
6. 감사, 릴리스, 업그레이드 서명·활성화(testnet)
