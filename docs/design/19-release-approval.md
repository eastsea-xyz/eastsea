# 19. Mac 앱 릴리스 승인: 빌더 공동 서명과 체인 공개 기록

결정: 2026-09-29. 배포 서버, Apple 개발자 인증서, Sparkle EdDSA 키 중 하나가 탈취되어도 한 사람이 모든 지갑에 업데이트를 설치할 수 없게 한다. 공개 기록은 별도 서비스가 아니라 Aether 체인이다. 위원회의 프로토콜 업그레이드 서명은 향후 추가 조건이며 현재 앱 릴리스의 승인 조건으로 사용하지 않는다.

## 신뢰 경계와 배포 순서

1. 서로 다른 Mac 세 대가 **같은 태그**의 소스를 독립적으로 빌드한다. 각 Mac은 자체 Secure Enclave P-256 개인키로 정규화된 릴리스 매니페스트에 서명한다. 공개키 세 개와 ReleaseLog 주소는 앱에 고정한다. 키를 새 버전으로 교체할 때는 구 버전의 검증 규칙을 먼저 통과해야 한다.
2. 빌더는 `platform`, `version`, `build`, 각 아티팩트의 이름과 SHA-256을 비교한다. 같은 이름의 해시가 하나라도 다르면 **발행을 중단하고 불일치를 경고**한다. 앱 실행 파일과 번들된 `aether`, `aether-agent` 도우미를 각각 기록하고, 코드 서명 봉인 파일(`CodeResources`)만 제외한 **앱 번들 전체 파일·권한·심볼릭 링크 목록의 해시**도 매니페스트에 넣는다. 따라서 추가된 프레임워크나 리소스도 불일치로 잡힌다. 빌더마다 다른 Apple 코드 서명은 복사본에서 제거하고, 서명 이력에 따라 달라지는 Mach-O `__LINKEDIT` 크기 필드 두 개를 0으로 만든 뒤 **남은 전체 실행 파일 바이트**의 SHA-256을 비교한다(재서명만 한 파일은 일치하고 코드 바이트 변경은 불일치하는 테스트). 배포 DMG는 세 빌더가 같은 파일을 받아 해시·Sparkle 서명을 확인하지만, 아직 각자 만든 DMG가 바이트 단위로 같다고 주장하지 않는다. 압축물의 SHA-256은 설치 직전에 반드시 확인한다.
3. 누구나 불변 `ReleaseLog`에 매니페스트와 빌더 서명을 게시할 수 있다. 계약에는 관리자, 수정, 삭제, 긴급 우회 권한이 없다. 스팸 게시물은 앱이 고정 공개키로 서명과 해시를 확인해 무시한다. 배포 전에 확정된 게시 항목의 식별자·높이·지문을 공개한다.
4. Mac 앱은 Sparkle의 EdDSA 검증을 유지한다. 설치 전에 **사전 다운로드한 압축물의 SHA-256**이 매니페스트와 같고, 매니페스트가 ReleaseLog의 상태 증명과 위원회 확정 인증서로 확인되고, 서로 다른 고정 빌더 키 2개 이상의 유효한 서명이 있어야 한다. 매니페스트에는 Sparkle 앱캐스트의 EdDSA 서명도 넣는다. 앱은 두 서명이 같은지 확인한 후 Sparkle 다운로드를 허용하고, Sparkle은 실제 설치할 압축물에 **그 동일한 서명**을 검증한다. 따라서 배포 서버가 사전 검사 뒤 파일을 바꿔도 같은 서명으로 다른 바이트를 통과시킬 수 없다. 긴급 릴리스는 3개 모두 필요하다. 일반 릴리스는 게시 블록의 인증된 시각부터 72시간이 지난 뒤에만 설치한다. 인증서·증명·앵커 최신성·시간·서명 중 하나라도 확인할 수 없으면 업데이트를 보류하고 기존 앱을 계속 실행한다. Sparkle이 제공하는 설치 전 콜백에서 이 조건을 적용하며, 앱캐스트 조회만으로 승인된 것으로 취급하지 않는다.
5. 설정은 대기 중인 버전, 빌드 번호, 게시 높이, 설치 가능 시각, 긴급 여부와 SHA-256 지문을 보여 준다. 거절 이유는 `This update is not approved on chain yet`로 표시한다. 릴리스 로그를 읽지 못하는 상태도 승인이 아니다.

## 매니페스트와 계약

서명 대상은 도메인 구분(`AetherRelease/v1`), 체인 ID, ReleaseLog 주소, 플랫폼, 버전, 빌드, `emergency`, 이름순으로 정렬한 아티팩트 이름과 32바이트 SHA-256으로 이루어진 결정적 바이트열의 SHA-256이다. JSON의 키 순서, 공백, URL, 서명 배열 순서는 서명 결과에 영향을 주지 않는다. 빌더 서명은 P-256 ECDSA `(r,s)` 고정 64바이트 형식이며 가능한 경우 low-s로 정규화한다. 한 공개키의 중복 서명은 한 표로만 센다. 버전/빌드/플랫폼/아티팩트 이름의 길이와 아티팩트 수, 전체 페이로드 크기를 제한한다.

`contracts/src/ReleaseLog.sol`은 순차 번호별 항목을 저장하고 `Published` 이벤트를 낸다. `publish`는 누구나 호출할 수 있으나 기존 항목을 바꾸거나 지울 수 없다. 저장 항목에는 매니페스트 SHA-256, 압축물 SHA-256, 서명 묶음 SHA-256, `block.number`, 게시 시각과 긴급 표시가 있다. 원본 매니페스트와 서명은 이벤트와 배포 파일에 남기며, 앱은 이 파일의 해시를 증명된 저장 값과 비교한다. 앱은 RPC가 돌려준 문자열이나 이벤트만 믿지 않고, **계약 런타임 코드 해시**, 항목 개수와 해당 항목 슬롯을 EIP-7864 증명으로 확인한다. 증명 루트는 **항목을 포함한 블록의 다음 인증 블록**의 `parent_state_root`다. 게시 높이와 시각은 계약 코드가 기록한 저장 값으로 읽는다. 앱에 번들된 `network.json`은 `release_log`, `release_log_code_hash`, `builder_keys` 세 공개키를 고정한다. 이 값이 없는 신규 네트워크에서는 설치를 거부한다. 조회에는 식별자를 지정하므로 원격 서버가 다른 항목을 돌려주더라도 해시·서명 검사가 실패한다.

계약을 배포한 뒤 `scripts/release-approve.py contract-hash`로 로컬 컴파일 결과의 런타임 코드 해시를 구하고, 배포 주소의 검증된 코드 해시와 일치할 때만 두 값을 앱의 새 네트워크 파일에 고정한다. 7780의 기존 `network.json`에는 이 필드를 추가하지 않는다.

노드는 `aether_releaseEntries(<ReleaseLog 주소>, <시작 번호>, <최대 64개>)`로 현재 상태의 공개 항목을 열거한다. 이 응답은 탐색기·운영자의 **발견용**이며 자체로 승인 증거가 아니다. 앱은 고른 번호를 `verified_release`로 다시 읽어 코드 해시·저장소 증명·위원회 인증서를 확인한다. `Published` 이벤트도 `eth_getLogs`를 통해 탐색기가 색인할 수 있다.

**이벤트는 인가가 아니다(F-07, 감사 2026-10-05).** `publish`는 누구나 호출할 수 있으므로, 누구나 임의의 매니페스트와 서명 바이트, 긴급 표시로 똑같이 생긴 `Published` 이벤트를 만들 수 있다. 이벤트·`aether_releaseEntries` 응답·RPC가 돌려준 문자열·배포 사이드카의 항목 번호는 어느 것 하나 승인의 증거가 될 수 없다. 승인은 언제나 직접 검증의 결과다: 핀된 런타임 코드 해시, EIP-7864 저장 증명, 위원회 확정 인증서, 핀된 빌더 키 2/3(긴급 3/3)의 서명. 지갑의 승인 경로(`ReleaseUpdateGate` → `verified_release`)도 업데이터(`scripts/release-approve.py`, 서명을 만드는 쪽)도 이벤트를 읽지 않는다. 미래의 어떤 소비자도 이벤트를 승인 근거로 써서는 안 되며, 계약 NatSpec(`contracts/src/ReleaseLog.sol`)에 같은 경고가 들어 있다.

`aether upgrade-sign/combine`의 `releases`는 기존 프로토콜 변경용(BLAKE3, URL) 필드다. 앱 릴리스 로그와 혼동하거나 7780의 이 필드 해석을 바꾸지 않는다. 향후 위원회 승인 조건을 추가할 때는 새 제네시스 기능 플래그 뒤에 두고, 7780 합의 규칙은 유지한다.

## 긴급 프로토콜 업그레이드 (B4, 2026-10-05)

새 제네시스(`node_rewards` 또는 `history_v2`)의 일반 프로토콜 업그레이드는 위원회 BLS 임계 서명과 **604,800블록(7일)** 예고가 필요하다. `emergency: true`인 업그레이드는 같은 BLS 임계 서명에 더해 **현재 위원회 n−f명의 독립 Ed25519 승인**을 확인하고, **1에포크** 예고 뒤 활성화한다. f=⌊(n−1)/3⌋은 합의·DKG와 같은 `N3f1` 모델이며, 4석은 3명, 16석은 11명이 필요하다. 중복·현재 위원회 밖의 키·변조된 서명은 거부한다. 전원 승인 대신 정족수를 써서 위원 한 명이 연락 두절이어도 긴급 수정 경로를 유지한다.

이 변경은 프로토콜 업그레이드 정족수만 바꾼다. **긴급 앱 릴리스의 빌더 서명은 계속 3/3**, 앱의 긴급 표시는 그대로이며, 일반 앱 릴리스의 2/3·72시간 규칙도 그대로다. 7780은 긴급 플래그를 여전히 합의에서 거부하고, 기존 업그레이드 서명·직렬화 바이트를 유지한다. CLI의 7780 긴급 승인 검증도 기존 전원 규칙을 유지한다. `upgrade.rs`의 검증기를 CLI 조합·검증과 블록 admission이 공유하므로 정족수 판정이 일치한다.

## 시간과 구형 네트워크

72시간은 로컬 시계만으로 계산하지 않는다. 게시 블록의 인증된 타임스탬프와 현재의 최신 인증 블록 타임스탬프를 비교한다. 현재 인증 블록은 FFI의 기존 최신성 한도도 통과해야 한다. 시간 역행이나 과도한 미래 시각은 거부한다. 긴급 항목만 72시간 대기를 생략하며 3/3 빌더 서명과 화면의 긴급 표시가 필수다.

ReleaseLog가 없는 기존 7780 네트워크에서는 **기존 Sparkle EdDSA 업데이트 경로를 유지**한다. 존재 여부는 RPC의 주장으로 판정하지 않고, 앱에 고정된 체인 ID 및 새 제네시스 기능 정보와 검증된 코드 해시로 판정한다. 새 네트워크에서 로그 조회가 실패하면 구형 네트워크로 강등하지 않는다. 이 호환 경로는 7780 사용자가 업데이트를 못 받는 상황을 막기 위한 것이며 신규 네트워크의 보안 보증으로 표시하지 않는다.

## 재현성과 운영

태그와 커밋, Rust `rust-toolchain.toml`/잠금 파일, Xcode 및 macOS SDK 빌드 버전, Swift 패키지 잠금 파일, 서명/공증 도구 버전을 기록한다. `SOURCE_DATE_EPOCH`은 태그 커밋 시각으로 고정하고, Rust `--remap-path-prefix` 및 Swift 디버그 경로 매핑으로 빌드 머신 절대 경로를 제거한다. zip/DMG 파일 순서·mtime·소유자·권한·볼륨 메타데이터를 고정해야 전체 압축물의 바이트 동일성을 주장할 수 있다. Apple 코드 서명·공증의 비결정적 바이트가 남아 있으면 우선 앱 실행 파일과 도우미의 일치만 주장하고, 각 빌더는 실제 배포 압축물의 해시를 별도로 서명한다. 이 단계에서 빌더 간 **압축물 일치**를 증명했다고 표시하지 않는다.

`app-v<version>` 태그를 먼저 소스 커밋에 만들고 각 빌더가 그 태그에서 빌드한다. `scripts/release-mac.sh --prepare`는 HEAD와 태그가 같은지 검사하고 업로드 전 DMG/zip SHA-256과 매니페스트 초안을 출력한다. 매니페스트에는 커밋, 태그, Rust/Xcode/SDK/Sparkle 버전과 `SOURCE_DATE_EPOCH`, 앱 번들 재고의 해시를 넣고 재고 원문은 별도 `.inventory.json`에 남긴다. 빌드 스크립트는 Rust·Swift 디버그 경로를 동일한 가상 경로로 매핑한다. 다른 두 Mac은 `scripts/builder-build.sh <manifest> <shared-DMG> <rebuilt.json>`으로 서명용 인증서 없이 독립 빌드하고 비교한다. 각 빌더의 `scripts/builder-sign init`은 Secure Enclave 키를 한 번 만들고 공개키를 출력한다. `builder-sign sign`은 로컬 재빌드 매니페스트가 원본과 바이트 단위로 같아야 서명한다. 서명 2개(긴급 3개)를 `scripts/release-approve.py combine`으로 합쳐 계약 `publish` 호출 데이터를 만든다. 확정된 항목 번호를 `AETHER_RELEASE_INDEX`로 지정해 `--publish-prepared`를 실행하면 **같은 DMG 바이트**와 매니페스트·서명·재고·항목 번호 파일을 배포한다. 72시간 조건은 앱에서 강제한다. 빌더가 재빌드 결과 불일치를 발견하면 게시·업로드를 중단하고 파일별 지문 차이를 출력한다.

긴급 배포는 준비 단계에 `AETHER_RELEASE_EMERGENCY=1`을 설정한다. 긴급 표시는 서명 대상과 계약 항목에 모두 들어가고, `combine`·앱은 3/3 서명이 아니면 거부한다.

## 검증 기준과 남는 위험

- 일치하는 압축물·2개 서명·인증된 기록·72시간 경과 시 설치 가능; 해시가 다르거나 서명이 하나뿐이면 불가.
- 긴급은 3/3에서 즉시 가능하고 2/3에서는 불가. 위조 RPC 저장소 증명·변조된 인증서·과거 앵커는 거부.
- 7780은 이전 동작 유지. 신규 네트워크에서 읽기 장애는 설치 보류. 설정의 지문과 설치 대상 지문은 동일해야 한다.
- 창업자가 위원회 정족수를 쥔 부트스트랩 시기에는 상충하는 확정 인증서 두 개로 이력을 다시 쓸 수 있다. 전체 이력을 재실행하는 Mac 노드는 충돌을 감지하지만, 과거를 처음 보는 경량 앱은 독립 체크포인트 없이는 어느 이력이 먼저였는지 알 수 없다. 빌더 2/3 규칙은 이 위험과 별개로 적용한다.
