> **2026-10-05 A6 합의 변경:** 이 문서의 잔액 0 일반 거래 약속과 아래 1층의
> 설명은 새 제네시스에는 적용되지 않는다. 모든 거래가 서명된 거래 바이트와
> 영수증 바이트에 대한 [고정 상태 수수료](27-state-fee.md)를 낸다. 첫 송신자
> 계정도 100단위를 낸다. 잔액 0 Mac의 등록만 2층 무료 레인에서 가능하다.
> 3층 대납 풀은 아직 설계안이며 구현되지 않았다. 체인 7780의 기존 규칙은
> 그대로다.

근거: [15-node-rewards.md](15-node-rewards.md)(1/16 상한과 발행되지 않는 몫), `crates/execution/src/fees.rs`(기본 수수료는 목표 부하 이하에서 0), [14-registration.md](14-registration.md).

## 한 문장
> 새 지갑은 잔액 0으로도 거래한다. 평소에는 수수료가 0이고, 등록은 언제나 무료이며, 혼잡할 때만 **소각될 수수료의 일부**(2026-10-04 변경)로 채운 공용 풀이 기기당 정해진 만큼 대신 낸다. 관리자 키는 없다.

## 1층 구현: 수수료 0 (G2, 2026-09-29)

`fees.rs`의 기본 수수료는 EIP-4844형 지수 곡선이라 목표 부하(블록 실행 가스 15M) 이하에서 **정확히 0**이다. 잔액 0 계정도 `max_fee = 0`, `tip = 0`으로 보내면 필요 예산 계산(실행 가스 × 실행 상한 + 증명 가스 × 증명 기본 수수료 + 값)이 전부 0이 되어 그대로 들어간다.

**새 제네시스 A5-1 보완:** 위 무료 경로는 상태를 늘리지 않는 단순 송금과 nonce·잔액 갱신에 적용된다. 저장 슬롯, 새 계정, 코드 바이트를 영구 추가하는 거래는 실행·증명 기본 수수료가 0이어도 [고정 상태 증가 수수료](27-state-fee.md)를 낸다. 잔액 0 송신자의 상태 증가 거래는 멤풀과 블록 실행에서 거부된다. 무료 등록·비콘 시스템 쓰기는 아래의 별도 상한을 유지한다.

- **지갑 규칙(앱·확장 프로그램 공통)**: 잔액이 0이거나 기본 수수료가 0이면 팁 0, 실행 상한 = 기본 × 2(기본 수수료가 한 번 두 배로 뛰어도 커버). 그 외에는 지금처럼 기본 × 2에 1 gwei 팁. `crates/ffi/src/lib.rs::fee_caps`, `crates/wasm/src/lib.rs::fee_caps`.
- **굶주림 없음**: 제안자의 정렬은 `(논스, 인클루전 리스트 포함 여부, 송신자)`이고 **수수료를 전혀 보지 않는다**(`chain.rs::mempool_candidates`). 팁 0 거래가 유료 거래 뒤로 밀리지 않는다(같은 블록에 함께 들어간다).
- **송신자별 상한**: 멤풀은 송신자당 64건(`MAX_PER_SENDER`), 체류 10분(`MEMPOOL_TTL`), 64MiB 바이트 예산(`MAX_MEMPOOL_BYTES`), 블록당 최대 2,000건(`MAX_TXS_PER_BLOCK`). FOCIL 인클루전 리스트가 앞순서 거래를 못 버리게 한다.
- **혼잡해지는 순간**: 기본 수수료가 0보다 커지면 상한 0인 거래는 멤풀 사전 검사에서 거부된다(`fee caps below the base fee`). 잔액 0이면 기본 × 2 상한도 감당 못 한다(`insufficient funds …`). 이때 등록은 2층으로 간다.

## 2층 구현: 무료 등록 레인 (G2, 2026-09-29)

투표 노드 등록을 **언제나** 무료로 만든다(기본 수수료 > 0일 때도). 등록 항목을 블록 페이로드의 무수수료 항목(`payload.registrations`)으로 싣는다 — 비콘 답(`payload.beacons`)과 같은 방식이고, 검증·상태 쓰기는 컨트랙트 경로와 같은 코드를 시스템 쓰기로 돌린다(`registry::register_system`).

| 항목 | 규칙 |
|---|---|
| 항목 내용 | 운영자 주소, 투표 키, 노드 ID, beaconer, 등록 증명(레지스트라 P-256, 64B), **운영자 지갑 서명(64B)**, 운영자 공개키(33B), 논스, 만료. 고정 길이라 바이트 상한 = 개수 상한 |
| 운영자 서명 대상 | `aether-registration ‖ 체인 ID ‖ 레지스트리 주소 ‖ 운영자 ‖ 투표 키 ‖ 노드 ID ‖ beaconer ‖ 증명 ‖ 논스 ‖ 만료`(도메인 분리, `registry::relay_message`). 증명을 주워 중계하는 제3자는 서명이 안 나온다 |
| 소비 | 운영자별 레인 논스(레지스트리 태그 슬롯, 컨트랙트 슬롯과 안 겹침)와 정확히 일치해야 하고 등록이 적용되면 1 오른다. 소비된 항목 재전송은 상태 검사로 거부, 그런 블록은 무효 |
| 만료 | 블록 높이로(앱은 7,200블록 ≈ 2시간). 지난 항목을 실은 블록은 무효 |
| 상한 | 블록당 4건(`MAX_FREE_PER_BLOCK`, 항목당 P-256 검증 2회 = 블록당 8회). **에포크당 16건은 컨트랙트와 같은 슬롯(7·8·9)을 공유**해 한 에포크에 두 경로 합쳐 16건 — 상한은 한곳(CommitteeRegistry v2)에만 적는다 |
| 결정성 | 순수한 서명·상태 검증만(Apple 확인은 등록 서비스에서 이미 끝남). 하나라도 틀리면 블록 무효(`ChainError::Protocol`) — 노드별로 스킵하지 않는다 |
| 같은 결과 | 컨트랙트 `register`와 같은 단어(슬롯 0..=9, 후보 배열, indexOf)를 쓴다. 두 경로를 같은 제네시스의 두 네트워크에서 같은 높이에 돌리고 저장소를 바이트 단위로 비교하는 시험이 있다 |
| 제네시스 플래그 | node_rewards 플래그 뒤에만. 테스트넷 7780의 합의 규칙은 그대로다 |
| 수신 | RPC `aether_sendRegistration`(항목), `aether_registrationNonce`(운영자의 다음 논스), `aether_status`의 `free_registration`. 확정되면 항목 해시로 가스 0 영수증을 만들어, 앱의 기존 영수증 폴링이 그대로 돈다(재시작하면 풀과 영수증은 메모리에서 사라진다 — 남은 것 참조) |

## 3층: 공용 대납 풀

| 항목 | 규칙 |
|---|---|
| 재원 (2026-10-04 변경) | **소각되는 수수료의 일부**: 기본 실행 수수료(`base_exec`)와 팁의 소각분(20%) 중 고정 비율(제네시스 상수, 예: 절반)을 소각하지 않고 풀에 적립한다. 새 발행이 없고 누구의 몫도 줄지 않으며, 운영자 수와 무관하다. 기본 수수료는 혼잡할 때만 0보다 커지므로 **재원이 늘어나는 때와 대납이 필요한 때가 같다**. 이전 안(발행되지 않는 노드 몫의 1%)은 운영자가 16명을 넘으면 0이 되어 폐기. DEX·런치패드 수수료는 재원이 아니다(법적 구조상 수수료 0, [dex-launchpad-legal-2026.md](../research/dex-launchpad-legal-2026.md)) |
| 지출 한도 (수입에 묶기) | 에포크당 풀 전체 대납 상한 = min(풀 잔액, **직전 에포크 풀 유입액 × k**)(k는 제네시스 상수, 1 이하). 지출이 수입을 넘을 수 없어 풀이 빚지지 않고, 모자라면 대납이 멈춘다(가끔 멈출 수는 있어도 마이너스는 없다). "영구히 마르지 않는다"는 보장이 아니라 이 한도가 보장이다. 혼잡이 거의 없는 체인은 유입이 0이라 대납도 0이지만 그때는 1·2층(수수료 0, 무료 등록)이 받친다 |
| 풀 상한 | 잔액 상한 고정(예: 하루 평균 대납액 × 30). 넘는 몫은 소각으로 되돌린다(총발행 설계는 그대로) |
| 쓰임 | 수수료 대납만. 풀에서 사용자 잔액으로는 한 푼도 옮기지 않는다. 대납 거래의 값(value)은 0이어야 하고, 대상은 허용 목록(전송, 토큰 전송, 등록된 계정 컨트랙트 호출) |
| 자격 | 인증된 기기: Mac은 DeviceCheck 등록, iPhone은 App Attest 키. 기기마다 **평생 N건 또는 수수료 합계 X** 중 먼저 닿는 쪽까지 |
| 속도 상한 | 에포크당 풀 전체 대납 상한과 블록당 대납 거래 수 상한. 넘으면 다음 블록으로 |
| 순서 | 대납 거래는 같은 블록의 유료 거래 뒤에 온다(혼잡을 키우지 않음) |
| 관리 | 관리자 없음. 매개변수는 제네시스 상수, 바꾸려면 프로토콜 업그레이드 |
| 구현 위치 | 계정 컨트랙트가 이미 서명자와 지불자를 나눌 수 있으므로 paymaster 방식: 거래 봉투에 `sponsor = pool`과 기기 증명을 붙이고, 실행 규칙이 자격·상한을 검사한 뒤 풀에서 수수료를 뺀다 |

## 알려진 공격과 대응(레드팀 전 초안)

| 공격 | 대응 |
|---|---|
| 기기 농장(Sybil): Mac·iPhone 여러 대로 대납을 반복 | 기기당 평생 한도라 얻는 것은 수수료뿐이고 토큰은 아니다. 풀 잔액·에포크 상한으로 총손실 상한 |
| 풀 고갈로 새 사용자 차단 | 에포크 상한 + 기기당 한도. 고갈돼도 1·2층(평소 0, 등록 무료)은 그대로 |
| 대납으로 스팸해 혼잡 유발 | 대납 거래는 유료 뒤 순서 + 블록당 개수 상한. 혼잡이 커지면 대납이 먼저 밀린다 |
| 증명 재사용(한 기기 증명을 여러 계정에) | 증명에 계정 주소를 묶고, 한도를 기기 단위로 센다 |
| 법적 분류 | 토큰을 주지 않고 수수료만 대신 낸다. 그래도 법적 분류는 단정하지 않고 법률 검토 목록에 올린다(레드팀) |

## 조사 반영 ([attest-sybil-2026.md](../research/attest-sybil-2026.md))

- Mac은 App Attest를 쓸 수 없다(일반 앱에서 false). Mac의 자격은 이미 있는 DeviceCheck 등록(1 Mac 1 후보)으로 하고, iPhone만 App Attest를 쓴다.
- 중고 iPhone은 한 대에 약 20~35달러이고, 초기화 한 번에 5~10분이면 새 기기로 보일 수 있다. 그래서 **기기당 평생 대납 한도는 초기화 한 번의 노력보다 훨씬 작게**, 전송 몇 건 분량으로 둔다.
- **상계:** 대납받은 수수료는 계정이 나중에 잔액을 가지고 유료 거래를 할 때 그 수수료에 얹어 풀로 되돌린다. 수수료만 빼먹고 떠나는 쪽의 실익이 없어진다.
- 1시간에 하루 상한의 20%를 넘게 쓰면 그 에포크 남은 동안 대납을 멈춘다(프로토콜 규칙, 관리자 없음).

## 레드팀 반영 (Codex, 2026-09-29)

| 지적 | 등급 | 바뀐 규칙 |
|---|---|---|
| 기기당 한도는 사람당 한도가 아님(기기 농장) | High | 기기 한도는 시빌 방지가 아니라 **손실 상한**으로 부른다. 계정당 에포크 한도, 거래당 최대 가스·수수료, 전역 예산을 따로 둔다 |
| 농장이 풀을 먼저 써서 정상 사용자를 막음 | High | 에포크 예산을 기기별로 공정하게 나눈다(한 기기가 한 에포크에 쓸 수 있는 몫 = 에포크 예산 ÷ 최근 활성 기기 수의 상한). N, X, 풀 상한, 에포크·블록 상한은 구현 때 제네시스 상수로 확정한다 |

| 합의 결정성 | High | Apple 확인은 등록 서비스에서 끝난다. 블록에는 등록 서비스 서명과 기기 키 서명만 싣고, 노드는 순수한 서명 검증과 체인 상태만 본다. 사용량·잔액·순서·실패 시 소비 규칙은 모두 체인 상태 |
| 무료 등록 레인에 운영자 승인이 없음 | Medium→**G2에 반영** | 운영자 지갑의 도메인 분리 서명(체인 ID, 레지스트리, 전체 등록 내용, 논스, 만료)을 요구하고 한 번만 소비 |
| 무료 등록의 누적 상태 | High→**G2에 반영** | 바이트·서명 검증·개수로 블록·에포크 제한. 기존 컨트랙트 경로와 같은 결과·같은 상한 |
| 대납 증명 재사용 | Medium | 기기 키 서명 대상 = 체인 ID, 풀 ID, 계정, 거래 해시, 논스, 수수료 상한, 만료. 수수료를 뺄 때 원자적으로 소비 |
