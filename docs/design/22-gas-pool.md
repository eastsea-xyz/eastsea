# 22. 처음 쓰는 지갑의 수수료: 수수료 0 경로와 공용 대납 풀 (2026-09-29)

근거: [15-node-rewards.md](15-node-rewards.md)(1/16 상한과 발행되지 않는 몫), `crates/execution/src/fees.rs`(기본 수수료는 목표 부하 이하에서 0), [14-registration.md](14-registration.md).

## 한 문장
> 새 지갑은 잔액 0으로도 거래한다. 평소에는 수수료가 0이고, 등록은 언제나 무료이며, 혼잡할 때만 **발행되지 않고 남는 보상의 일부**로 채운 공용 풀이 기기당 정해진 만큼 대신 낸다. 관리자 키는 없다.

## 세 층

| 층 | 언제 | 어떻게 | 비용을 누가 |
|---|---|---|---|
| 1. 수수료 0 | 블록이 목표 부하 이하(평소) | 기본 수수료가 이미 0. 지갑이 잔액 0이거나 기본 수수료 0이면 팁도 0으로 보낸다(G2) | 아무도 |
| 2. 무료 등록 | 언제나(혼잡 포함) | 투표 노드 등록을 블록 페이로드의 무수수료 항목으로 싣는다. 비콘 답과 같은 방식. 등록 서비스 서명 + Mac당 1회 + 에포크·블록당 개수 상한(G2) | 아무도(개수 상한이 스팸 방지) |
| 3. 공용 대납 풀 | 혼잡해서 기본 수수료 > 0이고 계정 잔액이 모자랄 때 | 프로토콜 계정이 수수료만 대신 낸다(토큰을 나눠주지 않음) | 발행되지 않고 남는 노드 몫의 일부 |

## 3층: 공용 대납 풀

| 항목 | 규칙 |
|---|---|
| 재원 | 에포크마다 **발행되지 않는 노드 몫**(1/16 상한 때문에 남는 부분)의 1%를 풀에 발행. 누구 몫도 줄지 않는다. 운영자가 16명을 넘어 남는 몫이 0이면 풀도 채워지지 않는다 |
| 풀 상한 | 잔액 상한 고정(예: 하루 평균 대납액 × 30). 넘는 몫은 발행하지 않는다 |
| 쓰임 | 수수료 대납만. 풀에서 사용자 잔액으로는 한 푼도 옮기지 않는다. 대납 거래의 값(value)은 0이어야 하고, 대상은 허용 목록(전송, 토큰 전송, 등록된 계정 컨트랙트 호출) |
| 자격 | 인증된 기기: Mac은 DeviceCheck 등록, iPhone은 App Attest 키. 기기마다 **평생 N건 또는 수수료 합계 X** 중 먼저 닿는 쪽까지 |
| 속도 상한 | 에포크당 풀 전체 대납 상한과 블록당 대납 거래 수 상한. 넘으면 다음 블록으로 |
| 순서 | 대납 거래는 같은 블록의 유료 거래 뒤에 온다(혼잡을 키우지 않음) |
| 관리 | 관리자 없음. 매개변수는 제네시스 상수, 바꾸려면 프로토콜 업그레이드 |
| 구현 위치 | 계정 컨트랙트가 이미 서명자와 지불자를 나눌 수 있으므로 paymaster 방식: 거래 봉투에 `sponsor = pool`과 기기 증명을 붙이고, 실행 규칙이 자격·상한을 검사한 뒤 풀에서 수수료를 뺀다 |

## 알려진 공격과 대응(레드팀 전 초안)

| 공격 | 대응 |
|---|---|
| 기기 농장(Sybil): Mac·iPhone 여러 대로 대납을 반복 | 기기당 평생 한도라 얻는 것은 수수료뿐이고 토큰은 아니다. 풀 잔액·에포크 상한으로 총손실 상한 |
| 풀 고갈로 새 사용자 차단 | 에포크 상한 + 기기당 한도. 고갈돼도 1·2층(평소 0, 등록 무료)은 그대로 |
| 대납으로 스팸해 혼잡 유발 | 대납 거래는 유료 뒤 순서 + 블록당 개수 상한. 혼잡이 커지면 대납이 먼저 밀린다 |
| 증명 재사용(한 기기 증명을 여러 계정에) | 증명에 계정 주소를 묶고, 한도를 기기 단위로 센다 |
| 법적으로 에어드롭처럼 보임 | 토큰을 주지 않고 수수료만 대신 낸다. 풀 잔액은 누구에게도 이전되지 않는다 |
