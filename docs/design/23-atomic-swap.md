# 23. 원자적 스왑 1단계: HTLC (2026-09-30)

근거: [21-crosschain.md](21-crosschain.md)의 레드팀 반영 표와 [crosschain-2026.md](../research/crosschain-2026.md). 이 문서는 지갑·메이커가 함께 지켜야 할 실행 규칙이다. 아래 시간과 확인 수는 **초기 정책안**이며, 실제 체인 최종성과 수수료 지연을 측정한 뒤 배포 전에 다시 확정한다.

## 컨트랙트와 자산

`AtomicSwap.sol`은 EastSea의 DBLN 및 표준 ERC-20을, 같은 구현을 상속한 `AtomicSwapEVM.sol`은 Ethereum·BNB·Base의 네이티브 코인 및 표준 ERC-20을 잠근다. 배포 주소와 체인 ID만 다르다. 관리자·업그레이드·수수료·임의 지급 기능은 없다. `token = address(0)`은 네이티브 코인이다. ERC-20의 입금량 및 수취량이 요청량과 정확히 같지 않으면 전체 거래를 되돌린다. 리베이스가 거래 사이에 일어나는 자산은 온체인 검사만으로 안전성을 보장할 수 없으므로 호가와 지갑의 지원 자산 목록에서 제외한다.

`lock(recipient, hashlock, timelock, token, amount)`은 잠금 ID를 반환한다. `hashlock = SHA256(preimage)`이며, `timelock`은 Unix 초 단위 블록 타임스탬프다. `claim(id, preimage)`은 기한 **전**에 누구나 제출할 수 있지만 돈은 잠글 때 고정한 `recipient`에게만 간다. `refund(id)`는 기한 **이후** 누구나 실행할 수 있지만 돈은 원래 `sender`에게만 간다. 같은 ID는 한 번만 정산된다. 잠금 이벤트의 ID·해시·수취인·기한과 체인 ID·컨트랙트 주소를 함께 확인해야 다른 배포의 로그와 혼동하지 않는다. `claim`이 공개한 원문 프리이미지는 상대 체인 청구에 사용한다.

## 체인 쌍별 대기 및 기한

메이커는 **최종성이 더 느린 체인에 먼저 잠근다**. 아래 `H`는 메이커 잠금을 포함한 블록 높이, `T`는 그 잠금의 블록 시간이다. Aether 잠금은 메이커 잠금이 정해진 확인 수를 채운 뒤에만 만든다. EVM 잠금에는 높이를 쓰지 않고 Unix 타임스탬프를 쓴다. Bitcoin은 아래 P2WSH의 절대 높이 `OP_CHECKLOCKTIMEVERIFY`를 쓴다.

| 쌍 / 메이커 선잠금 체인 | 메이커 잠금 확정 조건 | 메이커 환불 높이 또는 시각 | 사용자 Aether 환불 시각 | 추가 수수료·지연 버퍼 |
|---|---|---|---|---|
| Bitcoin ↔ Aether | Bitcoin **6확인**; 재구성 시 다시 6확인 | Bitcoin `H + 144` 블록 (공칭 약 24시간) | `T + 72시간` 이상, 동시에 예상 Bitcoin 환불 가능 시각보다 **엄격히 나중** | Bitcoin 청구 확인·수수료 급등·재전송에 24시간 이상 |
| Ethereum ↔ Aether | Ethereum finalized 체크포인트에 잠금 포함 확인 | Ethereum `T + 24시간` | `T + 48시간` 이상 | 청구 확정·가스 급등에 12시간 이상 |
| BNB ↔ Aether | 잠금 후 30블록 및 체인 최종성 확인 | BNB `T + 24시간` | `T + 48시간` 이상 | 재구성·가스 지연에 12시간 이상 |
| Base ↔ Aether | L1에 게시된 상태의 확정까지 확인 | Base `T + 9일` | `T + 11일` 이상 | L1 게시·증명 지연에 24시간 이상 |

Bitcoin 블록 높이와 Aether 타임스탬프 사이에는 확정적인 환산식이 없다. 따라서 `H + 144`와 `T + 72시간`만으로 **엄격한 선후 관계를 수학적으로 보장하지 못한다**. 지갑은 사용자 잠금 직전에 최신 Bitcoin 높이·MTP·수수료를 다시 읽고, Bitcoin 환불 예상 시각 + 24시간보다 Aether 환불 시각이 늦지 않으면 거래를 중단한다. Bitcoin이 장시간 멈추거나 재구성되면 새 거래를 중단하고 진행 중인 거래를 감시·수동 대응한다. 운영 정책이 높이 기반 잠금과 절대 시간 잠금 간의 이 한계를 해결할 때까지 이 표는 배포 승인 근거가 아니다. 상대 체인이 Aether보다 느려지는 경우에도 같은 방식으로 잠금 순서와 기한을 다시 계산한다.

두 환불 기한 모두 단순 비율 하나로 계산하지 않는다. 사용자가 받을 체인에서 청구하고 프리이미지가 충분히 확정된 뒤, 메이커가 Aether에서 청구할 수 있도록 Aether 기한을 늦게 잡는다. 지갑은 호가가 요구한 확인 수·남은 시간·버퍼를 만족하지 않으면 잠금 버튼을 활성화하지 않는다.

## 호가와 지갑 상태 흐름

1. **호가:** 메이커의 서명된 호가에 체인 ID, 각 컨트랙트 주소, 자산·수량, 고정 수취인, SHA-256 해시, 두 환불 기한, 확인 수, 수수료 버퍼, 호가 만료 시각, 메이커 보증금 식별자를 넣는다. 사용자가 로컬에서 무작위 32바이트 프리이미지를 만들고 비밀 저장소에 보관한다. 프리이미지는 청구 시점 전에는 메이커에게 보내지 않는다.
2. **메이커 잠금 관찰·확정:** 메이커가 느린 체인에 먼저 잠근다. 지갑은 트랜잭션 성공만 보지 않고 이벤트/Bitcoin 스크립트의 금액·해시·수취인·기한을 호가와 대조하고 표의 최종성을 기다린다. 재구성 시 확정 상태를 취소한다.
3. **사용자 잠금:** 메이커 잠금이 확정된 뒤 빠른 체인(EastSea)에 같은 해시와 메이커 고정 주소로 잠근다. 그 직전 기한·수수료를 재검사하고 충분한 DBLN 가스를 남긴다. 한쪽 잠금이 실패하면 상대방에게 비밀을 공개하지 않는다.
4. **청구:** 사용자가 메이커 쪽 자산을 청구하며 프리이미지를 공개한다. 메이커는 공개된 프리이미지로 사용자 잠금을 청구한다. 제3자가 청구를 앞지르더라도 컨트랙트는 고정 수취인에게만 지급한다. 각 체인의 정산 확정을 별도로 표시한다.
5. **환불 안내:** 잠금이 열린 채 기한이 가까워지면 로컬 알림을 반복한다. 기한 뒤에는 `refund` 거래를 준비하고 가스·Bitcoin 채굴 수수료를 확인시킨다. 지갑 종료 중에도 복귀 시 만료 잠금을 재검색한다. 환불은 자동 실행을 약속하지 않는다. 지갑이 꺼져 있어도 누구나 환불을 호출할 수 있지만 Bitcoin은 사용자의 서명이 필요하다.

## 메이커 보증금과 미이행 기록

메이커는 호가 발행 전에 자산별 보증금 잔액을 공개하고, 호가에 보증금 식별자·최대 동시 호가액·잠금 제출 마감 시각을 서명한다. 메이커가 기한 안에 맞는 잠금을 만들지 않거나 잘못된 금액·수취인·해시로 잠그면 `quote_id`, 서명 호가, 관찰 높이·해시, 최종성 상태와 함께 미이행 기록을 남긴다. 재구성이나 RPC 누락을 오판하지 않도록 여러 독립 관찰 결과를 보관하고 이의 제기 기간을 둔다. 지갑은 반복 미이행 메이커의 호가를 숨기고 사용자는 기록을 확인할 수 있다.

보증금 몰수는 **별도 단계**다. Aether HTLC가 Bitcoin/EVM의 잠금 부재를 증명할 수는 없다. 신뢰 가능한 라이트 클라이언트·포함/부재 증명 또는 명시적 중재 규칙이 마련되기 전에는 부재 주장만으로 자동 몰수하지 않는다. 이 컨트랙트에는 보증금이나 운영자 판정 권한을 넣지 않는다. 보증금의 잠금·해제·분쟁·배상 정책은 독립 설계와 감사를 거쳐야 한다.

## Bitcoin P2WSH 템플릿 (문서 예시)

메이커가 Bitcoin을 먼저 잠그는 방향의 witness script 예시다. `recipient_pubkey`는 사용자, `refund_pubkey`는 메이커 키다. `H_refund`는 **블록 높이**이며 500,000,000 미만이어야 한다. 실제 구현은 최소 인코딩·표준성·서명 해시·수수료·UTXO 선택을 별도로 검증한다.

```text
OP_IF
    OP_SHA256 <hashlock_32> OP_EQUALVERIFY
    <recipient_pubkey> OP_CHECKSIG
OP_ELSE
    <H_refund> OP_CHECKLOCKTIMEVERIFY OP_DROP
    <refund_pubkey> OP_CHECKSIG
OP_ENDIF
```

청구 witness는 `<recipient_signature> <preimage> OP_TRUE <witness_script>`이고 환불 witness는 `<refund_signature> OP_FALSE <witness_script>`다. 환불 거래의 `nLockTime >= H_refund`, 해당 입력의 `nSequence < 0xffffffff`가 필요하다. EVM의 `sha256(bytes)`와 Bitcoin의 `OP_SHA256`이 **같은 원시 바이트**를 해시하도록 인코딩을 고정한다. Bitcoin 스크립트의 수취인은 공개키로 고정되며, EVM의 수취인은 주소로 고정된다.
