# 30. 출시 후 수정 가능성: 인벤토리, 수정 경로, 구멍

작성: 2026-10-05. 방침(창업자, 2026-10-05): **메인넷을 베타로 열고 출시 뒤에 계속 고친다.** 출시 전에 깐깐하게 걸러 놓고 출시 뒤에는 고치기 어렵게 만드는 것이 더 나쁘다 — 출시 뒤에 문제는 출시 전보다 많이 나온다. 게이트는 미해결 Critical 없음, **제네시스에서만 고칠 수 있는 High는 제네시스 전에**, 나머지는 전부 출시 후 패치. 이 문서의 임무는 출시 후 수정이 **쉽고, 빠르고, 안전한지** 점검하고, 어렵게 만드는 것을 미리 찾는 것이다. 이 문서 자체는 규칙을 바꾸지 않는다.

관련: [12-launch-plan.md](12-launch-plan.md)(결정 기록), [19-release-approval.md](19-release-approval.md)(앱 릴리스 승인), [24-self-healing.md](24-self-healing.md)(자가 회복), [13-protocol-2.md](13-protocol-2.md)(증명 시장·레지스트라 상한), [15-node-rewards.md](15-node-rewards.md)(발행), `docs/ops/mainnet-launch.md`(출시 절차·중단 기준), `docs/ops/consensus-recovery.md`(합의 복구).

## 0. 요약

수정 경로는 세 개뿐이고 셋 다 이미 만들어져 있다: **서명 앱 릴리스**(노드 바이너리는 앱 안에 있다), **프로토콜 업그레이드**(위원회 임계 서명, 7일 예고), **긴급 업그레이드**(위원 전원 승인, 1 에포크 = 1시간 예고). 컨트랙트에는 어드민·일시정지가 **의도적으로 없다**. 제동이 없는 자리가 세 곳이다: (1) 긴급 업그레이드가 위원 **전원** 승인을 요구해 한 명이 닿지 않으면 가장 빠른 경로가 막힌다(제네시스 전 결정), (2) 컨트랙트 계열 사고에 온체인 제동이 없다(DEX 배포 전 결정), (3) 현장에서 어떤 버전이 몇 대 도는지 알 수 없어 패치의 성공을 측정할 수 없다(출시 후 추가). 제네시스 전에 **결정**해야 하는 것은 이 세 개 중 앞의 두 개와, 예고 길이 7일·릴리스 승인 핀목록처럼 제네시스 파일·출시 창구에 굽는 값들이다(§4).

## 1. 인벤토리: 출시 뒤에 의미가 있는 모든 규칙·상수·파라미터

변경 경로 범례:

| 표시 | 경로 | 절차 |
|---|---|---|
| **U** | 프로토콜 업그레이드 | 위원회 임계 서명 → 블록 payload → 활성화까지 최소 **7일**(604,800블록; `upgrade.rs` `MAINNET_NOTICE_BLOCKS`, `chain.rs` `admissible_upgrade`) |
| **E** | 긴급 업그레이드 | 현재 위원 **전원** ed25519 승인 + 임계 서명, 예고 **1 에포크(3,600블록 ≈ 1시간)**, 앱에 긴급 표시 |
| **A** | 서명 앱 릴리스 | 일반 2/3 빌더 서명 + ReleaseLog 게시 후 **72시간**; 긴급 3/3 **즉시**. 노드 바이너리는 앱 번들 안(`Helpers/aether`) |
| **R** | 노드 재시작 | 바이너리 안의 로컬 값. 합의 무관. 사실상 A의 부분집합(앱이 노드를 싣는다) |
| **C** | 컨트랙트 관리자 호출 | **존재하지 않음.** 모든 컨트랙트가 불변·무관리자(원칙, 문서 12 생태계 트랙) |

### 1.1 제네시스 파일(network.json)이 굽는 값 — 출시 후 변경 불가(X)

체인 ID(7780/7799 제외한 새 값; `mainnet.rs` 예약 검사), 제네시스 위원회(validator 키 + DKG `identity`/`output`; 최종 파일 게이트가 좌석·그룹키 일치 검증), 창업자 예비 키(최대 3), 사전 발행 0·faucet 없음, 제네시스 프로토콜 3, `history_v2`, `node_rewards`, `group`(0), `max_committee = 16`. 신규 제네시스의 앱 `network.json`은 여기에 릴리스 승인 핀목록(ReleaseLog 주소·런타임 코드 해시·빌더 공개키 3개, 문서 19)을 더한다 — **이 파일이 없으면 앱은 신규 네트워크 설치를 거부한다.**

- 예외: **레지스트라 키**는 제네시스에 있지만 업그레이드 `registrar` 필드로 교체·철회 가능(U/E; `registry.rs` `set_registrar`, 0이면 등록 중지).

### 1.3 체인 상태(컨트랙트 저장)에 있지만 손으로 못 바꾸는 값

레지스트라 키(슬롯 0/1, U/E로 교체), 에포크 파라미터(제네시스 세팅, U로만), 등록 상한(§1.2). **컨트랙트 코드 전부가 불변**: EastSeaAccount(v2, 세션 키·가디언), EastSeaNames, EastSeaVault, CommitteeRegistry(v3), AtomicSwap, TokenLocker, MerkleDistributor, Randomness, ReleaseLog — 어드민·일시정지·업그레이드 없음. 계정 컨트랙트 버그는 **새 주소 배포 + 재위임**(EIP-7702, `forks.rs` 주석)로 고친다. 그 외 컨트랙트 버그는 새 배포 또는 U(§2c).

프리디플로이 주소(`REGISTRY 0x…7703`, `REWARDS 0x…7704`, `FEE_COLLECTOR 0x…fee00`, `PROVER_ESCROW 0x…e5c00`)는 합의 상수. 사용자 컨트랙트 주소(Names·Vault·ReleaseLog 등)는 배포 결과로 정해지고 앱 `network.json`에 고정된다.

### 1.4 노드 로컬 값 — 재시작(사실상 A)으로 바꿈, 합의 무관

멤풀(50,000건·64 MiB, 보낸 사람당 64, TTL 10분, 무료 몫 1/4·1/8, 수수료 대기 60초 — `chain.rs`), 스냅샷 청크 1 MiB(`rpc.rs`), 가지치기 기본 30일·에라 파일 보존, 자원 한도(디스크 5GB 정지·10GB 재개, 스왑 500‰, 증명 재개 5분 — `resources.rs`), 감시·백오프(1초→60초, 10분에 3회, 5분 생존 = 진행 — `supervisor.rs`), DKG 타이머(단계 후 릴레이 60초, share 준비 창 120초, 합의 뷰 틱·백오프 — `dkg.rs`, `dkg_agreement.rs`), 종료 코드 3(업데이트 필요)·4(저장소)·5(검증기 없음)·6(신원)·7(잠금)·8(투표 저널). 스냅샷은 폐기 가능(스냅샷 점프로 재취득)해서 버전 필드가 필요 없는 좋은 성질이다.

### 1.5 서명·배포 체인(앱)

빌더 키 3개(각 빌드 Mac Secure Enclave P-256; 일반 2/3·긴급 3/3; 교체는 "구 버전 검증 규칙을 먼저 통과한 서명 릴리스"로만), Sparkle EdDSA 키·appcast(GitHub Releases), Apple Developer ID 서명·공증(Pipln), 업데이트 확인 주기 3,600초(Sparkle 최소) + **체인이 더 새 프로토콜를 예약하면 즉시 확인**(구현됨), 일반 릴리스 72시간 대기(게시 블록 인증 시각 기준). 레지스트라 서명자는 별도의 서명 전용 Mac(`docs/ops/registrar.md`).

## 2. 수정 경로, 끝까지, 시간표와 함께

### (a) 노드 전용 버그(합의 변경 없음): 서명 앱 릴리스

`app-vX` 태그 → 세 Mac 독립 빌드·비교(재현 빌드 검증, `builder-build.sh`, ~1–2시간) → 2/3 서명 → ReleaseLog 게시 + GitHub Releases 업로드 → **72시간** → Sparkle가 시간당 확인으로 잡아 백그라운드 설치, 다음 실행에 적용.

- **정상 릴리스: 활동 중인 대부분의 Mac이 약 73–78시간 안에 새 노드** (72시간 대기 + 최대 1시간 확인 주기 + 재실행). 로그인 항목이 기본 켜짐이라 메뉴바 앱은 상시 구동이 보통이다.
- **긴급 앱 릴리스(3/3, 즉시): 약 1–2시간.**
- 노드만 죽어도 지갑은 원격 노드 폴백(문서 24 층 3)으로 계속 동작하고, 설치 뒤 60초 내 3회 죽으면 `aether.prev`로 되돌린다(감시 층 2).
- 한계: 앱을 켜지 않는 Mac은 못 받는다. 그리고 **몇 대가 새 버전으로 넘어갔는지 우리가 모른다**(§3 G1).

### (b) 합의 버그: 프로토콜 업그레이드

위원 임계 서명(`aether upgrade-sign/combine`) → 서명된 업그레이드가 블록 payload에 실려 체인에 기록(높이 h) → 활성화 높이 ≥ h + 604,800. 활성화 블록에서 `forks::activate`가 일회 상태 변경을 실행한다(제네시스는 다시 안 바뀐다).

- 노드와 앱은 상태의 예약(`newest_scheduled`)을 보고, **앱은 더 새 프로토콜이 예약되는 즉시 업데이트를 확인한다**(구현됨).
- **예고 기간 안에 못 올라온 노드: 활성화 높이 전에 스스로 멈춘다**(종료 코드 3). 감시는 코드 3을 재시작하지 않고 "업데이트 필요" 한 문장; 그동안 지갑은 원격 노드로 동작. `aether.prev` 롤백은 이전 바이너리가 예약된 프로토콜을 지원한다고 답할 때만 허용(`aether protocol` 즉답).
- 정족수 산술: 16석 중 11석만 새 프로토콜이어도 체인은 계속 확정한다. 예전 바이너리가 6석 이상이면 활성화 순간 체인이 잠시 멈춘다(안전이 깨지는 것이 아니라 그들이 올라올 때까지 활동이 멈추는 것).
- 시간표: 서명·게시 준비 ~1일 + **최소 7일 예고**. 출시 전 검증 도구로 **메인넷 그림자 재실행**(`aether shadow`: 새 바이너리로 제네시스부터 재실행해 같은 결과 확인)이 있다.
- 7일이 긴급 상황에 너무 길면 (c)의 긴급 업그레이드(1시간 예고)가 유일한 단축 경로다.

### (c) 실제로 익스플로잇 중인 Critical: 비상 경로

- **앱·노드 계열**: 긴급 릴리스(3/3, 즉시)로 바이너리를 고치고, 규칙까지 손대야 하면 긴급 업그레이드(위원 전원 승인 + 1 에포크 예고). 현실적 총 시간 **수 시간**(빌드·서명·게시 1–2시간 + 1시간 예고 + 시간당 확인). 지갑은 원격 폴백으로 즉시 대응.
- **컨트랙트 계열(names·vault·스왑·런치패드)**: **일시정지도 어드민도 없다**(불변·무관리자 원칙). 오늘 가능한 것은 (1) 서명 앱 릴리스로 지갑·탐색기가 문제의 컨트랙트·메서드를 차단(빠르지만 CLI·에이전트 사용자는 못 막음), (2) 그 주소로의 호출을 거부하는 프로토콜 업그레이드(U 7일, 긴급이면 1시간 + 전원 승인). 이미 들어간 자금의 회수 경로는 원래 없다(비수탁·불변).
- **레지스트라 키 유출**: 업그레이드 `registrar` 필드로 교체·0으로 철회(U 7일 / E 1시간). 이미 설계·구현됨.
- **빌더·Sparkle 키 1개 유출**: 2/3 규칙이 혼자서는 업데이트를 못 밀게 막는다. 교체는 나머지 키의 서명 릴리스로(구 규칙 통과 후).
- **가장 작은 안전한 설계(제안 — 이번엔 구현하지 않음, 합의 변경)**: 긴급 업그레이드 payload에 선택적 **동결 주소 목록**을 실어, 실행 계층이 프로토콜 버전에 따라 그 주소로의 호출을 거부하게 한다. 전원 서명 + 1 에포크 예고라는 기존 비상 절차를 그대로 타고, 한 컨트랙트만 1시간 안에 얼린다. 컨트랙트에 어드민을 만들지 않는 원칙은 지켜진다 — 제동은 언제나 위원회 서명으로만 걸린다.

## 3. 출시 후 수정을 어렵게 만드는 구멍 (순위)

형식: 심각도(베타 기준) / 가장 작은 수정 / 제네시스 전인가.

**G1. 현장 가시성이 없다.** 어떤 앱·노드 버전이 몇 대 도는지, 어떤 실패가 얼마나 자주 나는지 알 수 없다. "수정을 배포했다"와 "수정이 퍼졌다"가 다른 상태인데 뒤를 측정할 방법이 없다. 심각도 **High**(빈번한 패치가 기대되는 베타). 수정: 옵트인 무기명 상태 신호(버전·높이·플랫폼·실패 종류; 개인 데이터 없음; 원격 조작 금지 원칙과 양립 — 사용자가 켜는 신호일 뿐이다). **후.**

**G2. 단계별 롤아웃(카나리)이 없다.** appcast는 모두에게 한 번에 배포된다. 나쁜 "수정"이 100%에 동시 적용되고, 노드 롤백(`aether.prev`)은 있지만 앱 자체의 되돌림은 새 릴리스를 또 밀어야 한다. 심각도 **High**. 수정: 옵트인 카나리 피드(“미리 채널” appcast URL) 또는 appcast의 단계적 배포 태그로 자동 비율 상승. **후**, 저렴.

**G3. 컨트랙트에 대한 온체인 제동이 없다.** §2(c). DEX·런치패드가 출시와 함께라면 심각도 **High**(자금 접점). 수정: 위의 동결 목록 설계(합의 변경, U로 추가 가능 — 그러나 존재하지 않는 동안 사고가 나면 제동이 없다). **제네시스 직전·DEX 배포 전 결정 사항**(배포가 되돌릴 수 없는 시점).

**G4. 수수료·한도가 코드 상수다.** 모든 조정이 7일 업그레이드 + 새 바이너리를 필요로 한다. 레지스트리 파라미터(에포크 길이 등)는 이미 상태에 사는데 수수료 묶음은 안 그렇다 — 패턴은 이미 있다. 심각도 **Medium**(현재 값들이 합리적; 가장 유력한 조정 사유는 스팸 대응). 수정: 수수료 묶음을 레지스트리 파라미터 패턴(상태 저장 + 업그레이드 시스템 쓰기, 경계 안에서)으로 이전 — 파라미터당 한 번의 합의 변경 뒤로는 바이너리 없이 조정. **후**(메커니즘 추가 자체가 U).

**G5. 긴급 업그레이드가 위원 전원 승인을 요구한다.** 한 명이 자고 있거나 연락 두절이면 가장 빠른 수정 경로가 막힌다. 16운영자 베타에서 전원이 몇 시간 안에 서명할 확률이 낮다. 심각도 **High**. 수정: 긴급 승인 정족수 완화(예: 위원회 임계 + 빌더 3/3, 또는 n−f 위원) — 여전히 1 에포크 예고·앱 긴급 표시. 이 규칙을 바꾸는 것 자체가 평범한 U(7일)라, 사고가 나고 나서는 늦는다. **제네시스 전 결정.**

**G6. 블록 한도에 프로토콜 스위치가 없다.** exec/prove 한도는 바이너리 상수(`chain_config`)라서 값이 바뀐 새 바이너리와 예전 바이너리가 어긋나는 순간부터 높이 기반 전환 없이 포크 위험이 생긴다(에포크 파라미터·등록 상한과 다르게 상태나 프로토콜 버전에서 읽지 않는다). 심각도 **Medium**(당장 바꿀 이유는 없다; 바꾸려 할 때 문제가 된다). 수정: 한도를 프로토콜 버전 테이블(또는 상태 파라미터)에서 도출해 활성화 높이에 원자적으로 전환. **후**(메커니즘 추가 자체가 U; 그 전까지 한도는 불변 취급).

**G7. 에라 파일·마샬 아카이브 파티션에 버전이 없다.** 상태 DB는 스키마 버전 v1 + 단계 표식 + TooNew 거부 체계가 있으나(문서 24 구현 3부), 이력 증거 파일은 그 체계 밖이다. 심각도 **Low-Medium**(이력은 영구 증거라 형식 교체가 신중해야 한다). 수정: 다음 에라 형식 개편 때 매직+버전 헤더, 리더는 v1 계속 수용. **후.**

**G8. `run-state.json`에 버전이 없었다.** 감시의 재시작 이력이 무버전 배열로 저장됐다. 심각도 Low. 수정: **이번 커밋에서 버전 묶음(`{v:1, exits:[…]}`) 추가 — 낡은 배열 형태는 그대로 읽고, 미래 형식은 거부(빈 것으로 치지 않는다)**. 완료.

**G9. 레지스트라 서명자가 단일(서명 전용) Mac이다.** 그 Mac이 죽으면 새 등록·재인증이 멈춘다(기존 후보는 유예 24에포크 = 24시간). 런북이 있고(`docs/ops/registrar.md`) 키 회전 경로(E)가 있으므로 절차 문제. 심각도 **Low-Medium**. 수정: 런북 리허설을 출시 절차에 포함. **후.**

**G10. 체인을 멈추는 스위치가 없다(의도적).** 어드민 정지 기능을 만들지 않은 것은 원칙이다. 합의 자체가 깨진 상황은 `consensus-recovery.md`의 복구 절차(함께 재시작)가 담당하고, 규칙 수준의 제동은 긴급 업그레이드가 담당한다. 수용하고 문서로만 남긴다(§2(c)).

**구멍이 아닌 것(이미 강한 부분)**: 종료 코드 프로토콜과 감시의 원인별 대응, 자가 회복 4층(문서 24), 원격 지갑 폴백, 블록마다 프로토콜 버전 기록, 상태 안의 레지스트리 파라미터, DB 스키마 버전 + TooNew 거부 + 멱등 마이그레이션(롤백 없음이 안전한 이유: 앞으로만 가고 못 가면 종료 코드 3으로 멈춘다), 재현 빌드·2/3 빌더 서명·ReleaseLog, 긴급 3/3 앱 경로, 그림자 재실행, 스냅샷 점프(폐기 가능 재동기화).

## 4. 제네시스 전 체크리스트 (§3에서 제네시스 뒤에 불가능하거나 훨씬 어려워지는 것만)

1. **긴급 업그레이드 승인 규칙의 최종본**(G5). 전원제 유지인지 완화인지 지금 결정한다. 뒤에 바꾸려면 7일짜리 U가 필요하고, 그 U가 필요한 상황(긴급)에서는 이미 늦는다.
2. **DEX·런치패드와 함께 갈 제동 방식**(G3). 동결 목록 설계 확정(및 프로토콜에 반영) 또는 "제동 없음"의 명시적 수용. 배포가 되돌릴 수 없는 시점이다.
3. **릴리스 승인 핀목록이 출시 `network.json`에 실제로 들어갔는지**(ReleaseLog 주소·코드 해시·빌더 키 3개 — 문서 19; 없으면 앱이 신규 네트워크 설치를 거부한다).
4. **예고 길이 604,800블록(7일) 확정.** 코드 상수로 제네시스부터 시행된다. 더 짧은 기본값을 원한다면 지금이 유일한 창이다(길어지는 방향은 나중에도 U로 가능).
5. **제네시스 값 검증은 이미 기계적**(`aether mainnet-rules` 19개 규칙 + 최종 파일 게이트 4개, `mainnet.rs`): 체인 ID·프로토콜 3·레지스트라 키·에포크 파라미터·16석 성장·사전 발행 0이 전부 켜졌는지 출시 절차(`docs/ops/mainnet-launch.md` 4단계)의 당사자 확인과 함께 실행한다.

G1·G2·G4·G6·G7·G9는 출시 뒤에 추가해도 안전하다(메커니즘은 릴리스·U로 붙인다). 순서 권고: G1·G2(패치 신뢰성의 뼈대)를 출시 직후 첫 스프린트로.
