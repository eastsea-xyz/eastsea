## 0. 요약

- 놓친 사고 세 건(2026-10-05/06): **증명 보상 5일간 소리 없이 0**(지갑 증명기의 guest 프로그램 ID가 검증자와 달랐다), **재부팅 뒤 "connecting…"에 멈춘 지갑**, **디스크가 가득 찬(ENOSPC) 뒤 반쯤 죽은 검증자**. 세 건 모두 **어떤 사용자 데이터도 없이 잡을 수 있었다**. 지갑이 자기 상태를 알고 있었고(`aether_proverStatus`의 `program_mismatch`, `aether_status`의 `resources.disk_low`), 체인이 공개적으로 보여 주고 있었다(블록의 증명·보상). 그 사실을 **사람이 알아듣는 말로 바꿔 알리는 장치가 없었을 뿐이다.**
- 그래서 순서는 이렇다. **층 0: 체인에서 읽는 공개 건강 지표**(보고 없음), **층 1: 지갑이 스스로 진단해서 사용자에게 할 일을 알림**(보고 없음), **층 2: 옵트인 상태 신호**(기본 꺼짐, 버킷 값만, 식별자 없음). 베타에는 층 0·층 1과 카나리 링만 싣는다. 층 2는 출시 직후 첫 패치 릴리스에서, 처리방침을 고치고 법률 확인을 받은 뒤에 켤 수 있게 한다.
- 층 2의 전송은 **(a) 기존 iroh RPC로 아무 공개 노드에나 보내고, 아무 노드나 집계해서 서명된 요약을 공개하는 방식**을 고른다. Pipln 서버가 필요 없고 Pipln이 데이터 경로에 없어도 된다. 대시보드는 오픈소스 탐색기 페이지이므로 누구나 띄워 읽는다.
- G2 카나리는 **새 키 없이** Sparkle의 채널(`sparkle:channel`)과 단계 배포(`sparkle:phasedRolloutInterval`)로 한다. 카나리든 일반이든 **같은 ReleaseLog 항목·같은 2/3 서명·같은 72시간 대기**를 지난다. 채널은 *언제 제안되느냐*만 바꾸고 *무엇이 승인되느냐*는 바꾸지 않는다. 긴급(3/3)은 카나리와 단계를 건너뛴다.

## 1. 목표와 비목표

### 목표

1. **"수정을 배포했다"와 "수정이 퍼졌다"를 구분해서 측정한다**(G1). 어떤 앱·노드 버전이 대략 몇 대 도는지, 어떤 실패가 어떤 버전에서 늘었는지 본다.
2. **사고를 시간 단위로 알아챈다**(일 단위가 아니다). 증명 보상 0이 5일 가지 않게 한다.
3. **사용자에게 기술 대신 답을 준다.** 실패가 나면 사용자가 무엇을 하면 되는지 한 문장으로 알린다("보상 증명이 거절되고 있어요 → 업데이트하세요").
4. **나쁜 수정이 100%에 동시에 깔리지 않게 한다**(G2). 먼저 받겠다고 한 사람에게 먼저 보내고, 문제가 보이면 일반 배포를 멈춘다.

### 비목표 (하지 않는 것)

- **사용자 텔레메트리가 아니다.** 사용 패턴, 화면, 클릭, 거래, 세션 길이는 보지 않는다.
- **주소, 잔액, 거래 해시, 노드 ID, 피어 목록, IP 주소, 호스트 이름, 하드웨어 모델, 정확한 시각을 보내지도 보관하지도 않는다.** 받는 노드는 전송 중에 IP를 볼 수밖에 없지만(§3.4) 보고를 받자마자 카운터에 더하고 원문과 연결 정보를 버린다.
- **체인이 이 기능에 의존하지 않는다.** 상태 신호, 집계 노드, 대시보드, Pipln 서버 중 무엇이 없어도 합의·지갑·업데이트는 그대로 동작한다. 합의 변경도 없다.
- **원격 조작이 아니다.** 신호는 한 방향이다. 집계 결과가 사용자 기기의 동작을 자동으로 바꾸는 경로는 없다. 집계는 위조될 수 있으므로 사람이 보는 정보일 뿐이다(§3.5). 카나리 정지도 *배포 피드에서 항목을 빼는 것*이지 기기에 내리는 명령이 아니다.
- **Pipln의 관문을 만들지 않는다.** Pipln만 읽을 수 있는 데이터, Pipln만 운영할 수 있는 수집 서버, Pipln 키로만 바꿀 수 있는 설정을 만들지 않는다.

## 2. 무엇을 보고할 수 있나 (층 2, 옵트인)

### 2.1 동의 화면 원칙

- **기본은 꺼짐.** 첫 실행 온보딩에서 묻지 않는다(첫 화면은 잔액이어야 한다, 09 온보딩). 설정 ▸ 개인정보에 스위치 하나를 둔다. 문제가 생겨 알림을 띄울 때 "다른 사람들이 같은 문제를 겪는지 알리려면 상태 신호를 켤 수 있어요"라는 링크를 함께 둘 수 있다. 자동으로 켜지는 일은 없다.
- **켜기 전에 실제로 보낼 내용을 그대로 보여 준다.** 요약 문장과 함께 "보낼 내용 보기"를 누르면 지금 이 기기가 보낼 보고 원문(§2.3 JSON)이 펼쳐진다. 화면 문구 초안:
  > **상태 신호 보내기 (선택)**
  > 앱이 잘 도는지 알려 주는 짧은 신호를 하루 한 번 네트워크에 보냅니다. 앱 버전, macOS 버전, 체인을 얼마나 따라잡았는지, 최근에 난 오류의 종류만 들어갑니다. **주소·잔액·거래·이름·이 Mac을 가리키는 번호는 들어가지 않습니다.** 받는 노드는 인터넷 주소(IP)를 전송 중에 볼 수 있지만 저장하지 않도록 만들어졌습니다. 모인 숫자는 누구나 볼 수 있습니다. 언제든 끌 수 있고, 끄면 바로 멈춥니다.
- 끄면 다음 보고부터 즉시 멈춘다. 이미 보낸 것은 카운터에 섞여 있어 개별적으로 지울 대상이 없다는 사실도 화면에 적는다.
- 같은 문구를 영어로도 준비한다(앱은 한·영).

### 2.2 필드 (전부 버킷이거나 공개 목록의 값)

| 필드 | 값 | 이유·버킷 규칙 |
|---|---|---|
| `v` | 1 | 형식 버전. 모르는 버전은 집계 노드가 버린다 |
| `kind` | `daily` \| `event` | 하루 한 번의 생존 보고 / 실패 종류가 처음 나타났을 때의 보고 |
| `day` | `2026-10-12` (UTC 날짜) | 정확한 시각은 넣지 않는다. 받는 노드도 날짜 창 단위로만 센다 |
| `app` | 공개 릴리스 버전 문자열(예 `1.4.2`) 또는 `custom` | ReleaseLog 매니페스트에 있는 버전만 그대로. 개발 빌드는 `custom` |
| `release` | ReleaseLog 항목 번호 또는 `null` | **바이너리 해시 대신.** 앱 실행 파일·`aether`·`aether-agent`의 SHA-256이 그 항목 매니페스트와 모두 같을 때만 번호를 넣는다. 다르면 `null`(= "공개 빌드와 다른 바이너리"). 해시 원문은 보내지 않는다 |
| `protocol` | 노드가 실행하는 프로토콜 번호, 체인이 예약한 최신 번호 | `aether_status`의 `node_protocol`, `newest_scheduled` |
| `prover_program` | guest 프로그램 ID 앞 8자리 16진 또는 `custom`, 그리고 `matches_network: bool` | 공개 빌드라면 같은 버전의 모든 설치가 같은 값이라 식별력이 없다. `release`가 `null`이면 `custom`. 10-05 사고를 바로 보여 주는 필드다 |
| `role` | `wallet` / `follower` / `voting` / `prover` 중 해당하는 것들 | 역할 조합은 16가지 이하 |
| `lag` | `0` / `1-10` / `11-100` / `101-1000` / `1000+` / `unknown` 블록 | 높이는 보내지 않는다 |
| `finalized_age` | `<1m` / `1-10m` / `10-60m` / `>1h` / `unknown` | 이 기기가 본 마지막 확정 블록이 얼마나 오래됐나 |
| `os` | `macos-14` / `macos-15` / `macos-26` / `ios-26` … | 메이저 버전만 |
| `failures` | 실패 종류(§2.4) → 지난 24시간 횟수 버킷 `1` / `2-5` / `6+` | 없는 종류는 생략 |
| `anchor` | 현재 에포크 시작 블록 해시 앞 8바이트 | 재사용·사전 계산 방지(§3.5). 그 시각의 모든 보고자가 같은 값을 가진다 |
| `pow` | 작업 증명 논스 | §3.5 |

**보내지 않는 것**(코드 검사로 고정, §6 시험): 주소, 잔액, 거래·블록 해시(앵커 앞 8바이트 제외), 정확한 높이, 노드 ID·iroh 키·피어 ID, IP·호스트 이름, 하드웨어 모델·RAM·디스크 크기, 시간대·로캘, 전체 바이너리 해시, 로그 문구, 오류 메시지 원문.

### 2.3 예시 (실제 보고 바이트는 이것뿐이다)

```json
{"v":1,"kind":"event","day":"2026-10-12","app":"1.4.2","release":17,
 "protocol":[3,3],"prover_program":{"id":"3f629756","matches_network":false},
 "role":["follower","prover"],"lag":"0","finalized_age":"<1m","os":"macos-15",
 "failures":{"prover_program_mismatch":"6+","proof_rejected":"6+"},
 "anchor":"9c1e02aa41f07d3b","pow":"0000a1f3"}
```

정규 인코딩 후 **512바이트 이하**. 더 크면 집계 노드가 버린다.

### 2.4 실패 종류 (닫힌 열거형)

| 값 | 의미 | 출처(이미 있는 신호) |
|---|---|---|
| `proof_rejected` | 증명이 검증에서 거절된다 | 증명기 `Status.proofs_failing` / `acceptance_failing`(최근 16건 중 수락 1/4 미만) |
| `prover_program_mismatch` | 증명기 guest ID ≠ 검증자 guest ID | `Status.program_mismatch` (또는 `paused == "program"`) |
| `disk_floor_pause` | 디스크 바닥(기본 5 GB) 아래라 참여·증명 정지 | `aether_status.resources.disk_low`, 감시 종료 코드 12(`EXIT_DISK_LOW`) |
| `disk_full` | 쓰기가 ENOSPC로 실패 | 감시가 종료 코드 4·9를 `disk_low`와 함께 봄(`supervisor.rs` `disk_wait_needed`). 노드가 마지막 I/O 오류 종류를 `aether_status`에 내보내도록 작은 추가 필요(§6 N2) |
| `follower_stuck` | 네트워크 높이는 오르는데 내 노드는 멈춤 | 종료 코드 11(`EXIT_STALLED`), 앱 `NodeWatchdog`의 60초 정지 판정 |
| `rpc_unreachable` | 노드 프로세스는 살아 있는데 로컬 RPC(`127.0.0.1:18545`)가 응답 없음, 또는 원격 읽기 노드를 하나도 못 찾음 | 앱 `NodeController`/`WalletModel` 연결 상태 |
| `crash_loop` | 10분에 3번 넘게 죽어 감시가 재시작을 멈춤 | `supervisor.rs` `next_restart` → `Next::Stop`, 앱 `NodeWatchdog.Decision.stop` |
| `upgrade_required` *(추가 제안)* | 체인이 이 바이너리보다 새 프로토콜을 활성화 | 종료 코드 3 |
| `update_unhealthy` *(추가 제안)* | 업데이트 뒤 건강 확인 창 안에 노드가 살아나지 못함 또는 `aether.prev`로 되돌림 | `UpdateTracker` `Cause.health`, 감시 층 2 롤백 |

뒤의 두 개는 G2 카나리 판정에 꼭 필요해서 더했다(§5.3). 열거형에 새 값을 더하는 것은 `v`를 올리지 않고 할 수 있다. 집계 노드는 모르는 값을 `other`로 센다.

### 2.5 설치별 ID: **두지 않는다**

- 주 단위로 바뀌는 무작위 ID를 검토했다. 장점은 같은 설치의 중복 보고를 걸러 "고유 설치 수"를 셀 수 있다는 것이다. 단점은 일주일 동안 보고들을 이어 붙일 수 있게 되고, 받는 노드가 본 IP와 합치면 쉽게 특정할 수 있는 정보가 된다는 것이다(§7.2 PIPA). 베타의 질문("새 버전이 퍼졌나, 무엇이 늘었나")에는 **하루 보고 수 ≈ 하루 활성 옵트인 설치 수**로 충분하다.
- 중복은 클라이언트 규칙으로 막는다: `daily` 하루 1건, `event`는 실패 종류별로 하루 1건. 정직하지 않은 클라이언트의 부풀리기는 §3.5에서 다룬다.
- Sparkle 단계 배포가 쓰는 로컬 그룹 번호(§5.2)는 기기 밖으로 나가지 않으며 보고에 넣지 않는다.

## 3. 전송: 아무도 통제하지 않는 쪽을 고른다

### 3.1 후보

**(a) 기존 p2p(iroh)로 아무 공개 노드에나 보내고, 아무 노드나 집계한다.** 지갑은 이미 iroh `aether/rpc/1`로 공개 팔로워 노드에서 읽는다(08, 지갑 읽기 분산). 여기에 RPC 메서드 두 개를 더한다.
- `aether_healthReport(report)` — 노드는 형식·크기·앵커·작업 증명을 확인하고, `(day, 필드 버킷)` 카운터를 올리고, 원문을 버린다. 응답은 `ok` 하나. 체인에 아무것도 쓰지 않는다(온체인 없음).
- `aether_healthSummary(day)` — 그 노드가 센 카운터를 **노드 키로 서명해** 돌려준다. 5 미만인 칸은 `"<5"`로 가린다(§7.1).
- 각 보고는 **노드 하나에만** 간다. 그래서 대시보드가 여러 노드의 요약을 더해도 이중으로 세지 않는다. 노드 사이 요약 가십은 나중 일이다(§6 단계 3).
- 합의 변경이 아니다. 노드 로컬 RPC라 **서명 앱 릴리스(경로 A)** 하나로 배포된다. 메서드를 모르는 옛 노드는 `-32601`을 돌려주고, 지갑은 다른 노드를 고른다.

**(b) 누구나 미러할 수 있는 정적 공개 버킷에 올린다.** 읽기 쪽으로는 훌륭하다(R2·GitHub·IPFS 어디든 복제 가능, 08 이력 배포와 같은 성질). 하지만 **쓰기**에는 누군가 쓰기 자격 증명을 쥔 업로드 창구가 필요하다. 그 창구가 곧 (c)다. 아니면 누구나 쓰는 버킷이 되어 스팸을 막을 수 없다. 그래서 (b)는 **보고 수단이 아니라 요약 보관 수단**으로 쓴다. 누구든 (a)의 서명된 요약을 긁어 날짜별 파일로 올리면, 서명이 있어 어느 미러에서 받아도 진위를 확인할 수 있다.

**(c) Pipln HTTPS 엔드포인트.** 가장 빠르고 단순하다. 그러나 Pipln이 모든 보고자의 IP를 받는 **개인정보처리자**가 되고(Cloudflare 로그 포함), 단일 장애점이자 단일 관문이 되며, 대시보드도 Pipln이 공개해야만 볼 수 있다. 창업자 원칙(통제·권리 없음)과 처리방침의 현재 약속에 정면으로 걸린다.

### 3.2 비교

| 기준 | (a) iroh RPC + 아무 노드 집계 | (b) 정적 공개 버킷 | (c) Pipln HTTPS |
|---|---|---|---|
| 누가 통제하나 | 아무도. 노드 운영자 각자가 자기 카운터만 가진다 | 쓰기 창구를 쥔 사람 | Pipln |
| Pipln 서버 필요 | 없음 | 쓰기 창구 필요 | 필요 |
| IP를 보는 쪽 | 보고를 받은 노드 하나(이미 읽기 요청을 받는 같은 종류의 노드) | 쓰기 창구 | Pipln·CDN |
| 누구나 읽기 | 아무 노드에 `aether_healthSummary`, 서명 확인 | 그렇다 | Pipln이 공개할 때만 |
| 스팸 저항 | 작업 증명·앵커·노드별 속도 한도·노드 간 비교 | 쓰기 창구에 달림 | 서버 쪽 한도(가장 쉬움) |
| 위조 | 집계 노드가 자기 숫자를 부풀릴 수 있음 → 노드 간 중앙값으로 걸러냄 | 창구가 위조 가능 | Pipln이 위조 가능(검증 불가) |
| 베타까지 구현 비용 | 중간(노드 RPC 2개 + 지갑 송신) | 낮음(요약 보관용) | 낮음 |
| 원칙 부합 | 부합 | 읽기만 부합 | 어긋남 |

### 3.3 선택: (a), 시점은 **베타 직후 첫 패치**

- (a)를 고른다. 이유: Pipln 없이 동작하고, Pipln이 IP를 받지 않아도 되며(Pipln 노드는 `--health-aggregate=off`로 받지 않게 둘 수 있다, §8 질문 2), 누구나 읽을 수 있고, 합의 변경 없이 앱 릴리스로 고칠 수 있다.
- **베타 주간에는 층 2 송신을 켜지 않는다.** 세 사고는 층 0·층 1로 잡힌다(§4.3 대조표). 처리방침은 지금 "사용 통계도 수집·전송하지 않는다"고 약속한다. 그 문장을 바꾸고 법률 확인(§7.2)을 받기 전에는 스위치를 화면에 내놓지 않는다. 노드의 집계 RPC는 먼저 실어 둬도 된다. 받기만 하는 것이고, 보내는 클라이언트가 없으면 카운터는 0이다.

### 3.4 송신 절차 (지갑)

1. 하루 한 번 무작위 시각에(그리고 `event`는 실패가 처음 보이고 0–30분 무작위 지연 뒤에) 보고를 만든다. 순수 함수 `HealthReport.build(state) -> bytes`이고 입력은 이미 앱이 가진 상태뿐이다.
2. **읽기용 연결과 다른, 그 보고에만 쓰는 임시 iroh 엔드포인트 키**로, 읽기에 쓰는 노드와 **다른** 공개 노드를 무작위로 골라 보낸다. 같은 연결로 보내면 노드가 "이 주소의 잔액을 읽은 쪽 = 이 실패를 보고한 쪽"으로 엮을 수 있기 때문이다.
3. 실패하면 다른 노드로 한 번 더 보내고, 그래도 안 되면 버린다(쌓아 두었다가 몰아 보내지 않는다).
4. iroh 릴레이를 거치면 릴레이 운영자도 연결 메타데이터를 본다. 지갑의 평소 읽기와 같은 노출이며, 문서에 그대로 적는다.

### 3.5 남용·스팸 저항

- **크기·형식**: 512바이트 이하, 닫힌 필드, 모르는 `v`는 버린다.
- **앵커**: `anchor`가 현재 또는 직전 에포크(3,600블록 ≈ 1시간) 시작 블록 해시여야 받는다. 미리 만들어 둔 보고를 쏟아낼 수 없다.
- **작업 증명**: `BLAKE3(anchor ‖ report ‖ pow)`의 앞 비트가 정해진 수만큼 0이어야 한다. 목표는 Apple silicon에서 약 1초다. 정직한 설치는 하루 몇 번이라 비용이 없고, 1만 건을 위조하려면 약 3시간 CPU가 든다. 난이도는 노드 로컬 값(경로 R)이라 릴리스로 조정한다.
- **노드별 속도 한도**: 연결당 10분에 1건, 노드 전체 분당 600건, 날짜당 카운터 칸 수 상한. 넘치면 버린다(기존 `aether/rpc/1` 연결 한도 위에 얹는다).
- **집계 노드의 거짓말**: 요약은 노드 키로 서명되어 누가 무엇을 주장했는지 남는다. 대시보드는 여러 노드의 요약을 노드별로 나란히 보여 주고, 합계와 함께 **노드별 비율의 중앙값**을 보여 준다. 한 노드만 "실패 90%"라고 하면 바로 튄다. 등록 노드(레지스트리에 공개된 노드 ID)의 요약과 미등록 노드의 요약을 따로 표시한다.
- **위조 보고로 노리는 것과 결과**:
  - 실패를 부풀려 카나리 승격을 막는다 → **지연만 된다**(안전한 방향). 긴급 릴리스는 카나리·단계를 거치지 않는다(§5.4).
  - "건강함"을 부풀려 나쁜 릴리스를 밀어붙인다 → 설치 권한은 여전히 빌더 2/3 + 72시간 게이트가 쥐고 있다. 단계 배포 속도만 정상으로 보일 뿐이고, 각 기기의 건강 확인과 `aether.prev` 롤백(24 층 2)은 그대로다.
  - 숫자는 **사람의 판단 재료일 뿐이고 어떤 기기의 동작도 자동으로 바꾸지 않는다**(§1 비목표).

### 3.6 누구나 읽는 대시보드

- **탐색기(`apps/explorer`, 정적·오픈소스, 앱에 번들, 누구나 호스팅)**에 "네트워크 건강" 페이지를 더한다. 같은 페이지가 앱 안(Explore 탭)에서도, 아무 정적 호스팅에서도 돈다.
- 데이터 출처 두 가지: (1) 층 0 공개 체인 지표(§4.1). 아무 RPC나 읽기 게이트웨이에서 읽는다. (2) 층 2 요약. 레지스트리·DHT로 찾은 노드 N개(기본 16개 무작위)에 `aether_healthSummary`를 묻고 서명을 확인한다.
- 화면은 숫자보다 문장이 먼저다. 예: "지난 24시간 증명 보상 0건 — 평소 하루 1,900건", "1.4.2 설치의 41%가 '증명 거절'을 보고 — 1.4.1은 0%".
- `scripts/health-snapshot.py`(누구나 실행): 요약을 긁어 날짜별 JSON으로 저장하고 원하면 정적 버킷에 올린다((b)의 보관 역할). Pipln도 하나를 돌릴 수 있지만, 다른 사람의 사본과 서명으로 대조되므로 Pipln 사본이 기준이 되지는 않는다.

## 4. 로컬 우선: 보고 없이 기기에서 먼저 잡는다

가치의 대부분은 여기서 나온다. 지갑은 자기 노드의 상태를 이미 다 안다. 할 일은 그것을 **사용자가 할 수 있는 행동 한 문장**으로 바꾸고, 놓치지 않게 알리는 것이다. 네트워크로는 아무것도 보내지 않는다.

### 4.1 층 0: 공개 체인 지표 (기기·운영 공통, 보고 없음)

체인은 이미 공개적으로 기록하고 있다. 누구나 계산할 수 있고 개인 데이터가 아니다.

| 지표 | 출처 | 경보 문턱(초안) |
|---|---|---|
| 시간당 블록에 실린 증명 수 / 지급된 증명 보상 | 블록 `Payload`의 증명, `proofs.rs`·`aether_rewardStatus` | 6시간 0건(평소 > 0일 때) |
| 확정 간격 | 블록 타임스탬프 | 중앙값의 3배 이상 1시간 지속 |
| 에포크당 비컨 응답 수(살아 있는 등록 Mac) | 블록 `Payload::beacons`(15 §비컨) | 7일 중앙값 대비 −30% |
| 실행 중 프로토콜·예약된 업그레이드 | `aether_status` `protocol`/`schedule` | 예약 후 활성화 전 7일간 표시 |
| ReleaseLog 새 항목 | `aether_releaseEntries` | 표시만 |

- **ops: `scripts/health-watch.py`** — 위 지표를 아무 공개 RPC에서 읽어 문턱을 넘으면 알린다(창업자 Mac 알림·메일 등 실행하는 사람의 선택). 공개 데이터만 읽으므로 누구나 돌릴 수 있고, Pipln이 돌린다고 통제가 생기지 않는다. **10-05 증명 사고는 이것만으로 6시간 안에 보였다.**
- 지갑도 같은 계산 일부를 쓴다(§4.2 L1의 교차 확인).

### 4.2 층 1: 기기 안 점검과 사용자 문장

공통 규칙:
- 판정은 `NodeWatchdog`·`UpdateTracker`처럼 **순수 로직 모듈 `HealthCheck`**(시계 주입, 입력은 이미 있는 상태)에 두고 표마다 단위 시험을 둔다.
- 표시는 세 곳이다. 심플 모드 홈 배너(한 문장 + 버튼 하나), 메뉴 막대, **macOS 알림(사건당 한 번)**. 같은 사건은 다시 알리지 않고, 해소되면 "해결됐어요"를 한 번 알린다. 지금 증명 실패는 메뉴 막대에 영어 빨간 글씨로만 나온다(`ProverMenu.swift`). 메뉴를 열지 않으면 보이지 않는 것이 5일의 원인 중 하나다.

## 5. G2 카나리 채널

### 5.1 원칙

- **같은 승인, 다른 시점.** 카나리 항목과 일반 항목은 같은 ReleaseLog 항목·같은 매니페스트·같은 DMG를 가리킨다. 둘 다 `ReleaseUpdateGate`가 빌더 2/3 서명, 위원회 확정 인증서와 저장 증명, 게시 후 72시간을 확인한다. **카나리라서 일찍 설치되는 바이너리는 없다**. 카나리는 72시간이 끝나는 순간 가장 먼저 제안받는 무리다.
- **새 키 없음.** appcast는 보안 경계가 아니다(19: 승인은 언제나 직접 검증). 그래서 채널과 단계 값을 appcast에 적는 것은 *배포* 작업이고 서명이 필요 없다. 이 말은 appcast를 쥔 사람(지금은 GitHub Releases, Pipln 저장소)이 **늦추거나 멈출 수는 있어도 승인되지 않은 것을 설치시킬 수는 없다**는 뜻이다. 그 비대칭이 통제를 만들지 않는 이유다.
- 미승인 테스트 빌드용 "더 이른 채널"은 만들지 않는다. 그런 빌드는 devnet에서만 돈다.

### 5.2 메커니즘 (Sparkle 2.6+, 이미 번들됨)

- **채널**: appcast 항목에 `<sparkle:channel>canary</sparkle:channel>`. 채널 표시가 있는 항목은 그 채널을 허용한 클라이언트만 본다. 앱은 `SPUUpdaterDelegate.allowedChannels(for:)`에서 설정 "새 버전 먼저 받기"가 켜져 있을 때만 `["canary"]`를 돌려준다. 이미 깔린 앱은 채널 항목을 무시하므로 배포 피드만 바꿔도 안전하다.
- **단계 배포**: 일반 항목에 `<sparkle:phasedRolloutInterval>21600</sparkle:phasedRolloutInterval>`(6시간). Sparkle은 기기마다 로컬 무작위 그룹(7개)을 정해 두고, 그룹 *g*는 `pubDate + g × 간격`부터 자동 업데이트 대상이 된다. 그룹 번호는 기기 밖으로 나가지 않는다. 사용자가 직접 "업데이트 확인"을 누르면 단계와 무관하게 받는다(Sparkle 동작). 그 경우에도 게이트는 그대로 적용된다.
- **긴급**: `<sparkle:criticalUpdate>`를 달면 단계 배포를 무시한다. 채널 표시도 없다.
- **피드 구조**: `SUFeedURL`은 `releases/latest/download/appcast.xml`이다. 그래서 최신 GitHub 릴리스의 appcast 한 파일에 **현재 일반 항목(채널 없음) + 새 카나리 항목**을 함께 적는다. 새 버전은 GitHub *prerelease*로 올려 `latest`를 바꾸지 않고, 카나리 항목의 `enclosure`가 그 prerelease의 DMG를 가리키게 한다. 승격할 때 새 버전을 `latest`로 바꾸고 단계 값이 붙은 일반 항목으로 appcast를 다시 쓴다. `scripts/release-mac.sh`가 지금은 항목 하나짜리 appcast를 쓰므로 바꿔야 한다(§6 O3).
- **미러**: 누구든 appcast·DMG를 미러할 수 있다. 다만 클라이언트 피드 URL은 Info.plist에 고정이라 미러는 사람이 받는 경로다. 장기적으로는 단계 일정을 체인 시각으로 게이트 안에서 계산해 피드 호스트의 역할마저 없애는 안을 둔다(§6 단계 3).

### 5.3 시간표 (일반 릴리스, 2/3)

T0 = ReleaseLog 게시 블록의 인증 시각.

**정지 기준** (하나라도 해당하면 승격하지 않거나, 진행 중인 단계 배포 항목을 appcast에서 내린다):
1. 팀 카나리 Mac 2대 이상에서 `crash_loop`, `update_unhealthy`, 롤백, 또는 L1–L9 중 새로 나타난 경보.
2. 층 2 요약(옵트인 카나리 설치)에서 새 버전의 어떤 실패 종류 비율이 직전 버전의 2배를 넘고, 그 버전 보고가 최소 20건 이상. 노드 간 중앙값 기준(§3.5).
3. 층 0 지표가 카나리 설치 시점 뒤로 꺾임: 시간당 증명 보상이 7일 중앙값 대비 −50%, 확정 간격 3배, 비컨 −30%.
4. 사용자가 공개 채널에 올린 "진단 정보 복사" 내용에서 같은 증상이 2건 이상.

**누가 멈추나**: 빌더 3명 중 누구든 혼자 멈출 수 있다(appcast에서 항목을 내린다). 멈추는 쪽은 안전한 방향이라 혼자서 할 수 있게 한다. 다시 여는 것도 appcast 작업이지만, 정지 사유와 해소 근거를 릴리스 노트에 남기는 것을 런북 규칙으로 한다(`docs/ops/`에 추가, §6 O4). 이미 설치된 기기는 되돌리지 않는다. 앞으로 고친다(새 릴리스). 노드는 감시 층 2가 `aether.prev`로 자동 롤백한다.

## 7. 위험 (있는 그대로)

### 7.1 개인정보

- **IP는 보인다.** 보고를 받는 노드(와 iroh 릴레이)는 전송 중에 보고자의 IP를 본다. 우리 노드 코드는 저장하지 않지만, **악의적인 노드 운영자는 코드를 고쳐 IP와 보고를 기록할 수 있다.** 그 노드가 얻는 것은 "이 IP가 이 버전을 쓰고 이 실패를 겪었다"다. 주소나 잔액은 아니다. 읽기용 연결과 다른 키·다른 노드로 보내므로 "이 IP = 이 주소"와 엮이지는 않는다. 다만 지갑이 그 노드에서 따로 읽기도 했다면 IP로 엮일 수 있다. 완화: 읽기에 쓰는 노드를 보고 대상에서 뺀다. 그래도 남는 위험은 동의 화면에 적는다.
- **작은 모집단은 버킷이 있어도 특정된다.** `custom` 빌드나 사용자가 3명뿐인 버전 + 희귀 OS 조합은 사실상 한 사람을 가리킬 수 있다. 완화: 요약에서 5 미만 칸은 `<5`로 가리고, `custom`은 버전 문자열을 버린다.
- **시간 상관.** `event` 보고가 실패 직후에 가면 그 시각 그 노드에 연결한 IP와 엮인다. 0–30분 무작위 지연으로 줄이지만 없애지는 못한다.
- **보고 원문 보관 금지가 코드 약속뿐이다.** 서드파티 노드에 강제할 방법은 없다. 그래서 "보관하지 않습니다"가 아니라 **"보관하지 않도록 만들어졌습니다"**라고 쓴다.

### 7.2 법률 (개인정보 보호법, 실제 변호사 의견 아님)

- PIPA상 개인정보는 다른 정보와 **쉽게 결합해** 알아볼 수 있는 정보까지 포함한다(제2조 제1호 나목). IP는 결합 가능성에 따라 개인정보로 다뤄질 수 있다. 설치별 ID를 두지 않고 값을 버킷으로 만든 것은 보고 자체를 **익명정보**(제58조의2, 시간·비용·기술을 합리적으로 고려해도 알아볼 수 없는 정보에는 법 적용 제외)에 가깝게 두기 위해서다. 그러나 전송 중 IP가 함께 오가는 한 "익명"이라고 단정하지 않는다.
- **Pipln이 처리자가 되는지가 핵심이다.** (a)에서 Pipln이 집계 노드를 돌리지 않으면(`--health-aggregate=off`) Pipln은 보고도 IP도 받지 않는다. Pipln 노드가 받으면 그 범위에서 처리자가 될 수 있고, 처리방침 고지·목적·보관 기간이 필요하다. (c)를 고르면 확실히 처리자다.
- **현재 처리방침과 충돌한다.** `docs/ops/privacy-policy.md` §2는 "지갑·노드 앱에는 분석 도구가 없고, 사용 통계도 수집·전송하지 않는다"고 약속한다. 층 2 스위치를 화면에 내기 **전에** 이 문장을 고치고 변경을 알려야 한다(같은 문서 §8: 수집 항목이 늘면 앱 안에도 알린다). 층 0·층 1·카나리는 이 약속과 충돌하지 않는다.
- 동의: 개인정보가 아니라는 결론이 나도 옵트인 + 실제 내용 미리 보기를 유지한다(신뢰의 문제다). 개인정보라는 결론이 나면 제15조 동의 요건(항목·목적·보관 기간·거부 권리)을 화면에 다섯 항목 모두 넣는다.
- iOS로 확장할 때 App Store 개인정보 라벨에 "진단" 수집을 표시해야 한다.

### 7.3 남용

- 위조 보고로 카나리를 멈추는 공격 → 일반 릴리스가 늦어진다. 긴급 경로는 영향이 없다. 정지 기준 1·3(팀 Mac·공개 체인)은 위조 보고로 움직이지 않으므로, 기준 2만으로 멈출 때는 사람이 다른 근거를 확인한다는 규칙을 런북에 둔다.
- 집계 노드 DoS → 작업 증명·한도·크기 상한. 그래도 넘치면 버린다. 신호가 없어도 체인과 지갑은 영향이 없다.
- 거짓 요약 → 서명으로 책임을 남기고 노드 간 중앙값으로 무력화한다.

### 7.4 원칙·운영

- appcast(GitHub Releases, Pipln 저장소)를 쥔 쪽이 롤아웃 속도를 정한다. 설치 권한은 없지만 **늦출 힘**은 있다. 단계 3의 체인 시각 일정과 철회 항목이 이 힘을 줄이는 방향이다.
- 알림 피로: 사건당 한 번, 해소 한 번으로 묶고, 같은 사건 재알림 금지를 시험으로 고정한다.
- 카나리에 실제 사용자가 거의 없으면 정지 기준 2는 표본이 모자란다. 그래서 팀 Mac 링(기준 1)과 공개 체인(기준 3)이 1차 방어선이다.

## 8. 창업자 결정이 필요한 것

1. **베타 주간에는 층 2 송신을 켜지 않는다**(층 0·1과 카나리 링만)는 순서에 동의하는가.
2. **Pipln 노드가 상태 보고를 받지 않게(`--health-aggregate=off`)** 둘 것인가. 받지 않으면 Pipln은 처리자가 아니게 되지만, 초기에 공개 노드가 적으면 집계 노드가 부족할 수 있다.
3. **일반 릴리스가 약 2.5일 늦어지는 것**(72시간 → 카나리 24시간 관찰 → 36시간 단계)을 받아들이는가. 아니면 기본 관찰 0시간·단계 간격 3시간처럼 더 짧게 갈 것인가.
4. **정지는 빌더 1명이 혼자** 할 수 있다는 규칙에 동의하는가.
5. 설치별 ID는 **두지 않음**으로 확정해도 되는가. 고유 설치 수 대신 하루 보고 수로 만족할 것인가.
6. 처리방침 개정 문구와 법률 확인을 **누가 언제** 받을 것인가(D1 — 층 2 공개의 선행 조건).

### 8.1 리드 결정 (2026-10-06, 출시 결정 위임 원칙에 따라)

1. 동의한다. 베타 주간에는 층 0·1과 카나리 링만 싣고, 층 2 송신은 싣지 않는다.
2. Pipln 노드는 상태 보고를 받지 않는다(`--health-aggregate=off`가 기본이고 Pipln 노드도 같다). Pipln은 처리자가 되지 않는다. 집계 노드가 모자라면 층 2를 늦춘다. Pipln이 대신 받지는 않는다.
3. 짧게 간다. 카나리 관찰은 12시간, 단계 간격은 6시간이다. 일반 릴리스의 72시간 대기는 그대로 두고, 늘어나는 시간은 약 1일이다. 실제 운영 데이터를 본 뒤 다시 정한다.
4. 동의한다. 정지는 빌더 1명이 혼자 할 수 있다. 정지는 늦추기만 하므로 승인 권한이 생기지 않는다. 재개는 2/3가 한다.
5. 설치별 ID는 두지 않는다. 하루 보고 수로 충분하다.
6. 처리방침 개정 문구는 층 2를 구현할 때 함께 쓴다. 법률 확인은 실제 변호사 상담 묶음(G 사용자 몫 5번)에 넣는다.
