# Aether / EastSea mainnet security audit — round 1

**Target:** detached `consensus-freeze-1`, 2026-10-03. Independent, read-only source audit; no source changes. This is one of the two required rounds, not a mainnet approval. Severity follows the requested definition: **Critical** includes loss of funds or chain halt/fork; **High** is a serious conditional failure; **Medium** and **Low** are narrower. The PoCs below used only `./tmp/` and were removed after this report.

## Findings

### A1 — Critical — One Byzantine roster member can stop the honest committee after restart

**Locations:** `crates/node/src/follow.rs:918-935` (`roster_heights` trusts `aether_status.height`), `:975-1007` (maximum unproved height controls startup), `:903-907` (any answer above the margin means `Wait`), `crates/node/src/main.rs:1954-1962` (validator startup gate).

**Sequence:** In a four-member committee, one compromised member stays online while the three honest Macs restart for an update. It answers the authenticated peer connection's `aether_status` with an invented height far beyond the actual finalized height, and serves no corresponding certified blocks. Each honest Mac takes that maximum, chooses the liar for catch-up, times out or receives no certifiable block, and asks again. The liar keeps answering, so `heard` is reset on every census; the five-minute fail-open applies only when *no* peer answers. All three honest Macs remain before voting, while the liar alone cannot finalize. The chain is halted without a threshold-key compromise. The same attack works against a single returning validator and can reduce a live committee below quorum.

**Evidence:** Read the caller and loop; ran `cargo test -p aether-node when_a_member_may_start_voting --lib --offline` (1 passed). Its existing assertion at `follow.rs:1122-1123` explicitly expects `[98, 500]` to remain `Wait` after the patience window. I did not run a live four-node malicious-peer simulation.

**Smallest safe fix:** Use only a *verified finalization certificate and block height* as evidence that a peer is ahead. After a bounded failed fetch from a claimant, quarantine that claim and re-evaluate the gate against certified heights; never let a continuously answering but unproved height reset the fail-open clock. Keep the vote journal's existing restart gate.

### A2 — Critical — Unchecked genesis epoch arithmetic can make every validator panic while `mainnet-rules` passes

**Locations:** `crates/node/src/roster.rs:175-205` (no bound or checked product for `epoch_blocks` / `draw_epochs`), `crates/node/src/chain.rs:2886-2889` (`current_draw` divides by their unchecked product), `:949` (`resume` calls it), `crates/node/src/main.rs:1999` (every network-file validator resumes), `crates/node/src/mainnet.rs:29-116` (checklist accepts the configuration).

**Sequence:** Create a new-genesis network with otherwise valid mainnet flags, `epoch_blocks = 9223372036854775808` and `draw_epochs = 2`. Both fields fit their `u64` parser. `mainnet-rules` reports every check `ok`. On validator startup, `chain.resume()` calls `current_draw`; the product exceeds `u64`. A debug build panics on multiplication. The release profile has no overflow checks configured, so the product wraps to zero and the following division panics. Every validator given this genesis crashes on launch; the chain cannot start. This does not change testnet 7780 unless such a new genesis is selected.

**Evidence:** A standalone Rust PoC under `./tmp/audit-cap` constructed the same `ChainConfig`: `mainnet::check` returned `all_checks=true`, and `chain.resume()` panicked at `chain.rs:2889` in the debug build. Release behavior follows the wrapping product and division by zero; I did not compile the full release profile.

**Smallest safe fix:** Validate nonzero, operationally bounded epoch parameters and `epoch_blocks.checked_mul(draw_epochs)` when parsing the genesis. Use checked arithmetic at all draw computations; have `mainnet-rules` refuse out-of-range parameters before launch.

### A3 — Critical — An untrusted RPC can change an extension token's units before the user signs

**Locations:** `apps/extension/src/background.js:299-305` (ERC-20 metadata read through unverified `eth_call`), `apps/extension/src/lib/tokens.js:96-115` (`decimals` accepted from that answer), `apps/extension/ui/popup.js:260-276` (display and signed `transfer` amount use it), `apps/extension/src/background.js:423-435` (send path checks only an equally unverified token balance), `apps/extension/src/lib/rpc.js:118-123` (only AETH account methods enter the WASM proof path).

**Sequence:** A malicious selected RPC answers `decimals()` as 9 for a genuine six-decimal token the wallet already holds. A real balance of 1,000 tokens is `1,000,000,000` base units and appears as **1 token** in the popup. The user selects Max or types 1 and confirms a one-token send. `parseTokenAmount` creates `transfer(recipient, 1,000,000,000)`, which the actual token contract executes as **1,000 tokens**. The RPC can also return success for the unverified `sendCheck` simulation at `background.js:410-420`. The attacker need not forge a finality certificate or obtain the browser key; the AETH proof path does not cover the token metadata used to construct this calldata. A known token with sufficient real balance and a cooperating recipient are the attack preconditions.

**Evidence:** Ran a Node PoC using the repository's `tokenInfo` and `parseTokenAmount` with a mocked `decimals()` response: `reportedDecimals=9`, `displayedAmount=1`, `signedTransferUnits=1000000000`, `actualAmountAtSixDecimals=1000`. `node --test apps/extension/test/tokens.test.mjs` passed 9/9. The PoC did not send a transaction on a live chain.

**Smallest safe fix:** Verify `decimals`, token identity and balance against one certified state root (for example code/storage proofs or a locally re-executed certified read) before using them to format or sign a transfer. Until that is available, do not let remotely supplied decimals determine signed base units; require a trusted, pinned denomination for the selected token and show the exact base-unit amount at confirmation.

### A4 — High — “Seven days” of upgrade notice is only a block count

**Locations:** `crates/node/src/upgrade.rs:29` (`604_800` blocks), `crates/node/src/chain.rs:2063-2088` (activation compares heights only), `crates/node/src/application.rs:103-109` (one local proposer's pacing), `:178-187` (other validators accept an equal parent timestamp), `crates/node/src/main.rs:164-165` (proposal pacing is a local CLI flag).

**Sequence:** A quorum signs an ordinary upgrade for the earliest permitted activation height. A validator using a modified proposer, or operators starting with a shorter `--block-time-ms`, produce blocks with intervals below one second. Honest validators vote for equal or short-interval timestamps because verification checks only `timestamp >= parent.timestamp` and waits only when the timestamp is ahead of the local clock. The chain reaches the activation height before seven wall-clock days without the unanimous emergency approvals. Unattended Macs counting on the advertised release window can meet the new protocol before their update is installed and stop validating. This is a failure of the notice guarantee, not a claim that one member can sign an upgrade.

**Evidence:** Source review and `cargo test -p aether-node --test activation new_genesis_requires_seven_days_except_unanimous_emergencies --offline` (1 passed). That test checks the height boundary, not elapsed time. No fast-block network PoC was run.

**Smallest safe fix:** For new-genesis rules, make the one-second inter-block timestamp floor a consensus rule independent of the proposer CLI flag. Add a committee-signed absolute `not_before` time which each honest signer checks as at least seven days away; require the activation block's timestamp to reach it, with the existing future-time wait preventing early finalization. Keep the 7780 timestamp rule unchanged.

### A5 — High — `mainnet-rules` certifies “16-seat growth” with a four-seat genesis cap

**Locations:** `crates/node/src/mainnet.rs:58-62` (the named check tests only protocol version), `crates/node/src/roster.rs:175-182` (four is an accepted genesis ceiling), `crates/node/src/rotation.rs:174-185` (the ceiling actually controls draws), `crates/node/src/main.rs:954-963` (the checklist's pass/fail gate).

**Sequence:** Generate a protocol-3, history-v2, rewards-enabled root genesis with `--max-committee 4`, then follow the documented `aether mainnet-rules` launch gate. It prints `ok  16-seat growth` and exits successfully, although the consensus committee can never grow beyond four. If this was an accidental flag or a carried config error, the mainnet's promised expansion and fault margin cannot be repaired without a new genesis. Four seats also make the A1 restart attack particularly direct.

**Evidence:** A standalone Rust PoC under `./tmp/audit-cap` set `max_committee=4` on otherwise passing mainnet flags. Output: `actual_cap=4 default_cap=16 16-seat_check=true all_checks=true`; `mainnet::missing` said “every mainnet rule is on.” This did not run a full DKG/rehearsal.

**Smallest safe fix:** Make this specific mainnet checklist check `cfg.max_committee == GROW_UNTIL` and the state word equals it, or rename it to report the actual configured ceiling and add an explicit launch requirement for 16. Add a negative checklist test for `max_committee=4`.

## Areas checked without another confirmed finding

- **Certificates, state proofs, chain rules:** Traced `aether_light::verify_finalized_chain`, group namespace and digest binding, account/storage/history proof checks, `Chain::execute_as` canonical payload, protocol activation, and emergency all-member signatures. This was targeted code review, not an independent audit of Commonware BLS or revm internals. No single-key certificate forgery or emergency-approval bypass was established.
- **Rewards and registrations:** Read issuance and capped operator shares, beacon/re-attestation accounting, registry-v3 status words, registrar signature checks, the fee-free registration lane and its per-block/per-epoch caps. No additional reproducible issuance or free-lane bypass was established; long-horizon economics and every registry transition remain for round 2.
- **Mac release gate:** Traced ReleaseLog storage proofs and code-hash pin, two-of-three pinned builder signatures (three for emergency), the signed DMG hash, the 72-hour certified-timestamp gate, and Sparkle's independent EdDSA archive check. I found no route for one builder key or a changed download alone to install a malicious Mac app. This is a source-level conclusion; the real signing/notarization and Sparkle runtime were not exercised.
- **Snapshot/recovery:** Traced next-block certificate anchoring, state/history/meta roots, code-byte closure, download and disk bounds, store move-aside, and the vote-journal marker. I found no path in these inspected checks for one malicious snapshot to install a different state root or for store reset to move the vote journal. A live resource-exhaustion test was not performed.
- **Agent/session policy and genesis ceremonies:** Read the on-chain session caps, recipient checks, nonce, expiry and agent owner-signing path. Checked `network -> dkg -> run`, `carry_genesis`, `keep_genesis`, reshare and `mainnet-rehearsal.sh` for a repeat of the already-fixed protocol-field drop. No further hand-built network-file omission was established. The two confirmed launch-check defects above remain.

## Verification limits and Not reviewed

The focused Rust startup and activation tests passed. The extension token tests passed 9/9. An attempted full `node --test apps/extension/test/*.test.mjs` run passed 52 of 54 tests; the other two could not start because the generated `apps/extension/wasm/aether_wasm.js` artifact is absent in this checkout. This is a missing build artifact, not a sandbox denial or a discovered test failure. The temporary Cargo target was removed after testing.

**Not reviewed:** Commonware's internal simplex/BLS/DKG proofs; a full multi-node Byzantine simulation; complete `revm` and state-tree implementations; every rewards branch and long-term supply simulation; full Foundry contract fuzzing; live Secure Enclave, Apple notarization, Sparkle and Chrome Web Store update behavior; 1 GB snapshot memory pressure on an 8 GB Mac; real network DKG/reshare/mainnet rehearsal; generated WASM and full browser end-to-end tests. Round 2 should prioritize those plus regression tests for A1–A5 after fixes.

## Overall judgement

I would **not** allow this genesis to mainnet unfixed. A1 gives one committee member a practical post-restart chain-halt path; A2 lets an accepted genesis configuration crash all validators while the launch gate is green; A3 can turn an apparently small browser-token payment into a much larger signed transfer. A4 breaks the promised seven-day update window, and A5 makes the launch gate certify a committee property the genesis does not have. Resolve and re-test all five before the second audit round; the Mac app's inspected release gate did not show a one-builder update bypass.
