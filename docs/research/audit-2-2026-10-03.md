# Aether / EastSea mainnet security audit — round 2

**Target:** detached `consensus-freeze-2` (`1329611d04d9b612b793515bef5351662c8d83eb`), 2026-10-03. I inspected the requested areas independently before reading round 1, then reviewed `git diff consensus-freeze-1 consensus-freeze-2` and attacked its five fixes. Source was not changed. PoCs and build products were confined to `./tmp/`. **This is not a clean second round.** Severity uses the launch definition: Critical includes loss of funds or chain halt/fork; High is a serious conditional failure.

## Findings

### R2-1 — Critical — Reshare participants agree on the identity while holding incompatible threshold keys

**Locations:** `crates/node/src/dkg.rs:304-325` (a player fixes its output from the logs it has), `:328-342` (agreement compares only the group identity), `:445-460` (after the dealing window, a quorum of logs and a quorum of matching identity announcements suffice), `crates/node/src/main.rs:1375-1399` (each Mac stages its own output), `crates/node/src/handoff.rs:94-105` (the old committee can sign one staged output).

**Sequence:** During a four-player reshare, delay one dealer's signed log to one new validator past the quorum-log deadline while the other three receive it. The three finish with one public polynomial; the fourth finishes from a different valid quorum of dealer logs. Resharing preserves the *constant* group identity, so all four `Done` messages carry the same identity and `agreement(true)` accepts both results. Three old signers can approve the majority output as the handoff. After the switch, the fourth validator's partial signature does not verify under that committed output. If the dealer who caused the split stops voting, only two valid shares remain, short of the three-of-four quorum: the chain halts despite only one Byzantine validator at that point. A two-to-two split instead prevents a common handoff and can keep the old committee from rotating. Delayed log delivery is the additional precondition; the PoC did not simulate the complete live handoff.

**CONFIRMED:** An isolated Rust test in `./tmp/dkgprobe/tests/dkgprobe.rs` drove the repository's `Ceremony` with selective delivery of authenticated `Msg::Log` messages. Both two-to-two and three-to-one splits returned success. Every participant reported `agreement(true) == Some(true)` and the same `identity`, but the public `output` strings differed. In the three-to-one case, `handoff::check_seed_partial` rejected the minority share against the majority polynomial. The normal DKG integration test covers loss and an entirely offline dealer, but not different valid dealer subsets finishing in one round.

**Smallest safe fix:** Bind `Done` and the final agreement to a digest of the complete public DKG output and the exact accepted dealer set, not just its constant identity. A participant with a different digest must refuse to stage or sign a handoff. Test the three-to-one delayed-log schedule and a post-switch partial-signature quorum.

### R2-2 — Critical — Two attacker-controlled RPC URLs still poison a token's first pin and signed units

**Locations:** `apps/extension/src/lib/rpc.js:145-165` (counts matching URL responses as independent sources), `apps/extension/src/lib/tokenPin.js:39-59` (accepts two matching answers), `:71-78` (first answer becomes the pin), `apps/extension/src/background.js:312-320` (first-use path), `:463-482` (signed calldata uses the pin). A lone configured endpoint is also accepted at `background.js:313-317`.

**Sequence:** The attacker controls both configured RPC endpoints (or the only configured endpoint) for a real six-decimal token. On first discovery, both reply `decimals() = 9` and matching name/symbol while the real contract has six decimals. `callAgreed` returns `sources = 2`; the extension stores the false denomination without a change warning. The user sees a balance of 1 and sends “1” to an attacker-controlled recipient. The extension signs `transfer(recipient, 1,000,000,000)` base units, which the real contract executes as 1,000 tokens. A correct or rate-limited second endpoint causes the first sighting to remain unconfirmed, but two URLs under one operator provide no state authenticity. Reconfirmation never runs because there is no prior pin to disagree with.

**CONFIRMED:** `./tmp/token_poison.mjs` called the shipped `pinnedTokenInfo`, `foldObserved`, and `parseTokenAmount` with two identical malicious answers: `sources=2`, `outcome=pinned`, `pinnedDecimals=9`, `signedUnits=1000000000`, `actualAtSixDecimals=1000`. The 28 focused extension RPC, token and pin tests passed; those tests do not assert independent endpoint ownership or certified metadata.

**Smallest safe fix:** Derive transfer units from metadata verified against a certified state root or a trusted, immutable denomination for the exact token address. Until that exists, first-use RPC agreement must not authorize a denomination-dependent send; show exact base units and require an explicit trusted denomination. Distinct URLs are not a security quorum.

### R2-3 — High — The 15-rule launch gate accepts a disabled registrar and unsafe candidate timing

**Locations:** `crates/node/src/roster.rs:167-182` (checks registrar length but not whether the P-256 point is valid), `crates/execution/src/registry.rs:43-52` (stores the key and all three timing fields), `crates/node/src/mainnet.rs:67-89` (bounds epoch/draw length and checks only `registrar.is_some()`), `crates/node/src/rotation.rs:58-65` (the warm-up parameter controls eligibility).

**Sequence:** Publish an otherwise normal new-genesis configuration with registrar `00…00` (64 bytes), `min_streak = 0`, and `draw_epochs = 1`. The zero point cannot verify a registrar attestation, so new Macs cannot register through either paid or free registration. The launch gate nonetheless prints `ok` for re-attestation and growth. Alternatively, with a real registrar, the zero warm-up and hourly draws accelerate seat entry relative to the published day-long policy; the stability rule requires only three recent up epochs. This is a ceremony/configuration attack or fatal launch mistake, not a remotely mutable field after genesis. The prior A5 cap check now catches `max_committee=4`, but its named growth/re-attestation checks still do not prove the network can register or meet its advertised timing.

**CONFIRMED:** `./tmp/dkgprobe/tests/launchcheck.rs` built that `ChainConfig` and asserted `mainnet::check` returned 15/15 `ok` (`all_checks=true; registrar=zero; min_streak=0; draw_epochs=1`). The inability of a zero P-256 point to verify a valid attestation follows from the verification path; I did not run a complete DeviceCheck ceremony with this genesis.

**Smallest safe fix:** Validate the registrar as a nonzero, on-curve P-256 public key at network-file parsing and in the launch check. Have `mainnet-rules` check the exact intended `epoch_blocks`, `min_streak`, and `draw_epochs` values, or explicitly report and require review of deviations rather than marking the advertised mainnet policy `ok`.

### R2-4 — High — A snapshot request can force multi-gigabyte synchronous work on a validator

**Locations:** `crates/node/src/rpc.rs:58-70` (a request rebuilds the cached snapshot every 121 finalized blocks), `:77-85` (RPC handler on the node), `:401-415` (snapshot methods), `crates/node/src/snapshot.rs:42-65` (copies all state entries while holding `chain.lock()`, then serializes full-size buffers), `crates/node/src/follow.rs:279-296` (client collects every chunk before a second full buffer and decode), `crates/node/src/snapshot.rs:90-92` (checking clones decoded entries).

**Sequence:** On an 8 GB validator near the allowed 1 GB encoded snapshot size, an RPC caller asks for `aether_snapshot` after the cache ages by 120 blocks. The synchronous path copies the full finalized state under the consensus chain mutex, allocates the encoded postcard buffer, and copies it into the new-genesis envelope before replacing the cache. A peer can repeat this every 121 blocks. A joining Mac additionally holds collected chunks, an assembled buffer, decoded entries, and a cloned tree input during verification. These live allocations are multiple times the advertised 1 GB limit, beside the existing state and OS/app footprint. A slow allocation pauses finalization; memory pressure can kill an unattended node. The server path is more acute because an external request chooses when it runs.

**READ-ONLY, not memory-confirmed:** I traced buffer lifetimes and the lock scope. I did not run a 1 GB snapshot on a physical 8 GB Mac, so the precise peak RSS and whether the OS kills this process remain unproven. The 1 GB bound is a wire-size limit, not a memory budget.

**Smallest safe fix:** Build and serve snapshots from a bounded, streamed file outside the consensus chain mutex; cache by file/height, rate-limit rebuilds, and refuse builds that exceed measured free headroom. Download to disk, authenticate the file hash, then decode without keeping all chunks plus a second full copy resident. Verify the peak on an 8 GB Mac before launch.

### R2-5 — Medium — The extension can sign different token units than its open confirmation showed

**Locations:** `apps/extension/ui/popup.js:270-305` (captures `pin`, parses amount and displays units), `apps/extension/src/background.js:463-480` (reads the current pin and reparses amount only after the final click), `:501-516` (another Assets view can replace the pin), `:309-345` (asset refresh writes the whole pin object without a version check).

**Sequence:** A Send popup builds its confirmation from a six-decimal pin and successfully dry-runs `transfer(..., 1,000,000)` for “1”. Before its Confirm click, another extension Assets view reviews a reported metadata change and accepts nine decimals; the shared pin becomes nine. The original Send popup stays open with its six-decimal display, but its `send` call transmits amount text only and the background reparses it under nine decimals to `1,000,000,000` units. A concurrent asset scan can also overwrite a just-accepted pin or change flag because both paths read, await network work, and write the entire object. This requires overlapping extension UI actions; a web page cannot call `confirmTokenChange` directly because `background.js:576-581` restricts UI messages.

**READ-ONLY:** The two different parses and unversioned storage writes are directly visible. I did not drive two live Chrome windows through this timing. The R2-2 PoC independently confirms the 1-versus-1,000 unit conversion.

**Smallest safe fix:** Bind the confirmation to a pin generation and exact token calldata/base-unit amount; at final send reject if the saved pin generation or change flag differs. Serialize or compare-and-swap pin updates from refresh and confirmation.

### R2-6 — High — Free zero-balance transactions can fill the mempool and exclude paying senders

**Locations:** `crates/node/src/chain.rs:23-37` (50,000 global entries, 64 per sender, 10-minute TTL), `:2297-2337` (the full-pool rejection precedes fee or sender admission and has no paid-tx eviction), `:2716-2730` (a tx below the new base fee remains until TTL), `crates/node/src/rpc.rs:560-567` (every accepted signed tx enters that pool), `crates/execution/src/fees.rs:57-69` (base fee is zero at or below target gas).

**Sequence:** While base fees are zero, an attacker makes hundreds of fresh P-256 accounts with zero balance and signs zero-value, zero-tip, zero-max-fee calls. Each costs the attacker no coin, passes the balance check, and occupies a global mempool slot. Once 50,000 are present, the node rejects a funded sender's higher-fee transaction *before* considering its fee or sender. The 64-per-sender bound only changes how many keys the attacker needs. Even when congestion raises the base fee above the spam's cap, `keep_in_pool` retains those transactions until their 10-minute TTL, so the occupied capacity does not immediately clear. The attack must be repeated against enough validators to prevent the wallet finding a clean one; admission to a single targeted validator is confirmed, sustained network-wide starvation is not.

**CONFIRMED:** `./tmp/dkgprobe/tests/mempool.rs` used the repository's `sign_call_with` to construct 50,000 signed zero-balance transactions from 782 keys and admitted all of them to a fee-enabled `Chain` at base fee zero. A stateless check passed on a representative spam transaction and on the funded paying transaction. `add_to_mempool` then returned `Err("mempool full")` for the paying one. The PoC did not run a live network or measure attacker throughput against continuously finalizing blocks.

**Smallest safe fix:** Reserve admission capacity for transactions with a positive effective fee, or evict the lowest-fee pending transaction when a higher-fee valid one arrives; preserve nonce chains and inclusion-list obligations. Apply an explicit bounded quota to zero-fee entries across identities (not only per sender), and test paying admission while the free lane is saturated.

## Other requested areas and verification

- **Commonware boundary and Byzantine simulation:** The repo uses marshal's `Inline` application adapter and `DurableVote` before notarization (`engine.rs:46-49`, `voting.rs:61-97`), with separate vote-journal and finalized-state recovery checks (`engine.rs:254-290`, `:421-460`). `cargo test -p aether-node --test sim -- --nocapture` passed 13 active four-validator scenarios and ignored one soak scenario: equivocation, loss/partition, withheld proposer, slow/stalled disks, skew, restart and handoff. The DKG boundary is R2-1. The simulation did not inject an invalid-but-parseable proposal; application unit tests covered malformed timestamp rejection, and `Chain::execute` rejects bad payload, root, gas, protocol and group before a true vote. I did not review Commonware internals.
- **Genesis, registry and rotation:** I checked `NetworkFile::carry_genesis`/`keep_genesis` field-by-field against `Genesis` and `ChainConfig`; the existing roster carry tests passed. I traced v3 leaving/back status, the last-four-up/six-drop stability word, hour profiles, bounded early replacement, operator seat caps, reserve seating and group/committee ceilings. I found no second independent path for one announced departure to shrink a four-seat quorum below its signed handoff requirement; R2-3 covers the unchecked launch parameters. The Secure Enclave helper path validates its public point and each returned signature (`registrar_signer.rs:107-155`), but its socket tests could not run here.
- **Execution, proof market, free registration and zero tip:** `chain.rs:2994-3029` caps proofs at two and verifies each claim before payout; `registrations.rs:67-76` caps fee-free items at four per block and calls `registry::register_system`, whose shared epoch count caps all registration routes at 16. `chain.rs:2297-2337` caps mempool count/bytes and 64 pending per sender; `fees.rs:57-69` raises base fees after above-target gas. A zero-balance spammer can fill the initially free half-target capacity with many keys, but repeated full blocks raise a fee it cannot pay; the inclusion-list tests kept an older paying sender's nonce chain ahead of 2,000 unrelated nonce-zero txs. I found no demonstrated over-mint or free-registration cap bypass. R2-6 is a confirmed paying-admission failure under a full free-tx pool; I reviewed repository integration, not revm internals or a live hostile mempool.
- **Ten-year rewards:** A Python model under `./tmp/reward_sim.py` used the repository's integer daily decay, 3,600-block epochs, half split, floor, 1/16 share denominator and randomized churn across 87,600 epochs. Every simulated node and proof payout remained at or below its epoch pool (`max_over_wei=0`); unallocated shares and division dust remained unminted. This models formulas, not all state transitions or proof-claim timing.
- **Contracts and agent policy:** The installed Forge 0.2.0 rejects the literal `--fuzz-runs` flag. With `FOUNDRY_FUZZ_RUNS=5000`, the existing `contracts/` suite passed all 90 tests. An isolated `./tmp/forge-audit` copy added a native `AtomicSwap` claim/refund conservation property, which passed 5,000 generated cases. I read the HTLC status-before-transfer and exact ERC-20 balance-delta checks, the AllowanceAccount/P256Fallback recovery/session guards, and `AetherAccount` on-chain payee, cap, nonce and expiry enforcement behind `apps/agent`; no additional reproducible fund-loss path was found. Fuzz coverage was not built for every contract; the existing suite has no parameterized fuzz tests for most of them.
- **Mac update trust chain:** `scripts/release-approve.py:203-224` requires two distinct pinned builder signatures (three emergency); `ReleaseUpdateGate.swift:125-197` binds their manifest, the on-chain ReleaseLog proof/code hash, Sparkle signature and downloaded archive hash. A single compromised builder or GitHub account alone did not yield an inspected path to install malicious bytes; GitHub can withhold or corrupt assets and delay an update. The three release-approval Python tests passed. `InstallLocation`'s pure Swift test passed. Store schema's `TooNew` forward-reader and interrupted-migration tests passed inside the broader node run. I read `Clock.swift`'s uptime clock and `UpdateTracker.swift`'s persisted retry transitions, but did not exercise a real Sparkle cycle. The update-state Swift test could not verify persistence here: Foundation `.atomic` writes under `./tmp/` returned `NSPOSIXErrorDomain Code=1 Operation not permitted` in this sandbox; a non-atomic write to the same directory worked.
- **Test limits in this sandbox:** `cargo test -p aether-node --lib --offline` ran 144 tests: 134 passed, 2 ignored, 8 failed. Seven failed at `TcpListener::bind("127.0.0.1:0")` or `UnixListener::bind(.../signer.sock)` with `Operation not permitted` (`devicecheck.rs:419`, `registrar_signer.rs:208`). The eighth expected a Darwin page-pressure sysctl that this host did not expose (`resources.rs:707`). These are environment failures, not evidence that the associated production paths work. The isolated DKG and launch-check PoCs, simulation, Foundry and extension tests did run.

## Mainnet judgement

**I would not let this genesis go to mainnet.** R2-1 is a confirmed reshare agreement failure capable of leaving a committee with incompatible shares, and R2-2 is a confirmed first-use token-denomination poisoning path that can turn a displayed one-token payment into 1,000 real tokens. R2-3 means the launch gate can certify a genesis whose registrar cannot register anyone or whose candidate timing differs materially from the announced policy. R2-6 permits cost-free mempool saturation that rejects paying transactions. Resolve those, measure the snapshot path on the minimum Mac, and restart the required two-clean-round sequence because this round contains Critical and High findings.
