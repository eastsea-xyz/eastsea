# Aether / EastSea security audit — round 3

**Target:** detached `consensus-freeze-3` (`e4ba0348d0ec2cacf83bb4053f032adfd44453c9`), 2026-10-04 KST. This is **not a clean round** and does not start the required two-clean-round sequence. I made no source-code changes. I inspected the round-3 diff and the relevant surrounding paths before reading the round-1 and round-2 reports. The probes and copied Foundry project were confined to `./tmp/`.

Severity here follows the launch rule: **Critical** means a plausible loss of funds, chain halt/fork, or malicious update; **High** means a serious conditional failure. “CONFIRMED” means I ran repository code for the stated part of the sequence; any unrun network or physical-device step is called out.

## Findings

### A3-1 — Critical — Three matching DKG outputs can be staged before the fourth player reveals a different one

**Locations:** `crates/node/src/dkg.rs:365-376` accepts a late quorum of announcements; `:480-496` finishes from a quorum of logs and returns five seconds after quorum agreement; `crates/node/src/main.rs:1382-1407` stages the reshare and `:2619-2635` writes genesis keys. The new digest at `dkg.rs:340-350` correctly binds a *received* public output and dealer set, but does not make an unannounced player's output known.

**Sequence:** In a four-player round, delay dealer 1's signed log to honest player 4. Players 1–3 finish with four logs and announce the same digest; player 4 has a valid three-log quorum and finishes with a different output. At `dealing + 20 s`, players 1–3 have three matching `Done` messages; `agreement(true)` returns `Some(true)` without player 4. If player 4's completion/announcement is more than five seconds later, those three write their key files. Player 4 subsequently reports a different digest and fails its ceremony. During a reshare the old committee may sign the staged majority output into a handoff. The fourth new member has no matching staged share. If the one faulty dealer in the majority then stops voting, only two usable shares remain for a three-of-four threshold and the chain halts. At genesis the same scheduling can start with only three usable shares and no remaining fault tolerance.

**CONFIRMED:** `tmp/probe/src/main.rs` drove the actual `Ceremony` with four participants and a withheld signed log, first at genesis and then in a reshare. It printed `reshare_3_of_4_before_minority_done=Some(true) outputs_differ=true_identity_same=true`. The shipped split-output tests pass only after they deliver *all* `Done` messages (`crates/node/tests/dkg.rs:367-373`). I did not run the five-second live timer, stage a real handoff, or start four physical validators; the timing and staging follow the cited call sites.

**Smallest safe fix:** Do not stage a quorum output until a canonical dealer transcript/output has been agreed and every admitted player can use or recover the matching share. Bind that decision to the handoff, and test a fourth announcement arriving after the current five-second return window followed by one majority player going offline. Merely increasing the grace timer leaves the same scheduling attack.

### A3-2 — Critical — One Byzantine player can abort every DKG attempt with an arbitrary `Done`

**Locations:** `crates/node/src/dkg.rs:277-280` accepts any byte vector from a roster player as its announcement; `:372-374` treats *one* mismatching vector as fatal even when an honest matching quorum exists; `:490-491` exits on that mismatch. The genesis CLI exits without writing a key at `crates/node/src/main.rs:2639-2642`.

**Sequence:** Four genesis validators reach the same real output. The faulty fourth sends `Done(00…00)` to an honest peer just before its agreement tick. That peer returns `Disagreement`, and the CLI stops. The faulty player repeats this on every fresh attempt. The code tolerates a fully offline fourth player after the late quorum timer, but an online fourth can prevent genesis indefinitely; the same behavior blocks automatic reshare. This also remains the original identity-only agreement on chain 7780 (`main.rs:1336-1339`, `:2605-2608`), where the round-2 incompatible-share attack still applies to that chain.

**CONFIRMED:** The four-player `Ceremony` probe delivered `Msg::Done(vec![0; 32])` from player 4 after three matching honest announcements; `agreement(true)` changed from `Some(true)` to `Some(false)`. The `run` error/CLI exit was checked by reading; no malicious TCP ceremony was run.

**Smallest safe fix:** Make agreement tolerate up to the configured Byzantine fault count: validate announcement shape, collect a quorum for one canonical transcript, and isolate a disagreeing player without letting that one message abort honest progress. This must be paired with A3-1's share-availability rule; simply ignoring a fourth digest and staging immediately is unsafe.

### A3-3 — High — A rejected fee-bumped transaction evicts paying mempool entries for free

**Locations:** `crates/node/src/chain.rs:2366-2375` calls `evict_for` before deciding whether the new transaction fits; `:2788-2808` selects only each sender's highest nonce; `:2809-2828` removes candidates as it walks them, then can return `false` with no rollback. This is new R2-6 code.

**Sequence:** Fill the 64 MiB byte budget with funded, signed high-fee calldata transactions in several 64-nonce sender chains. Give each chain a small zero-fee final nonce. Submit a signed 126 kB transaction paying more than those tips but less than the large earlier transactions. The eight small tips are its only eligible victims, and together free too few bytes. `evict_for` removes all eight, returns `false`, and the RPC rejects the new transaction. The attacker pays no on-chain fee for that rejected submission and can repeat after arranging new eligible tips. Unlisted honest transactions disappear before they can age into an inclusion list, even though no higher-fee replacement entered the pool; already held list entries are spared. A spammer can first use the free lane's byte capacity to create the same pressure; the new count quota does not reserve bytes.

**CONFIRMED:** `tmp/probe/src/main.rs` generated valid P-256-signed envelopes, checked `validate_stateless`, and called the actual `Chain::add_to_mempool`. It printed `mempool_bytes_before=67099501 free=9363 ... answer=Err("mempool byte budget full") entries_before=539 entries_after=531`. This was a local policy test, not a sustained multi-validator gossip attack. All 16 shipped `chain::pool_tests` pass; none asserts that a failed admission leaves the pool unchanged.

**Smallest safe fix:** Compute the complete evictable set and required count/bytes first. If it cannot fit the newcomer, return without changing any pool map or counter. Add a regression assertion for count, bytes, arrivals, sender counts, and inclusion obligations after failed admission.

### A3-4 — Critical when native token sends are enabled — the Mac/iOS wallet still signs RPC-defined token units

**Locations:** `apps/wallet/Sources/TokenAssets.swift:148-153` accepts one unverified `eth_call` result for `decimals`; `apps/wallet/Sources/WalletModel.swift:492-506` stores and displays it; `apps/wallet/Sources/SimpleDashboard.swift:1172-1176`, `:1291-1294`, and `:1323-1344` construct the send from those units without an exact-base-unit acknowledgement; `apps/wallet/Sources/WalletModel.swift:751-770` reparses that metadata into signed ERC-20 calldata. The Assets header at `AssetsSheet.swift:45` says the node answer is unverified, but the Send sheet does not impose the extension's protection.

**Sequence:** A malicious selected RPC reports `decimals() = 9` for a genuine six-decimal token and a real balance of `1,000,000,000` base units. The Mac shows a balance of **1**. The owner enters “1,” sees no base-unit warning, and approves with Touch ID. The wallet signs `transfer(recipient, 1,000,000,000)`, which the real token transfers as **1,000** units of the six-decimal denomination. The dry-run goes to the same untrusted node and cannot authenticate the unit choice. The iOS target includes the same source tree.

**CONFIRMED:** A pure Swift probe compiled against the shipped `TokenScanner`, `TokenAmount`, and `ERC20` functions with a mocked RPC response printed `reported_decimals=9 displayed_balance=1 signed_units=1000000000 actual_six_decimal_tokens=1000 calldata_units=1000000000`; the pure `token-send` test also passed. I did not authorize a real Secure Enclave transaction. **Launch scope:** the currently bundled `apps/wallet/Resources/token-sources.json` contains only chain 7780, so this exact frozen bundle does not discover mainnet ERC-20s on a new chain. It becomes an immediate funds-loss path if mainnet token sources are added or native token sending is otherwise enabled without this fix.

**Smallest safe fix:** Apply the extension's address-pinned trusted denominations to Mac/iOS; for every other token, prominently show and require acknowledgement of the exact base-unit integer. Freeze token address, recipient, units, and metadata generation before the asynchronous dry-run and sign only that frozen intent. Keep native token sending disabled on a new chain until this ships.

### A3-5 — High, not memory-confirmed — snapshot consumers decode up to 1 GiB before authentication without a memory guard

**Locations:** `crates/node/src/follow.rs:254-266` accepts a peer-advertised snapshot as large as 1 GiB and checks only disk space (`:219-235`); `:280-298` assembles it in memory and deserializes it; `:310-316` obtains the next certified block *after* decoding and calls `Snapshot::check`; `crates/node/src/snapshot.rs:110-130` decodes and then clones entries to rebuild the state. The new server-side headroom gate at `crates/node/src/rpc.rs:119-128` does not apply to a peer's answer.

**Sequence:** A malicious upstream advertises a near-1 GiB snapshot and supplies matching chunks and its own BLAKE3 hash. A joining or recovering 8 GiB Mac retains the assembled byte vector and decoded entry/code collections before it asks for the next certificate. If the attacker supplies a real next certified block with the expected parent hash, `check` also clones entries and builds a tree before its root comparison rejects the fake state. The attack needs no forged finality certificate; the resource work precedes the authenticity decision. A legitimately large snapshot may also be refused persistently by an 8 GiB serving node's `available/4` budget, forcing era replay instead of checkpoint sync.

**READ-ONLY for the 1 GiB failure:** I traced these lifetimes and ran the shipped 100,000-entry server allocation probe: 6,400,348 wire bytes, 42,377,216 estimated extra bytes, 9,715,776 sampled footprint delta. The single-flight/rate-limit RPC test passed too. These support the server changes at small scale, not the follower's peak or an OS kill at 1 GiB. The new bounded eight-chunk download and off-mutex single worker are real improvements; no stale-handle state mismatch was found because the source captures one finalized `Arc` and summary under the same lock.

**Smallest safe fix:** Apply a measured inbound memory budget before accepting the manifest, stream chunks to a bounded workspace file, and authenticate the file before allocating decoded entries. Bound decode/build peak separately on the minimum supported Mac; make checkpoint refusal visibly fall back to verified era replay.

### A3-6 — Critical if GitHub ZIP installation is supported — the released extension ZIP is outside release approval

**Locations:** `scripts/release-mac.sh:89-105` publishes `aether-extension-*.zip` as a GitHub release asset; `scripts/release-approve.py:130-145` signs the DMG and three app executables but no extension ZIP; `:244-265` finalization checks the DMG, app inventory, appcast, and builder signatures, not the ZIP.

**Sequence:** One compromised GitHub release account replaces the published extension ZIP while leaving the approved DMG and appcast intact. A user who obtains and loads the extension from that GitHub asset runs attacker-controlled wallet JavaScript; its next unlock/sign interaction can move funds. This is a **manual ZIP distribution** risk, not an observed bypass of Sparkle, the Mac on-chain release gate, or a Chrome/Edge store's signed automatic updates. A single compromised builder signing key or GitHub account alone did not yield a Mac auto-install bypass in the inspected code.

**READ-ONLY:** I compared the publish asset list with the manifest/finalize checks. I did not download a release, sideload an extension, or exercise store updates. The three `scripts.tests.test_release_approve` tests passed.

**Smallest safe fix:** Include the extension ZIP's exact hash in the builder-approved release manifest and verify it again at publication and before any supported manual installation. If the ZIP is not a supported user install path, remove it from user-facing release assets.

## Mainnet judgement

**I would not let this genesis go to mainnet now.** A3-1 can stage only three compatible shares before a delayed fourth reveals a split; with one of those three faulty, the new committee can halt. A3-2 lets one Byzantine player block genesis or reshare indefinitely. A3-3 makes rejected transactions evict legitimate mempool entries. A3-5 leaves minimum-Mac snapshot recovery exposed to a large unauthenticated decode, pending physical measurement. Before enabling mainnet ERC-20 sends, A3-4 must be fixed or that feature must remain disabled; A3-6 requires a signed ZIP or an explicit end to GitHub ZIP installation support. This round contains Critical and High findings, so the required two consecutive clean rounds have **not begun**.
