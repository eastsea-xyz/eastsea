# Aether / EastSea security audit — round 4

**Target:** detached `consensus-freeze-4` (`b87fafdb899983675bede6126b2054fb740bf4a0`), 2026-10-04. I inspected the freeze-4 changes and surrounding call paths before reading rounds 1–3. No source code was changed. I used no other agents. **This round is not clean:** a certified DKG output can disclose a committee share, and the new ceremony's deadline conflicts with the shipped supervisor timeout. It does not start the two-consecutive-clean-round count. “CONFIRMED” refers to the stated executed probe; downstream network/fork steps that I did not run are identified separately.

## Findings

### A4-1 — Critical — A certified DKG output can contain a publicly reconstructible validator share

**Locations:** `crates/node/src/dkg.rs:636-639` accepts a publicly valid output without checking `output.revealed()`; `:654-660` makes it vote-eligible; `:697-730` finalizes it; `crates/node/src/main.rs:2665-2685` loads the output's polynomial for consensus without checking its revealed set. Commonware's `Output::revealed()` contract is in `commonware-cryptography-2026.9.0/src/bls12381/dkg/feldman_desmedt.rs:601-609`: these players' shares can be reconstructed from selected dealer reveals. Its V1 reveal threshold is computed at `:781-793`; threshold certificates are recovered from quorum partials and verified as a group signature in `commonware-cryptography-2026.9.0/src/bls12381/certificate/threshold/mod.rs:340-390`.

**Sequence:** In a four-player genesis or reshare, one player misses the 30-second private-dealing/ack window (an unattended Mac briefly sleeps or loses its link). Three dealers publish signed logs with that player's private evaluations revealed instead of acknowledgements. A three-dealer quorum remains valid. Two selected reveals already meet Commonware V1's reveal threshold for this four-dealer configuration, so the selected output marks that player's threshold share `revealed`. The new agreement certifies the exact signed-log bundle and all returning players can finalize it; neither certification nor staging rejects the disclosure. The Byzantine committee member receives the broadcast logs and can reconstruct that player's BLS share in addition to its own. The threshold is three of four: a single honest partial signature now suffices to assemble a group certificate. Commonware's threshold certificate verifier checks the recovered group signature, not the secrecy history of its contributing shares. This removes the one-fault safety margin and permits a conflicting certificate/fork when honest validators sign different proposals.

**CONFIRMED:** A temporary test under `./tmp/dkg_audit` drove the repository's actual `Ceremony`, transcript vote, and `finish_decided` paths with three active members and the fourth absent. It printed `certified_output_players=4 selected_dealers=3 publicly_recoverable_player4=true threshold=3`; the test passed. The Commonware source explicitly defines `revealed` as reconstructible from selected logs. I did **not** reconstruct the scalar in the probe or run a forged-cert/fork simulation; that final exploitation step is source-level reasoning. The shipped offline-player DKG tests check usable online shares but never inspect `revealed`.

**Smallest safe fix:** Reject a candidate before voting, finalizing, staging, or accepting a handoff if `output.revealed()` contains any seated player. Start a new ceremony ID with fresh DKG randomness after the missing player returns, or replace the seat before handoff; retrying the same journal/seed does not undo a published reveal. Add a four-player delayed-ack test that asserts no revealed-share output can become a committee key. Simply relaying the existing bundle longer cannot restore secrecy after a reveal is published.

### A4-2 — High — One silent new player prevents every default automatic reshare from staging

**Locations:** `crates/node/src/dkg.rs:930-932` computes a four-player strict deadline of **316 seconds** (`30 + 4 × (8 << 4) × 0.5 + 30`); `:988-999` permits an earlier return only after **all** players announce the certified result; `crates/node/src/main.rs:347-349` defaults `--reshare-timeout` to **300 seconds**; `crates/node/src/supervisor.rs:459-465,475-485` starts the child once per rotation epoch and kills it after that timeout.

**Sequence:** A four-seat rotation includes one offline or Byzantine new player that never sends its `Done`. Three honest players can obtain a decision and usable shares, but `all_players_finished_certified()` stays false. Their DKG children deliberately keep relaying the decision until after 316 seconds. At 300 seconds each default `aether run` supervisor kills its child, before it can return and write a staged threshold file. The running committee cannot sign a handoff to the proposed set. A silent seat can therefore suppress replacement rotations indefinitely; the old committee may still make blocks while its remaining quorum is healthy, but unattended replacement cannot restore its fault margin.

**CONFIRMED:** I evaluated the exact shipped constants and ran `aether run --help`, which reports `--reshare-timeout ... [default: 300]`; the computed earliest non-unanimous return is **greater than 316 seconds**. The 14 DKG integration tests passed, including a quorum with an unreachable new player, but their in-memory driver has no supervisor or wall-clock deadline. I could not run the five-minute live ceremony because this sandbox denies both TCP and Unix socket bind (`errno=1, Operation not permitted`).

**Smallest safe fix:** Derive the supervisor deadline from the same `timeouts.dealing + longest_view × players + relay` bound as the child and add a return margin, rather than using a fixed 300 seconds. The DKG must still retain a recoverable certified transcript after its relay task exits; the timeout change alone does not fix A4-1 or late share recovery.

### A4-3 — Critical, operator action required — The advertised vote-journal override can sign again above its recovery floor

**Locations:** `crates/node/src/engine.rs:205-234` accepts `AETHER_RECOVER_CONSENSUS=<finalized-view>@<last-finalized-height>` without establishing the highest previously signed view; `:277-279` bypasses the restart journal gate for recovery; `:425-428` selects a fresh `-consensus-r<view>` journal; `:536-538` starts simplex from that stored finalization. The error at `:449-451` names the environment variable as the operator-led override. `docs/ops/consensus-recovery.md` instructs operators to use that new partition after a stalled view.

**Sequence:** Validator A has durably signed a vote in view `v` above its last stored finalization `F`; the vote was broadcast, but its old journal then becomes unreadable. The safe normal path refuses to vote. If an operator follows the advertised override with `F` and no prior `-rF` partition, `recover` checks only that `F` is the last finalization. It neither imports nor proves the absence of A's votes in `(F, v]`. Simplex restarts under the same committee share in a new partition from `F` and can sign a conflicting value at `v`. A Byzantine member that retained the first vote can use A's two votes with different honest voters to form incompatible quorums. This is **not** a remote-only attack and ordinary SIGKILL does not set the override; it is an unsafe manual recovery path for an unattended chain.

**READ-ONLY:** I traced the fresh partition and `Floor::Finalized` construction and Commonware's sync-before-broadcast vote barrier. I did not execute a corrupted-journal/two-certificate PoC. The source establishes that the override discards evidence of votes above `F`; whether a particular incident has a conflicting prior vote depends on its journal and network history.

**Smallest safe fix:** Do not reuse the same committee share from a fresh journal below any view it may already have signed. Require a trustworthy authenticated maximum-voted-view record and start strictly above it, or quarantine this signer until a fresh committee round. The last **finalized** view alone is insufficient evidence.

## Other checks and reliability judgement

- **Vote-journal SIGKILL:** Commonware's metadata store keeps alternating `left`/`right` checksummed copies (`commonware-storage-2026.9.0/src/metadata/storage.rs:90-124,173-226`). A checksum mismatch on one copy is a warning; startup normalizes that copy from the valid one. The voter syncs journal appends before broadcasting votes (`commonware-consensus-2026.9.0/src/simplex/actors/voter/actor.rs:279-304,885-905`). Under the store's stated sync ordering, SIGKILL during one write should leave the other copy usable, so the reported single mismatch followed by a successful rerun does **not** establish permanent loss of voting or a forgotten published vote. If both copies fail, voting must stay off; a remote party cannot directly issue SIGKILL, although load can make an external kill more likely. I did not reproduce the heavy-load kill. A4-3 applies only if someone invokes the override after an untrusted journal.
- **Consensus and execution:** Thirteen active deterministic `sim.rs` Byzantine/restart tests passed (one soak ignored), covering partitions, isolation, conflicting votes, inclusion-list splits, skew, slow disks, and handoff. Execution unit tests passed. I read `execution/src/tx.rs:151-188` (chain/group signature binding), `execution/src/block.rs:195-310` (revm fee/prove reserve and settlement), and `execution/src/world.rs:267-337` (touched account/code/storage commits). Zero-tip acceptance is confined to a zero base fee and the fee-free lane's caps; I found no zero-tip mint or state-root fork in these paths. The custom DKG probe above extended the fault coverage under `./tmp/`; a live socket simulation was blocked by the sandbox.
- **Rewards and supply:** A 20-year deterministic integer model of the published 3,600-block epochs, daily fixed-point issuance, randomized operator weights, and per-operator node/proof caps covered **175,200 epochs**. Upper issuance was `193070928926224542635590400` wei; model node mint was `36197680588754034923327401` wei and proof mint `15435597651544820974538087` wei; both pool-overrun counters were zero. All 39 reward unit tests passed. I also traced `rewards/src/lib.rs:185-227,313-366,432-470`. This models formulas/caps, not every live registry and proof transition or every block's EVM state.
- **Contracts:** `FOUNDRY_FUZZ_RUNS=5000 forge test --root contracts --offline` passed all **90** shipped tests; the shipped suite contains no fuzz/invariant functions. Three temporary fuzz properties under `./tmp/forge-audit` each passed **5,000** generated cases (15,000 total): native swap claim/refund conservation and ReleaseLog's exact hashes after a second publication. The first local fuzz draft accidentally consumed `vm.prank` with a SHA-256 precompile call; I fixed that temporary test and reran it green. Contract source was not edited.
- **Mac update trust:** Read `ReleaseUpdateGate.swift:20-35,113-167`, `ReleaseApproval.swift:73-116`, `scripts/release-approve.py:127-145,244-265`, and the release asset list. One compromised builder lacks the required second signature (third for emergency); one compromised GitHub account cannot substitute a DMG accepted by the pinned on-chain hash, builder signatures, and Sparkle EdDSA check. Three release-approval tests passed. This is a source-level result, not a live notarization/Sparkle or browser-store test.
- **Actual genesis gate:** I ran the strict `aether mainnet-rules --network apps/wallet/Resources/network.json` against the only shipped wallet network file. It exited **1**, with 12 `FAIL` lines, as expected for chain **7780** testnet. The CLI actually calls `NetworkFile::genesis()` and `mainnet::check_with(..., rehearsal=false)` (`main.rs:960-970`). No proposed final mainnet `network.json` exists in this worktree; therefore **the required strict check on the actual proposed genesis has not passed**. A rehearsal or a test fixture cannot substitute for that file.

## Mainnet judgement

**I would not let this genesis go to mainnet now.** A4-1 is a Critical threshold-share disclosure in an otherwise certified DKG output; A4-2 blocks default automatic reshare when one new player is silent; A4-3 leaves the advertised corrupted-journal override capable of forgetting votes above its floor. The finite DKG transcript relay also leaves a late player without a guaranteed path to a usable share. Fix and re-audit those boundaries, then run the strict `mainnet-rules` command on the actual final production `network.json` and repeat the required clean-round sequence. This round has Critical and High findings, so it is **not** the first clean round.
