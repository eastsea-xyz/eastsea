# Aether / EastSea security audit — round 5

**Target:** detached `consensus-freeze-5` (`5a99e94da6654ed3fe01614b544855c1856dc3d1`), 2026-10-04. I inspected the freeze-4→freeze-5 changes and their call paths before reading audits 1–4. No source code was changed and no other agent was used. This round is **not clean** and does not start the required two-consecutive-clean-round count. “CONFIRMED” names the executed part of a finding; a downstream fork, disk exhaustion, or timed handoff is identified separately when it was inferred rather than run.

## Findings

### A5-1 — Critical — Free, permanent state writes can exhaust every validator's disk

**Locations:** `contracts/src/EastSeaNames.sol:90-103,111-125` (unbonded commitments are stored and only a successful reveal deletes them); `crates/execution/src/fees.rs:57-69` (both base fees stay zero when blocks remain below half target; no state fee); `crates/node/src/chain.rs:2387-2424` (the free-lane cap is only for *pending* transactions). `crates/execution/src/block.rs:265-276` permits a zero-balance, zero-value call when both base fees and fee caps are zero.

**Sequence:** An attacker generates distinct commitments and sends zero-tip `commit` calls from several fresh addresses. They pace execution below the 15-million-gas half target of a 30-million-gas block and proving below its half target, so `next_excess` and both base fees stay zero. Each commitment expires for registration after 24 hours but its storage word is never deleted. The mempool's 64-pending-per-sender and free-lane limits do not constrain cumulative finalized state; five senders can rotate 300 small pending calls through each block. At the measured **40,555 gas per call**, 300 calls use 12.17 million gas per block and add 25.92 million permanent entries per 86,400-block day: **at least 829 MB/day of raw 32-byte values**, before state-tree and redb overhead, for no token expenditure. Continued below-target traffic eventually fills finite consumer-Mac disks and stops finalization. This is a chain-wide zero-fee state-growth defect; the names contract is a ready-made path, and an attacker could deploy another storage-writing contract if only this one were changed.

**CONFIRMED component PoC:** My temporary Foundry property ran 5,000 seeds, measured 40,555 gas for a fresh `commit`, read the mapping slot after `MAX_COMMIT_AGE + 1`, and found it still occupied with `totalBurned == 0`. The execution and rewards tests passed. The sustained live-chain fill and physical disk impact were **not** run because this sandbox denies loopback bind. The below-target fee calculation and lack of a persistent-state quota follow directly from the cited code.

**Smallest safe fix:** Charge for persistent EVM state growth even while execution/proving base fees are zero, with the state charge included in transaction affordability and consensus execution. Bond or charge name commitments too, but a names-only fix does not close the arbitrary-contract path. Test many consecutive below-target blocks and assert their net storage growth cannot be free.

### A5-2 — Critical — The finite post-stage relay can certify a committee with an unusable seat

**Locations:** `crates/node/src/dkg.rs:50-55,943-1000` (five-second grace and only 60 seconds of journal-backed relay); `crates/node/src/main.rs:1451-1473` (reshare child returns after that relay); `crates/node/src/supervisor.rs:536-568,570-576` (old validators sign once the child exits, while a late joining Mac merely refuses its own install); `crates/node/src/handoff.rs:262-309` (handoff signature checks the output and old signers, with no proof that every new seat holds a share).

**Sequence:** In a four-to-five reshare, the new fifth player receives and durably records its private dealings, then sleeps before learning the certified decision. Four players, one of them Byzantine, certify the bundle and stage. After their five-second grace and 60-second relay, their children exit and the old committee signs a handoff to **five** seats. The fifth wakes after the relay ended; it cannot fetch the certificate and exact signed bundle, so it cannot finalize or stage its share. Its supervisor correctly refuses to install, but the handoff still counts it. Four usable shares meet the five-seat quorum of four only while all four cooperate. The Byzantine holder now stops: three usable honest shares cannot finalize, so the chain halts. A departing old-only dealer serving the same bounded relay does not change the expiry of this recovery path.

**READ-ONLY downstream timing:** The 16 DKG integration tests passed, including `four_of_five_stage_while_a_silent_player_recovers_from_relay` and `departing_dealer_serves_the_decided_bundle_to_a_late_candidate`. Those tests deliver relay messages within eight in-memory ticks; none advances past the 60-second expiry and then signs a handoff. I verified the exact return/sign/install conditions in source. A live timed handoff was blocked by TCP bind `errno=1`.

**Smallest safe fix:** Before the old committee signs, require an authenticated, output-bound proof that each *seated* new player finalized a usable partial share. If one fails that bounded readiness check, do not install it: propose a roster without that seat and rerun a fresh DKG round. A local `check_joining_share` after a handoff cannot protect the other signers from certifying a missing seat.

### A5-3 — High — Anyone can reset a name commitment just before its reveal

**Locations:** `contracts/src/EastSeaNames.sol:99-103,108-116`.

**Sequence:** Alice posts `C = keccak256(name, owner, salt)` and waits the required 60 seconds. When her reveal enters the public mempool, Mallory reads its arguments, computes `C`, and places a higher-priority `commit(C)` before the reveal. The mapping timestamp is replaced with the current block time regardless of sender. Alice's registration reverts `CommitTooNew`; Mallory pays no name fee. Repeating this before each reveal can prevent a target name from being registered indefinitely, even though Mallory cannot register it using Alice's salt.

**CONFIRMED:** My temporary Foundry test committed as Alice, warped exactly 60 seconds, recommitted the same hash as a different account, observed `CommitTooNew`, then observed success 60 seconds after the attacker stopped. It passed alongside 15,000 generated property cases. A live mempool ordering attack was not run.

**Smallest safe fix:** Store commitment age by committer as well as hash and require the reveal's payer or a predesignated relayer to be that committer. Keep registration-for-another-owner by retaining `owner` inside the commitment; an unrelated sender must not refresh someone else's timestamp.

### A5-4 — High — The strict genesis gate accepts an unusable output and the rehearsal chain ID

**Locations:** `scripts/mainnet-genesis.sh:108-113,132-137,284-305` (final output/identity only need nonempty strings, `--chain-id` is optional and otherwise any positive ID passes); `crates/node/src/mainnet.rs:29-43` and `crates/node/src/main.rs:964-973` (the 17 rules rebuild genesis without validating the DKG output); `crates/node/src/main.rs:777-781` (a node command actually decodes that output).

**Sequence:** The coordinator runs the real `assemble` path with four distinct validator public entries, three reserve public entries, a real P-256 registrar public key, and the published policy. After DKG, a copy/paste error or modified `network.json` supplies `identity: "aa"` and `output: "bb"`. The advertised strict final check is green, even though the output cannot decode and does not establish a usable committee. Validator startup (`main.rs:1208-1227,2746-2770`) uses its local threshold file and does not compare those public strings, so it can vote while wallets reject the file or cannot verify its finality; other node commands that decode `network.output` fail. The same `check` command accepts chain ID **7799**, which `assemble` reserves for rehearsal, when the rest of the file has strict policy values. The 7799 allowance is not reported as a rehearsal in this path. An unattended launch can therefore follow a green gate into a network or wallet trust file that cannot support the intended committee.

**CONFIRMED:** I ran `mainnet-genesis.sh assemble` using fresh public entries under `./tmp/`, then inserted the two invalid nonempty fields. `aether mainnet-rules --network` printed **17 `ok`** and exited 0; `mainnet-genesis.sh check ... --chain-id 7801` printed **CHECK PASS 16/16**. `aether upgrade-combine --network` on the same file exited 1 with `output: EndOfBuffer`. Changing only its ID to 7799 still gave **CHECK PASS 16/16** in strict mode. I did not claim this is a successful real DKG output.

**Smallest safe fix:** Make the final gate decode the exact output, compare its players to the genesis roster and its group public key to `identity`, reject revealed seated shares, and require a new nonreserved chain ID equal to a separately recorded ceremony ID. Make each validator compare its local `threshold.json` with the checked final file before voting.

### A5-5 — High — A cross-volume wallet migration can run two copies of one validator identity

**Locations:** `apps/wallet/Sources/DataMigration.swift:37-44` (failed move falls back to recursive copy without checking a running old node); `crates/node/src/supervisor.rs:973-992` (one-instance lock is only `<data>/run.lock`); `apps/wallet/Sources/NodeController.swift:187-190,268-315` (the new bundle starts `aether run` against the copied path).

**Sequence:** A consumer has relocated one of the old/new Application Support trees to another volume, or a destination symlink points there. The old `Aether.app` node is running and holds the old directory's `run.lock`. First launch of `EastSea.app` cannot rename across volumes, so `moveOrCopyTree` copies `validator.key`, `threshold.json`, the vote journal, and `run.lock` while the old signer is live. Copying makes a **new lock inode**; the new `aether run` takes it while the old one still owns its original lock. The copied journal may also predate the old process's latest vote. Both processes can now use the same validator identity from different data directories and sign in one view without a shared journal. An additional Byzantine signer can exploit that second equivocating identity to break the intended one-fault safety bound.

**CONFIRMED component PoC, not a live fork:** Under `./tmp/` I locked `old-run.lock`, copied it, and simultaneously acquired an exclusive flock on `new-run.lock`; inode numbers differed. The fallback copy and per-directory lock are directly visible in source. I could not create a cross-volume mount or run two networked nodes in this sandbox.

**Smallest safe fix:** Enforce an OS-wide exclusive lock keyed by validator public key across both bundle/data paths, and defer migration while the old signer holds it. After the old signer exits, copy and verify its journal and keys before permitting the new node to start; never treat a copied `run.lock` as signer exclusion.

### A5-6 — Medium — An attempt-window edge assigns different honest nodes different DKG rounds

**Locations:** `crates/node/src/supervisor.rs:118-149,490-525,643-711` (attempt is current height divided by a fixed block window and is passed as the DKG round); `crates/node/src/chain.rs:3085-3103` (proposals are kept only in their originating attempt window).

**Sequence:** With the initial four validators and three reserve keys, the bound is eight players, giving a 653-second supervisor timeout and a **713-block** attempt window. Two honest supervisors see a proposal at height 712 and start round `old+1`; three other proposed players see it at height 713 and start round `old+2`. All are online, yet neither group can reach the four-of-five new-player agreement quorum because messages from the other round have different context. The first ceremony fails. Retries can eventually align as height advances, but a slow chain stretches the wait for a new attempt, and a node that starts after a dealer's 30-second window cannot obtain a safe acknowledged bundle for that attempt.

**CONFIRMED arithmetic, READ-ONLY network result:** I evaluated the shipped timeout/window constants (heights 712 and 713 map to attempts 0 and 1); the supervisor's boundary unit test passed. I did not run a five-node edge schedule because local socket bind is denied. This is a liveness delay, not a demonstrated permanent fork.

**Smallest safe fix:** Start a ceremony only within a bounded admission interval at the beginning of a shared attempt window; late observers wait for the next round. Better, commit an attempt ID/start height in the finalized proposal and have all supervisors cancel an old attempt before joining the next one.

### A5-7 — Medium — First-launch migration records success before moving either identity

**Locations:** `apps/wallet/Sources/DataMigration.swift:14-32,37-53`; `apps/wallet/Sources/EnclaveKey.swift:36-41,58-80`; `apps/wallet/Sources/NodeController.swift:187-190,268-290`.

**Sequence:** On the first EastSea launch, a full disk, temporary access denial, or failed copy stops the old enclave handle or node tree from reaching its new path. `ensure()` already wrote `renameMigrationDone=true` and the helpers swallow the errors. Later launches never retry. `EnclaveKey.loadOrCreate` sees no handle at the new path and can create a new Secure Enclave account, hiding the user's old address and funds in the app until manual recovery; the node can create a different validator identity and leave its old seat unserved. The old handle and key files normally remain, so this is loss of automatic access, not proof that secret material was destroyed or exported.

**READ-ONLY:** The ordering and error swallowing are direct source facts. The pure Swift migration test compiled but its first atomic file write under `./tmp/` failed with `NSCocoaErrorDomain 513` / `EPERM` in this sandbox, so I do not claim a completed runtime migration test.

**Smallest safe fix:** Mark migration done only after each required identity and journal copy/move is verified durable. Return a failure that prevents a new wallet or validator key from being created while an old identity exists, and retry idempotently on the next launch.

### A5-8 — Medium, existing-address compatibility — The vault factory's CREATE2 addresses changed with the rename

**Location:** `contracts/src/EastSeaVault.sol:343-362` (`predict` hashes `type(EastSeaVault).creationCode`, including compiler metadata).

**Sequence:** A client pre-funds a counterfactual vault address predicted from the old `AetherVault` creation code, then the renamed factory artifact is deployed at the same factory address or used to recompute its expected address. The child creation code's metadata changed with the filename/contract rename, so the new factory predicts and deploys to a different address for the same owner keys, limits, delay, and salt. Funds pre-funded at the old empty address cannot be reached by that new deployment path. This does not affect a fresh mainnet with no preannounced vault addresses.

**CONFIRMED:** I compiled freeze-4 and freeze-5 with the same solc 0.8.19 settings. After stripping each runtime's trailing metadata, 14 of 16 old contract artifacts matched byte-for-byte and all old selectors matched; `EastSeaVaultFactory` and `MerkleDistributorFactory` retained 32/31 changed bytes of *embedded child metadata* in their runtimes. With one key `(1,1)`, threshold 1, limit 0, delay 600, salt 0 and the same hypothetical factory `0x11…11`, the old and new CREATE2 predictions were respectively `0x39eb0e75e5a4261abd2333977ed4375ee8d69aee` and `0xd63f962832f9592853806388a403e16ff4de98f5`. The vault's ordinary storage slots 0–8, the account's ERC-7201 slot, signature domain constants, and function selectors did not change.

**Smallest safe fix:** Preserve the exact old child initcode for any already announced or pre-funded CREATE2 addresses, or migrate those addresses explicitly before switching clients to the renamed factory. Publish the new factory code hash and predicted addresses as a deliberate compatibility break on a fresh chain.

## Not reviewed

A physical multi-Mac DKG/handoff with a late player beyond 60 seconds, a five-node attempt-edge schedule, sustained state growth to disk-full, actual Secure Enclave migration/signing, notarized Sparkle transition from the old bundle ID, browser-store updates, and a 20-year execution replay were not run. This sandbox denied `bind(('127.0.0.1', 0))` with **`PermissionError: [Errno 1] Operation not permitted`**, so the full `mainnet-genesis.sh --dry-run` DKG and live p2p PoCs could not run. The broad node library suite had **166 passes, 8 failures, 4 ignored**: seven failures attempted forbidden local sockets in DeviceCheck/registrar-helper tests, and one machine-pressure query returned no accepted value in this sandbox. The focused integration suites above passed. The pure Swift migration executable reached its first `./tmp/` atomic write and macOS returned `NSCocoaErrorDomain 513` / `EPERM`; token-icon, token-guard and release-approval pure Swift tests did run. Commonware's complete cryptographic proof, every revm opcode, a production mainnet network file and the real release signing environment remain outside this round's execution evidence.

**Mainnet judgement:** I would **not** let this genesis go to mainnet now. A5-1 permits economically free, permanent state growth until unattended validator disks fail; A5-2 can finalize a committee one Byzantine withdrawal away from a halt; A5-3 lets an unrelated account censor name registrations; A5-4 makes the advertised strict launch gate green for a malformed or rehearsal-ID file; and A5-5 can duplicate a live signing identity on cross-volume migration. The production final `network.json` and its strict check are still absent. Fix these Critical/High paths and independently audit the resulting freeze; round 5 is not the first clean round.
