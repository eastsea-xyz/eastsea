# Aether / EastSea independent security audit — round 6

**Target:** detached `consensus-freeze-6`, commit `a66d37b3955dbe8e15cfcf8939097f913f3c8dfa`; audited in this worktree on 2026-10-05 KST. I inspected `git diff consensus-freeze-5 consensus-freeze-6` and the relevant call paths before reading audits 1–5. I changed no source code and used no other agent. This round is **not clean**: the new state price still permits two sustained zero-fee disk-growth attacks. It does not start the required two consecutive clean rounds. “CONFIRMED” covers only what I ran; downstream disk exhaustion, a live consensus split, and a cross-volume dual signer are not claimed as executed.

## Findings

### A6-1 — Critical — Unmetered event logs can fill validator disks at a zero fee

**Locations:** `crates/execution/src/block.rs:194-231,304-339` meters account, code and storage differences but does not meter logs; `crates/node/src/store.rs:1098-1111` persists the full receipt, including event data, in redb; `crates/execution/src/fees.rs:68-77` keeps execution and proving base fees zero when use stays below their half-block targets; `crates/node/src/prune.rs:18-28,38-65` retains recent receipts for 30 days by default. The block's 8 MiB wire cap applies to signed payloads, not the execution-produced receipt (`crates/light/src/lib.rs:45`).

**Sequence:** Pay once to deploy a small logger (after issuance makes a funded account possible). A zero-balance signer then calls it with zero tip, zero execution/proving caps and zero state budget. The logger emits 400 `LOG0` records of 4,096 zero bytes without changing contract storage. The call consumes 13,298,447 execution gas, below the 15,000,000 target, and a tiny fraction of the proving target. Its receipt carries 1,638,400 event-data bytes, but `state_gas` and `state_fee` are zero. Reuse the signer at the next nonce every block. The fee floor stays zero at this pace. That is **141,557,760,000 raw log bytes per 86,400-block day** before JSON encoding and redb overhead; a consumer Mac can run out of disk well before the 30-day receipt retention window. The one-time deployment charge does not price the ongoing attack.

**CONFIRMED:** A temporary Foundry test under `./tmp/` emitted the stated 400 records in 13,337,805 gas (including test-call overhead). A temporary Rust harness using this tree's `aether-execution::execute_block` then executed the logger for two successive new-genesis-context blocks. Each produced `success=true`, 400 logs, 1,638,400 event-data bytes, `state_gas=0`, `state_fee=0`, and sender balance 0. I did not run a disk-fill campaign or real network blocks; loopback bind is denied by this sandbox with `PermissionError [Errno 1] Operation not permitted`.

**Smallest safe fix:** Meter execution-produced persistent receipt/event bytes with a nonzero floor price and a per-block byte cap enforced by proposers and validators; make admission and replay use the same bound. Include account-history rows and any permanently retained block/era data in the storage budget or cap them separately. Keep zero-balance plain transfers possible without allowing arbitrary log generation for free.

### A6-2 — Critical — A fresh zero-balance signer still creates a free permanent state account

**Locations:** `crates/execution/src/block.rs:216-228` excludes the `bare_sender` from account growth, `crates/execution/src/world.rs:280-295,322-325` nevertheless writes its nonce-bearing account into the state tree, and `crates/node/src/chain.rs:2369-2425` limits only the pending free pool, not cumulative finalized accounts.

**Sequence:** Generate fresh P-256 keys and sign nonce-0 zero-value plain transfers at a zero execution/proving base fee. Each transaction consumes 21,000 execution gas, creates one new sender account with nonce 1, and is charged no state units. Submit at most 714 such transfers per block: 14,994,000 gas remains below the 15-million target, so the fee stays zero. This yields 61,689,600 durable account entries per 86,400-block day. Their 32-byte values alone are about 1.97 GB/day, excluding keys, tree and database overhead, receipts and history. The 100,000 state-unit and 512-slot block caps never see them. This is a chain-wide disk exhaustion route independent of contracts and the registrar.

**CONFIRMED:** My temporary executor harness included 100 distinct fresh signers in one block: all 100 succeeded, used 2,100,000 execution gas, added 100 state-tree entries, and reported `state_gas=0`. The shipped `zero_fee` test also confirmed admission and persisted nonce 1 for one such sender. The 714-per-block and daily figures are arithmetic extrapolations, not a sustained live-chain run.

**Smallest safe fix:** Charge the new sender account record, including the first transaction, or use an explicitly bounded, separately funded first-use allowance with a durable per-block and lifetime budget. A per-block cap alone delays but does not price unbounded growth. If a zero-balance first transfer remains a product requirement, it needs a protocol-level subsidy with a hard economic bound.

### A6-3 — High — `verify-local` accepts a changed chain ID after the coordinator's check

**Locations:** `scripts/mainnet-genesis.sh:364-380` reads `chain_id` from the very final file being verified, passes that value back as the strict check's expected ID, and compares only `round`, `output` and `identity` with `threshold.json`. The ceremony-ID comparison exists only in `cmd_check` at `:310-345`, not in `verify-local`.

**Sequence:** The coordinator checks a valid final `network.json` for intended chain ID 7801 and distributes it. In transit, replace only its `chain_id` with another nonreserved positive ID such as 7802. The DKG output and each Mac's local threshold file still match byte-for-byte; the output's group key and roster still decode. On every validator Mac, `verify-local` derives its expected ID as 7802 from the substituted file, so the strict rule check and local round/output/identity comparison pass. If all Macs and wallets launch from it, they permanently start the wrong chain ID despite the public ceremony record saying 7801. A one-Mac substitution causes a divergent signer or an unavailable seat.

**READ-ONLY:** The self-derived expected value and missing independent comparison are direct script facts. I did not run a real ceremony output: none is in this worktree, and the dry-run DKG requires sockets denied by this sandbox. I ran strict `aether mainnet-rules --network apps/wallet/Resources/network.json` only on the shipped 7780 file; it correctly exited 1 for the reserved testnet ID and other mainnet rules.

**Smallest safe fix:** Require the validator to provide the ceremony record (or independently pinned chain ID and genesis/roster digest) to `verify-local`, compare those values with the supplied final file, and fail if absent. Check the complete genesis configuration, not only the threshold fields.

### A6-4 — High — Validator startup can skip its share-to-network comparison or compare the wrong file

**Locations:** `crates/node/src/main.rs:687-695,1240-1259` loads the voting network from `--network`; `:2819-2834` instead checks `<data>/network.json` and silently skips the new comparison if that local file is unreadable, malformed, or carries another chain ID. `crates/node/src/supervisor.rs:1095-1099` also retains a stale local file whenever its chain ID and identity match the supplied one, even if other genesis fields or output differ.

**Sequence:** Start `aether node --network <checked-final-file> --data <dir>` with a threshold share for a different public polynomial of the same validator roster and round, while `<dir>/network.json` is absent or malformed. `committee_keys` checks the local share against its own output and the roster, but the advertised new comparison with the checked file is skipped. The process can reach its consensus signer with the wrong committee public key; peers using the checked file cannot count its votes. On the normal `aether run` path, a Mac that completed DKG from a divergent genesis file may instead retain that local network because chain ID and group identity match; the supplied, checked final file is ignored and `verify-local` does not compare genesis flags. Two unavailable four-seat validators remove the three-vote quorum. A single Mac with a different genesis can reject the other chain's blocks.

**READ-ONLY:** I traced both CLI paths, the local-file `if let` nesting, and `adopt_network`'s equality condition. I did not launch divergent validators: local TCP bind returns `PermissionError [Errno 1] Operation not permitted`, and no production ceremony file exists here.

**Smallest safe fix:** Pass the exact loaded `--network` value into `committee_keys` and fail closed on any missing or unparsable final file. On `aether run`, compare the complete immutable genesis, roster, round, output and identity with the checked final file before voting; a stale local file must be explicitly reconciled or rejected.

### A6-5 — High — A cross-volume migration leaves a second usable validator identity behind

**Locations:** `apps/wallet/Sources/DataMigration.swift:91-111,213-242,287-291` falls back to a verified copy and leaves the old node tree in place with only `MIGRATED-TO-EASTSEA`; `crates/node/src/supervisor.rs:1042-1059` locks only each data directory's `run.lock`. The new app's start gate (`DataMigration.swift:134-143`) returns once its new tree exists or migration is marked done.

**Sequence:** With old `Aether.app` stopped, a cross-volume `moveItem` fails and the migration copies the validator key, threshold share and vote journal into the EastSea tree. It deliberately leaves the old tree and a marker the old binary does not read. Start EastSea; it locks the new tree. Later start the old app; its original `run.lock` is free and it can sign with the same validator key and threshold share under an independent journal. A network with one Byzantine seat can now have a second equivocating seat, defeating the four-seat one-fault assumption. Holding the old lock during the copy prevents overlap *during* migration but not after it returns.

**READ-ONLY for the cross-volume sequence:** The retained old tree, marker, per-directory locks, and new start condition are direct source facts. I did not mount a second volume or run two live signers; the sandbox denies network sockets. The migration's pure Swift test could not complete here because Foundation's atomic file write under `./tmp/` returned an `NSError` in this sandbox. The source copy path and two lock locations are unambiguous.

**Smallest safe fix:** Make the old identity unusable to the old app before enabling the new signer, or enforce one OS-wide exclusive lock keyed by validator public key across both data roots and app versions. A marker only the new binary knows cannot exclude the old binary.

### A6-6 — Medium — A resumed migration accepts changed large database bytes as verified

**Locations:** `apps/wallet/Sources/DataMigration.swift:35-38,149-155` hashes only files at most 4 MiB; `:229-242` skips an existing destination file and approves the tree when path and size manifests match.

**Sequence:** A copy is interrupted after creating `<EastSea>/node/data.db`, or that existing destination file suffers a same-size overwrite. On the next launch, the old and destination database files both exceed 4 MiB and have equal length but different bytes. `fileMatches` says they match, `syncTreeVerified` skips the destination, and the manifest checks only size. On an unrestricted filesystem the migration can mark success while the new node starts from the wrong database; the old copy remains, but automatic recovery has lost its reliable source selection.

**CONFIRMED component:** A temporary Swift probe wrote two 4,194,305-byte files differing at byte zero and printed `same_size=true different_content=true fileMatches=true`; `syncTreeVerified` also returned true for an old/new tree containing them. The final marker write returned an `NSError` under this sandbox, so I did **not** confirm the full `done=true` transition here.

**Smallest safe fix:** Verify every copied or reused file by a streaming content hash, including large database and journal files, before marking migration done. Preserve the old tree until the destination has passed that check and a successful open.

### A6-7 — Medium — Native transfer fee display omits the mandatory new-recipient state fee

**Locations:** `crates/ffi/src/lib.rs:610-620,789-798` reports `transfer_fee_wei=0` whenever execution base fee is zero; `crates/execution/src/tx.rs:30-35` makes the wallet reserve 100 state units for a funded positive-value transfer; `crates/execution/src/block.rs:216-228,363-375` charges 100 units for a fresh recipient account and requires that reserve in addition to value.

**Sequence:** At the zero execution-fee floor, a funded user sends native coin to a fresh address. The wallet's transfer-fee line says zero, but block execution burns 0.0001 AETH for the new account. If the user attempts to send the balance shown as available, the signed transfer is rejected for insufficient funds because the 0.0001 AETH reserve was not reflected in the display. A recipient that already has an account may use none of the reserve, so this is a destination-dependent quote error.

**READ-ONLY:** The UI quote and signed budget were traced to their shared FFI source. The execution suite confirmed that a new recipient pays once, but I did not run a native GUI send.

**Smallest safe fix:** Include the possible 100-unit state charge in the displayed fee and sendable-balance calculation, labeling it as a maximum until the recipient's certified account state is known; show the actual receipt charge afterward.

## Other attack surfaces checked

- **State fee mechanics:** I traced `check_budget`, the reserved sender balance, final-diff metering, per-transaction and per-block slot caps, checked gas-vector accumulation, beneficiary credit exception, EIP-7702/delegation and selfdestruct handling, admission replay and future nonce simulation, plus the proving guest's call to the same executor. The 11 execution state-growth tests, 7 free-lane node tests and the focused proving replay test passed. I found no separate free SSTORE/code deployment, arithmetic wrap or proposer-only cap bypass. The new fee price is a consensus constant selected for new-genesis config; 7780 retains the legacy path.
- **Registration lane and system writes:** `registrations.rs:29-77` verifies operator and registrar signatures, chain-bound nonce/expiry and per-block count before state writes. `registry.rs:143-189,225-251` shares the contract's 16-per-epoch cap; the lane has four items per block and a finite 100,000-entry registry. Beacon answer writes remain bounded by the four slots and registered candidates. No independent replay or cap bypass was found. The single Pipln registrar remains an accepted, upgrade-revocable trust point.
- **DKG and Byzantine behavior:** I traced output-bound readiness index verification, authenticated relay, the 120-second readiness window and one reduced-roster retry. Thirteen active `sim.rs` tests passed, one soak test remained ignored; 18 DKG tests passed. I did not find a single forged readiness proof or a chain-7780 wire-format change. I could not validate a live delayed peer after the relay's deadline because socket bind is denied.
- **Names:** Besides the two independent Foundry properties above, I reviewed commitment age boundaries, `clear`, relayer payment, reentry order, text-key limits and record sweeping. An expired commitment may be cleared by anyone without bounty; it cannot clear a live one. No separate bond drain or relayer takeover was found.
- **Snapshot memory:** `rpc.rs:99-132` allows one concurrent build, checks an estimated peak against a quarter of available memory and rate-limits retries; `follow.rs:135-153,425-485` checks 8× advertised wire size before downloading, streams chunks, and falls back to replay. WARN now uses the budget while CRITICAL refuses; the focused gate unit test passed. `test-seam` is compiled out of ordinary builds by `cfg`, and I found no env/config/RPC setter; an explicit build with `--features test-seam` would include it, so the release build must omit that feature. I did not measure swap/jetsam on a minimum Mac or a malicious 1 GiB snapshot. The unrelated long history-cache resource integration test was interrupted after it exceeded several minutes; it does not exercise the snapshot gate.
- **Wallet and release trust:** Token icons are bundled/generated locally, not fetched from token metadata; the history notice changes display only; the earnings CSV keeps the exact wei string as well as 18-decimal display. I found no new key, signature or remote-content path in those edits. I traced the Mac update gate: a single compromised builder cannot satisfy its two distinct pinned P-256 signatures (three for emergency), and a single compromised GitHub release account cannot change the on-chain archive hash plus Sparkle EdDSA signature. Either can delay or deny delivery. This is a source-level judgement; no real notarized update was installed. The public intro site, launch-site copy and legal documents were not audited.
- **Supply horizon:** `rewards::issuance` still decays from 1 AETH/block to a 0.1 AETH/block tail, so total supply has no finite terminal cap. The new state burn is at most 100,000 units × 10^12 wei = 0.1 AETH/block before other burns, exactly the tail issuance at that maximum; it cannot be assumed to offset issuance under normal use or under A6-1/A6-2, where the state burn is zero. The long-running reward/supply integration tests passed; no overflow or double mint was found in the inspected path.
