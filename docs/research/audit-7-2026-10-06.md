## Findings

### A7-1 — Medium — Snapshot synchronization permanently disables the new archive exporter

**Locations:** `crates/node/src/main.rs:2827-2835,2981-2989` enables checkpoint startup for every archive; `crates/node/src/snapshot.rs:254-279` installs only the snapshot summary/state, with `staged: None`; `crates/node/src/chain.rs:799,3148-3187` cannot reconstruct a history index when earlier summaries/era roots are absent; `:954` explicitly removes that index on a later snapshot jump; `:2773-2787` updates only an already-existing index; `crates/node/src/export.rs:345-347,575-586` requires the index on every export pass. The advertised complete archive is described in `docs/ops/archive-node.md:3-19`.

**Sequence:** Start an archive with an empty data directory on an established chain whose upstream offers a valid, usable checkpoint at a nonzero height. Archive startup installs that checkpoint instead of replaying from genesis. The store lacks the historical summaries needed by `rebuild_history_index`, so `history_index` is `None`. Every export pass immediately returns `no history index (history v2 only)`, including after the archive follows enough new blocks to seal later complete eras. Finalization never initializes a missing index. Restart reconstructs the same incomplete history and does not repair it. An archive initially replayed from genesis can reach the same condition after falling behind and taking the ordinary follower's snapshot jump.

The archive can continue verifying current blocks, while its static export set remains unavailable and pre-checkpoint history is never backfilled. This defeats archive replacement/recovery and the promised historical mirror; it does not establish acceptance of forged state or a running committee halt.

**READ-ONLY / not runtime-confirmed:** The startup argument, snapshot commit, absent-index transition, and unconditional export prerequisite are direct source facts. The existing archive-export integration fixture constructs retained history from genesis; it does not exercise archive checkpoint startup or a later jump. I did not start an archive or download a snapshot.

**Smallest safe fix:** Give archive mode a complete-history synchronization policy: replay from genesis and prevent snapshot skips, or authenticate and backfill every skipped era and rebuild the history index before declaring the archive/export complete. Disabling startup checkpoints alone leaves the later `advance -> jump -> adopt` path open. Add a checkpoint-started archive regression and an archive lag/jump regression that demonstrate later export progress and complete historical coverage.

**Genesis-only:** **No.** Fix archive synchronization and restore missing history from an authenticated source after launch; already-lost source history cannot be recreated by this patch.

### A7-2 — Medium — The shipped public gateway runner has no restart owner for self-healing exits

**Locations:** `scripts/run-read-gateway.sh:152-157` backgrounds a bare `aether follow` and cloudflared; `crates/node/src/follow.rs:869-887` exits with `EXIT_STALLED`; `crates/node/src/main.rs:2867-2874,2945-2948` exits on follower-task or RPC-server loss. The restart implementation is instead in `crates/node/src/supervisor.rs:788-915`.

**Sequence:** Deploy the gateway through the provided runner. During a qualifying upstream stall, the follower's watchdog exits to restart its transport. The shell runner has already returned, and `nohup` supplies signal protection rather than process supervision. No parent starts a replacement follower. Cloudflared remains alive against a dead origin, and restoring upstream availability does not restore the gateway. A fatal follower-task failure or a disk-floor exit has the same missing restart owner.

**READ-ONLY / not runtime-confirmed:** The runner launches `follow`, not `run`, a service manager, or a restart loop. I traced the child exit paths and the separate supervisor; I did not launch cloudflared or induce a real stall. External supervision installed independently by an operator can mitigate this finding, but is not installed by this runner.

**Smallest safe fix:** Supervise the follower using the existing restart policy or a dedicated service definition that handles the intended stall/fatal exits, disk waiting, and bounded backoff. Keep the read-only flag and loopback bind on every restart. Add a runner-level regression in which the follower exits with the stall code and the origin returns after recovery.

**Genesis-only:** **No.** An operational runner/service patch suffices.

### A7-3 — Medium — A remembered at-tip answer disables the follower timeout watchdog

**Locations:** `crates/node/src/follow.rs:783-795` resets the stall clock whenever `net == Some(height)`, including when `failed` is true; `:962-963` updates `chain.net_height` only after a successful awaited height request; `:869,878-884` feeds the previously stored height into pending/error observations.

**Sequence:** A follower successfully reaches its upstream tip at height H, leaving `chain.net_height = Some(H)`. Subsequent height requests fail or repeatedly time out without advancing the local chain. The early `?` returns before updating that field. Both the pending-attempt watchdog and completed-error path continue supplying `Some(H)`. `StallWatch::observe` resets on each observation before considering failures or elapsed time. The ten-minute transport-restart action never becomes eligible, however long the failures last.

This is a regression in the fix that correctly lets a caught-up follower survive a genuine chain pause: a fresh successful pause observation and a stale observation from before transport failure are indistinguishable. Bounded individual RPC attempts still run; an endpoint state that needs process-level recovery can nevertheless remain unrecovered.

**READ-ONLY / not runtime-confirmed:** I traced the stored-field lifetime and the reset ordering. The shipped timeout test begins with `net = None`, while the healthy-pause test supplies successful at-tip observations; neither represents a previous successful tip followed by failed status requests. I did not reproduce a stale NAT/iroh endpoint on a live node.

**Smallest safe fix:** Track the result/freshness of the current height probe separately from the informational last-seen height. Failed or pending probes must not inherit an old at-tip exemption. Fresh successful, corroborated at-tip rounds should retain the healthy-pause exemption. Test successful H, then failures beyond the stall window, as well as a real pause followed by resumed progress.

**Genesis-only:** **No.** This changes local recovery logic only.

### A7-4 — Medium — An unsupported ahead-of-tip status can exhaust a healthy follower's restart budget

**Locations:** `crates/node/src/follow.rs:360-365,392-403` accepts the first unsigned ahead-of-local status without establishing its certificate; `:962-963` stores that claim as the network target; `:1002-1078` can return no adopted blocks when requested certificates are unavailable; `:783-795,884-887` counts unchanged local height against that target; `crates/node/src/supervisor.rs:515-544` stops after more than three stall exits within an hour.

**Sequence:** The genuine committee pauses at H, and honest reachable sources correctly remain at H. One configured source supplies an unsupported height above H. On HTTP, an ahead answer returns before the honest alternative is queried. On iroh, an ahead cached answer returns immediately; when an honest cached source is queried, corroboration can select the same higher unsupported claim from another source. Fetching cannot authenticate a block beyond the real tip, so the follower makes no progress and eventually exits as stalled. Under `aether run`, repetition consumes the persisted four-stall stop threshold within an hour. The follower can remain stopped when the real committee resumes, despite an honest configured alternative throughout the pause. With the bare runner, A7-2 makes the first exit sufficient.

This is a follower availability defect. The validator startup gate still uses certificate-backed heights and quarantines unsupported claims; the prior round-1 validator-startup halt is not being reported again.

**READ-ONLY / not runtime-confirmed:** The unverified early returns, no-progress fetch behavior, watchdog, and persisted restart threshold were inspected together. PA7/PA7B regressions cover false-low tips and honest pauses, but not an unsupported higher claim during a real pause. No malicious peer or timed forty-minute run was executed.

**Smallest safe fix:** Treat status heights as fetch hints. Before an ahead claim can suppress at-tip waiting or consume the permanent recovery budget, require a certificate-backed block at that height; quarantine a claim after bounded unsupported fetches and try honest alternatives. Reuse the startup evidence pattern. Add a false-ahead source plus honest-at-tip source test spanning a pause and subsequent real progress.

**Genesis-only:** **No.** This changes source selection and local recovery policy.

### A7-5 — Medium — Era-transfer rejection happens after the whole file has already been read

**Locations:** `crates/node/src/rpc.rs:377-401` reads the whole accepted file before acquiring `ERA_TRANSFERS`; `:355-365` describes a four-file aggregate bound; `crates/node/src/era_net.rs:33-34` allows a 256 MiB file. Exposure is deliberate for archive mode: `crates/node/src/main.rs:364-368,2989` and `scripts/install-archive-node.sh:98-105` select its non-loopback listener.

**Sequence:** An archive webseed has valid retained era files and four outstanding responses holding all transfer permits. Another request for an existing file still performs `std::fs::read` and allocates the complete buffer before discovering that the budget is full and returning 503. Concurrent rejected requests can therefore allocate additional full-file buffers on runtime workers, and repeated rejected requests keep performing synchronous disk reads and allocation/free cycles. Busy admission is supposed to prevent that preparation work, but is consulted too late.

Public read-only `/era/` removal remains effective; this finding concerns the intentionally exposed ordinary archive/webseed listener. Runtime thread count limits simultaneous synchronous handlers, so this is not a claim of unlimited active threads. The claimed four-whole-file memory bound nevertheless excludes those handlers' pre-admission buffers.

**READ-ONLY / not runtime-confirmed:** The read-before-acquire ordering is unambiguous. PA7B-03's response-owned permit fixes the reported handler-return lifetime; its current test holds small responses and checks the fifth status, which does not detect the fifth file read/allocation. I did not run slow transfers or measure peak RSS/OOM. I do not claim that moving a permit into a one-chunk body proves a bound on every downstream HTTP buffer lifetime.

**Smallest safe fix:** Acquire the transfer permit before file I/O/allocation, retain it across preparation and response lifetime, and stream bounded chunks off the async runtime instead of returning a whole-file allocation. Add an assertion that a full transfer budget causes zero file reads, plus bounded outstanding-transfer memory coverage.

**Genesis-only:** **No.** Patch the archive server.

### A7-6 — Medium — Public era metadata queries bypass the new retained-history work budget

**Locations:** `crates/node/src/rpc.rs:64-79` publicly allowlists `aether_eraInfo`; `:936-938` dispatches it synchronously without `history_slot`; `:2090-2102` defines the otherwise shared history-work admission budget. `crates/node/src/era_net.rs:36-44,76-105` hashes the complete file on a miss in a 16-entry cache, with the cache mutex released during hashing.

**Sequence:** A public gateway retains more era files than its metadata cache can hold. Requests across that retained working set continually miss the cache and synchronously stream/hash whole files on async runtime workers. Overlapping misses for the same file also perform independent hash passes because there is no in-flight coalescing. The caller receives a tiny metadata response, but this route does not acquire the history budget or move preparation to a blocking worker. Its per-call body and response limits do not constrain the file work. Sustained cache misses can impair follower/RPC scheduling even after the old-block and proof reconstruction routes refuse excess work.

**READ-ONLY / not runtime-confirmed:** The public dispatch, cache bound, streamed complete-file loop, and lack of admission/single-flight are direct source facts. No disk flood or scheduling benchmark was run. This path uses a one-MiB hashing buffer rather than allocating a whole era; the established issue is unbudgeted synchronous I/O/CPU, not a measured process OOM.

**Smallest safe fix:** Route public `eraInfo` preparation through bounded worker admission, with a permit owned by the worker, and coalesce concurrent hash misses. Alternatively serve metadata computed at sealing time. Keep public reads local-only. Add a cache-miss test with the work budget already occupied and a simultaneous same-era miss test.

**Genesis-only:** **No.** Patch public RPC preparation.

- **B1 paid persistent bytes:** I traced final-diff slot/account/code charging, first-sender nonce persistence, success/revert output and log charging, reserved sender funds, post-execution refunds, actual versus declared budgets, fee-only beneficiary exceptions, delegation/selfdestruct treatment, and parallel conflict replay. - **B2 ceremony and original intent:** The original assembly record is compared before generating the final byte digest; later signer binding is a separate boundary. The record is a trusted independently distributed artifact; simultaneous substitution of every trusted original input/record is outside this guarantee. A shareless consumer with no record warns and verifies certificates instead of acquiring signing authority. No production ceremony files were supplied here.
- **B3 receipts:** `execution/src/receipt.rs:27-155` commits all receipt fields with domains/lengths, index, count, odd-node duplication and exact sibling-path exhaustion. `chain.rs:1236-1243` checks reexecution against the proposed root; new-genesis empty blocks carry `Some(ZERO)`, and legacy blocks carry no root. `light/src/lib.rs:210-287` verifies the finalization/descendant links before receipt inclusion. `wasm/src/lib.rs:194-263` checks answer/finalized equality, height/floor, pinned identity/group, committed chain IDs, Merkle proof and transaction hash at the certified index. The native ordinary `receipt()` display still trusts RPC fields (`ffi/src/lib.rs:1872-1884`); B3 does not automatically authenticate that existing UI path. No generated WASM/browser execution was performed.
- **B4 emergency upgrades and drill containment:** `upgrade.rs:170-195` requires distinct valid current-member ed25519 approvals under the upgrade message/domain, at least `N3f1::quorum(n) = n−f`, as well as the normal committee BLS signature on admission. `chain.rs:2200-2265` checks chain/version/activation ordering, one-epoch emergency notice, ordinary 604,800-block notice and bounded signed contents. The new-genesis timestamp floor supplies the elapsed-time lower bound. Builder emergency approval remains **3/3**, separately from committee emergencies. `implements`, `dev_notice` and `DevB3` are feature-gated; `dev-drill` has no default or dependent-crate enablement, and ordinary wallet builds omit it. The drill uses isolated target directories and explicit feature builds. I inspected source containment, not compiled production artifacts or a live upgrade drill.
- **B5 shared execution and arithmetic:** `Chain::block_context` carries the parent's state debt as remaining state capacity, including zero capacity; `remember` updates it even without an execution/proving fee policy. Admission uses the same transaction executor; proposers aggregate gas/slots/persisted bytes, archive-congested selection tests exact serialized payloads, and FOCIL uses an incremental settled-state reversal and exact append preview. Validators/replay check canonical payloads and archive capacity before extras execution, then state/receipt/gas/BAL equality. The proving guest replays the shared sequential executor with the committed context and actual state units. **The guest statement proves transaction execution, not the complete outer payload archive budget or a separately exposed receipt root**; those checks belong to committee block validation. This is an explicit trust boundary, not an established bypass.
- **B5 persistence and liveness:** State debt persists in summary `excess`; nonzero payload debt uses the versioned packed-store and AUN3 snapshot envelopes (`store.rs:404-501`, `snapshot.rs:92-160`). `parent_meta` authenticates both debt dimensions; snapshot checking refuses changed metadata, and reopening restores the saved summary. Honest full-cap use leaves state debt at most 99,968 and payload debt at most `8 MiB − 4 KiB`. Empty execution consumes zero state units, preserving 32-unit refill; canonical empty payloads are smaller than the 4 KiB refill. Optional traffic reserves 256 KiB for bounded control items. Individually invalid oversized controls are dropped, fitting controls are selected, and empty proposals save capacity for deferred valid controls. I found no reachable honest-debt bucket deadlock, price wrap, zero-limit metering exemption or restart/snapshot reset in these inspected paths. This is not a live liveness proof.
- **B5 economic envelope:** Independent integer evaluation reproduced **2,915,909,632 bytes/day** and **85,019,410,432 bytes/30 days**, including the one-time bursts, for the documented 16× paid-row and four-copy payload planning allowances. Those are logical/representation planning bounds, not measured physical database growth: redb pages/fragmentation, state-tree overhead, separately subsidized protocol records, logs and archive retention must be budgeted operationally.
