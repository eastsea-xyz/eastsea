# EastSea precompiles, proving capacity, and execution specification

**Review:** 2026-10-06, detached checkout `f92c839` (lead-merge). Read-only source review; this report is the only task artifact. No source changes, commits, cargo builds, proof generation, or live-node testing.

## Verdict

**Keep and explicitly pin Osaka for the beta's Ethereum-contract compatibility goal; correct design 04. All 18 listed precompiles have implementations available to the Jolt guest, including KZG. The High concern is missing proving-resource accounting, not an unsupported precompile. No High that can only be fixed at genesis is established.**

The distinction matters: an implemented algorithm can still exceed the shipped guest's whole-block trace or memory capacity. The source does not establish that every execution-valid block fits that capacity. It also does not establish which individual valid precompile call first exceeds it, or the cheapest fee-paying workload that does so; those require measurements that this read-only review did not perform.

| Finding | Severity and impact | Remedy / genesis restriction |
|---|---|---|
| H1: Precompile work, transaction verification, and witness/state work are absent from the prove-gas counter; accepted blocks have no demonstrated bound against the guest trace limit. | **High for proof availability and proof-reward economics.** Credible resource/reward griefing exposure; exact inexpensive failure threshold unmeasured. Does not establish proof forgery or consensus halt. | Deterministic cost accounting/admission plus bounded tracing, or a prover architecture that covers accepted blocks. Consensus/guest upgrades are possible; **not genesis-only**. |
| M1: A failed generation attempt consumes its height, with volatile error status and no automatic archive backfill. | **Medium operational availability.** Transient failures can leave recoverable blocks unproved; long jobs can let other blocks leave the recent cache. | Durable per-height outcomes, bounded retries and backfill; principally node/sidecar changes. |
| M2: Design 04 describes different precompiles, hash/state gas, and guest acceleration. | **Medium specification/compatibility drift.** Implementing the document now would change consensus and break some existing contracts. | Declare the actual baseline; treat subsequent behavioral changes as upgrades. |
| M3: `PREVRANDAO` and `BLOCKHASH` are always zero. | **Medium protocol compatibility issue; potentially High for an application relying on these for security.** No such deployed application was established here. | Document the limitation and introduce authenticated environment values at a protocol activation if required. **Not genesis-only**. |
| M4: Execution rules/caps and the verifier program currently lack historical version dispatch. | **Medium upgrade engineering risk.** Replacing constants/defaults in a binary can change historical replay or reject still-open old proofs. | Add height/version selection and a coordinated verifier-program transition before changing rules. ## 1. What the guest proves and which precompiles it supports

### Execution path

The node prepares the pre-state after system writes, constructs a stateless witness and checks a native replay against the recorded statement (`crates/node/src/prover.rs:904-918`). The guest decodes `BlockInput` and calls `aether_proving::block::output`, panicking if replay fails (`apps/prover/guest/src/lib.rs:6`, `apps/prover/guest/src/lib.rs:55-59`). Shared replay reconstructs the witness, checks the pre-state root, executes every transaction through `execute_block_sequential`, and commits the context, transaction hash, both state roots and gas vector (`crates/proving/src/block.rs:83-99`). A payout-address-bound claim is the public output (`crates/proving/src/block.rs:57-66`). System writes themselves are committee-checked, outside this transaction-execution proof (`crates/proving/src/block.rs:11-16`).

Both real transaction execution and `eth_call` use stock `Context::mainnet()` (`crates/execution/src/block.rs:332-342`, `crates/execution/src/block.rs:111-121`). The builder defaults to `SpecId::default()` and builds the Ethereum instruction/precompile providers (`D/revm-handler-43.0.3/src/mainnet_builder.rs:55-60`, `D/revm-handler-43.0.3/src/mainnet_builder.rs:75-76`); that default is **OSAKA** (`D/revm-primitives-43.0.0/src/hardfork.rs:68-72`).

The guest dependency disables execution's default `native` feature (`crates/proving/Cargo.toml:14`). Execution still enables revm `std`; the guest is built with `--mode std`, not the documented `no_std` ECALL path (`crates/execution/Cargo.toml:15`, `apps/prover/build-guest.sh:81-85`, versus `docs/design/04-execution.md:69`). Native execution enables C KZG, C secp256k1 and portable code, but not revm's `bn` or `blst` feature (`crates/execution/Cargo.toml:24-25`). Consequently BN254 and BLS use Arkworks in both native execution and guest; ECRECOVER and KZG switch to pure Rust in the guest (`D/revm-precompile-43.0.3/src/bn254.rs:9-18`, `D/revm-precompile-43.0.3/src/bls12_381.rs:5-14`). A `blst` package in a lockfile does not by itself enable revm's BLS backend.

Two corrections to likely assumptions:

* **KZG is not missing.** Cancun dispatch inserts it unconditionally (`D/revm-precompile-43.0.3/src/lib.rs:312-314`); without native features, verification falls back to Arkworks. The omission comments in `crates/execution/Cargo.toml:21-23` and `D/revm-precompile-43.0.3/src/lib.rs:140-141` are stale.
* **The P-256 inline is not P256VERIFY acceleration.** The guest installs an `aether_crypto` transaction-signature backend and an `aether_hash` BLAKE3 backend (`apps/prover/guest/src/lib.rs:43-45`). Revm separately calls its own default crypto provider (`D/revm-precompile-43.0.3/src/interface.rs:11-20`, `D/revm-precompile-43.0.3/src/interface.rs:324-328`). No revm crypto-provider installation was found in the execution/prover paths. A future replacement must preserve precompile prehash/signature semantics, not copy transaction-signature rules blindly.

Ordinary invalid-input/OOG handling is part of an EVM result that can itself be proved: depending on the precompile, invalid input can produce a halt or a successful empty result. It is not automatically guest failure. The provider translates ordinary precompile results into interpreter outcomes (`D/revm-handler-43.0.3/src/precompile_provider.rs:95-124`), and Aether includes halt/revert results with `success=false` (`crates/execution/src/block.rs:347-357`). A true replay/provider error, guest panic, backend disagreement, or resource exhaustion is different and prevents an accepted proof (`crates/proving/src/block.rs:91`, `apps/prover/guest/src/lib.rs:59`, `apps/prover/src/engine.rs:33-42`).

### Trace budget and what has actually been measured

The shipped guest declares **67,108,864 maximum padded trace rows**, **4 MiB untrusted advice**, **256 MiB heap**, and **4 MiB stack** (`apps/prover/guest/src/lib.rs:55`). This is a whole-block program; the design's chunk market/aggregation is not connected to node proving (`docs/design/06-proving.md:29-31`).

Jolt pads the trace using `(rows.len() + 1).next_power_of_two()` and returns `ProverError::Unsupported` above the maximum (`J/crates/jolt-prover/src/config.rs:114-122`). Importantly, the default Akita path generates the trace **before** checking that shape (`J/jolt-sdk/src/host_akita.rs:366-390`). This is not an early guest instruction budget: tracing can already consume substantial time/memory before a clean over-limit error, or fail under the resource watchdog. Advice size is rejected before proving (`apps/prover/src/program.rs:62-70`).

No address-by-address guest vector/cycle suite was found in the reviewed execution tests, prover sample/self-test, or spike. Recorded transfer benchmarks are not that suite: the stateless-witness benchmark reports roughly **1.27M cycles/transaction for 50 transfers**, with native statement agreement (`docs/research/spike-2026-10.md:164-173`); the sidecar README records 10 transactions at a padded `2^24` trace and 50 at `2^26` (`apps/prover/README.md:44-53`). These older measurements show that transaction/witness overhead alone is material, but do not establish a current per-precompile threshold. Pairings/KZG/MSM, MODEXP, variable-round BLAKE2F, and curve verification are priority measurements; short hashes and identity still have input-dependent costs. **Do not claim that one particular call necessarily exceeds the budget, or that any listed address always fits it, from this source review.**

### Prove gas does not reflect this work

The actual meter is explicitly a placeholder: one unit for each **interpreted EVM instruction** (`crates/execution/src/block.rs:151-175`). Its call hook only watches accesses to the fee recipient (`crates/execution/src/block.rs:186-193`). Revm executes a precompile and returns before creating a bytecode interpreter (`D/revm-handler-43.0.3/src/frame.rs:207-225`, `D/revm-handler-43.0.3/src/frame.rs:237`); inspector instruction steps run inside the bytecode loop (`D/revm-inspector-43.0.3/src/handler.rs:247-271`). Thus:

* A direct top-level precompile transaction meters **zero interpreted steps for its precompile work**, despite guest cryptographic execution and transaction/witness overhead.
* A nested call meters the surrounding CALL/STATICCALL and other bytecode instructions, but not the precompile's cryptographic computation.
* The same missing cost coverage applies to transaction signature verification, witness reconstruction and state hashing; this is broader than the extra Osaka addresses.

For fees-enabled/new-genesis execution, `header.gas.prove` must cover the execution gas limit, and money is reserved accordingly (`crates/execution/src/block.rs:404-433`). However, the reserve is refunded except for **measured steps × base prove fee**, capped by that reserve (`crates/execution/src/block.rs:437-445`). The block uses the measured count, not the declared budget (`crates/execution/src/block.rs:344`, `crates/execution/src/block.rs:395`, `crates/execution/src/block.rs:721-724`). Reservation therefore does not repair the missing charge or capacity bound. Design 04's measured opcode/precompile table, ECALL charging and prove-budget-triggered revert/burn are not implemented (`docs/design/04-execution.md:52`, `docs/design/04-execution.md:58-60`).

**Griefing assessment:** accepted execution work can be disproportionately costly to prove without corresponding prove units, fee congestion or admission control. This establishes a credible proof-service/reward griefing exposure, including for precompiles already on the proposed whitelist. It does not quantify an experimentally confirmed cheap unprovable block. Execution gas is still charged; exec/prove base fees can be zero below congestion (`crates/execution/src/fees.rs:24-29`, `crates/execution/src/fees.rs:153-166`), but new-genesis state/archive charging has a nonzero floor (`crates/execution/src/fees.rs:35-43`, `crates/execution/src/block.rs:363-380`). Calling the exposure universally “free” would be incorrect. Gas/size limits and resource monitors mitigate work but do not convert this placeholder into a bound on Jolt cost.

## 2. What happens when proving fails

| Stage | Current behavior / evidence |
|---|---|
| Native pre-check, Jolt operation or guest output failure | Sidecar returns an error; panic is caught, guest panic rejected, and native/guest disagreement rejected (`apps/prover/src/engine.rs:28-43`, `apps/prover/src/engine.rs:130-145`; `apps/prover/src/program.rs:74-84`). `serve` emits `ok:false` rather than a fabricated proof (`apps/prover/src/main.rs:105-111`). |
| Overlong trace | Propagated unsupported-shape error after tracing, as above. Increasing available RAM alone does not make the same pinned program accept a trace beyond its configured bound. |
| Timeout or memory pressure | A proving request has a 30-minute timeout that kills/reaps the sidecar (`crates/node/src/prover.rs:53-56`, `crates/node/src/prover.rs:209-217`). The resource watchdog can also terminate it and back off restarts (`crates/node/src/prover.rs:574-577`, `crates/node/src/prover.rs:603-629`). |
| Job selection | **Oldest eligible among 32 recent finalized blocks**, despite stale “newest” comments. Selection records the height in `attempted` before input construction (`crates/node/src/chain.rs:1637-1658`). |
| Input construction/encoding failure | Warns, records `Status.error`, skips the height (`crates/node/src/prover.rs:776-803`). |
| Generation failure | Warns “proving failed,” records a volatile error, waits five seconds; a dead sidecar is restarted. The attempted height remains consumed, so another eligible height is selected (`crates/node/src/prover.rs:840-847`). **No automatic infinite regeneration retry for that height.** |
| Persistence/recovery | `attempted` is in-memory and initialized empty (`crates/node/src/chain.rs:573-575`, `crates/node/src/chain.rs:730-731`). The cache retains 32 blocks; attempted markers are retained for about 64 heights (`crates/node/src/chain.rs:2914-2924`). Restart can reconsider a height only if still available to selection. There is no durable failed-height/backfill ledger in this path; next successful generation clears the latest error (`crates/node/src/prover.rs:827-835`). |
| Already-generated proof not accepted | Different retry policy: kept in `unsent` and resubmitted while its claim is open, including definite verifier refusals (`crates/node/src/prover.rs:728-762`, `crates/node/src/prover.rs:819-825`). This does not retry failed proof generation. |

Proofs are optional payload content: `pay_proofs` processes supplied claims and accepts an empty list (`crates/node/src/chain.rs:3528-3564`). Therefore such transaction blocks can still finalize under committee re-execution; missing proofs alone do not stop consensus. An expensive proving job can consume resources and delay other proofs, and a failed job leaves a proof gap rather than blocking a FIFO forever. This consequence matches the supplemental-proof trust model (`docs/design/06-proving.md:15-25`).

Payout requires a valid, address-bound proof against the recorded statement (`crates/node/src/chain.rs:3547-3560`). Without it the block gets no prover payout/proof-share issuance. New-genesis proof issuance also requires operator registration and respects the epoch cap (`crates/rewards/src/lib.rs:442-469`). Claims expire after **2,592,000 blocks**, about 30 days at one-second blocks (`crates/execution/src/proofs.rs:18-19`, `crates/execution/src/proofs.rs:80-89`). Pruning removes claim records without releasing their escrow balance (`crates/execution/src/proofs.rs:45-52`); withholding proof rewards is not an attacker redirecting or forging them. The much longer claim window does not provide automatic backfill beyond the selector's 32-block cache.

**October 6 incident:** the checked-in evidence identifies a separate, now-addressed input-encoding defect. Postcard serialization omitted `TxHeader.group=None`, while decoding expected the field; every transaction-bearing input failed, reported in the October 6 rehearsal as present since September 30 (`crates/node/src/prover_input.rs:1-16`). The encoder now writes the full decoder layout and round-trips it, preserving guest ID and statement commitments (`crates/node/src/prover_input.rs:72-89`). The checklist records the successful rehearsal after the fix and detection of the previously unnoticed failure (`docs/03-analysis/feature-checklist-2026-10-05.md:23`, `docs/03-analysis/feature-checklist-2026-10-05.md:47`). These are repository records, not independently inspected production logs. Neither the fix nor the rehearsal establishes per-precompile proving capacity.

## 3. Which specification serves the compatibility goal?

The catalogue's goal is original contracts with original compiler settings (`docs/research/clone-catalog-2026-10-06.md:5-6`). **Choose explicit, pinned Osaka execution semantics**, including its complete precompile set and stock execution gas, then describe EastSea's additional resource dimensions and environment limitations separately.

The design whitelist removes not just KZG/BLS users but RIPEMD-160 and identity callers (`docs/design/04-execution.md:53` versus actual dispatch above). A call to a removed address would follow ordinary account execution; an empty address can return success with empty data, not necessarily an obvious “unsupported precompile” error (`D/revm-handler-43.0.3/src/frame.rs:231-234`). Silent behavioral differences are possible. Enforcing that whitelist is a consensus change and a narrowed compatibility promise. It also retains MODEXP, BN254 pairing, BLAKE2F and P256VERIFY, so it does not solve H1.

EIP-7667 is a proposed hash-gas repricing, currently marked Stagnant, rather than the stock Osaka schedule. It directly changes contract-visible execution costs; fixed internal gas allocations can change behavior. EastSea already has a separate prove dimension, so preserving execution gas while calibrating that dimension is the better compatibility direction. That does not justify pretending proof admission is free of application limits: publish those limits explicitly. [Primary EIP-7667 specification](https://eips.ethereum.org/EIPS/eip-7667).

Keeping Osaka cannot honestly mean every Ethereum application has identical behavior: zero randomness/history values, EastSea's transaction envelope, state charges and throughput limits remain material. Define the claim as bytecode/opcode/precompile compatibility with documented environmental and economic differences, and validate actual guest vectors before expanding the proof-coverage claim.

### Upgradeable, but not a current configuration toggle

The chain already authenticates scheduled protocol versions, rejects a node unable to run the scheduled version, and executes activation migrations (`crates/node/src/chain.rs:1298-1309`, `crates/node/src/chain.rs:1371-1373`). The migration module explicitly preserves genesis and applies new behavior at an activation (`crates/execution/src/forks.rs:4-8`). Ordinary new-genesis upgrades have a 604,800-block notice; emergency upgrades require the specified committee approvals and epoch notice (`crates/node/src/upgrade.rs:30`, `crates/node/src/chain.rs:2209-2214`, `crates/node/src/chain.rs:2232-2239`).

However, `BlockContext` has **no protocol/fork selector or randomness field**, and node context construction selects no execution rules by protocol (`crates/execution/src/block.rs:32-40`, `crates/node/src/chain.rs:1125-1147`). Current migration dispatch does not switch EVM rules (`crates/execution/src/forks.rs:15-20`). Whitelist, gas table, code-size limits, proof weights, block caps and randomness can be changed through an upgrade **after adding deterministic historical height/version dispatch**. Replacing a binary constant/default across all heights is unsafe: replay re-executes transactions and compares receipt root, BAL and gas (`crates/node/src/chain.rs:1233-1254`). The project already records the missing block-limit switch and its upgrade-based remedy (`docs/design/30-post-launch-fixability.md:102`).

Guest changes also change the program: release nodes pin one guest ELF SHA-256 and reject sidecar mismatch (`crates/node/src/prover.rs:20-22`, `crates/node/src/prover.rs:184-195`); the sidecar embeds, preprocesses and verifies one guest (`apps/prover/src/program.rs:19`, `apps/prover/src/program.rs:44-46`, `apps/prover/src/program.rs:89-105`). Plan activation and verifier routing for still-open historical claims, preferably retaining the old verifier while deploying a new height/version-aware guest. Historical statements remain immutable; an execution-rule change must not rewrite their gas or roots. An acceleration/limit-only guest change can potentially prove the same old statement, but its new program ID still needs coordinated acceptance.

Certified replay substitutes certificate-backed proof acceptance (`crates/node/src/chain.rs:1409-1419`), so it is inaccurate to say every old included proof byte necessarily needs cryptographic reverification after a program upgrade. Historical transaction replay and admission of newly submitted proofs are the obligations that still require an explicit transition.

**Neither keeping Osaka nor choosing a future whitelist is intrinsically genesis-only.** Removing a facility after contracts depend on it is a compatibility break even when technically upgradeable. Fixing fees/queues/guest capacity prospectively cannot undo already lost rewards or an application action made with predictable randomness. Those irreversible consequences are different from an engineering defect that only a new genesis can repair.

The published [EIP-7825 specification](https://eips.ethereum.org/EIPS/eip-7825) independently confirms the declared-gas cap. [EIP-7823](https://eips.ethereum.org/EIPS/eip-7823) limits each MODEXP operand to 1,024 bytes; [EIP-7883](https://eips.ethereum.org/EIPS/eip-7883) changes its pricing. These execution protections do not establish Jolt affordability.

## 5. Recommended action

1. **Adopt an explicit Osaka baseline and correct design 04**, including the stale KZG comment, full precompile set, actual gas schedule, std guest, whole-block proof scope and environment limitations. Do not enforce the old whitelist as a documentation fix.
2. **Treat H1 as a High proof-service/reward risk that merits prompt remediation.** Establish native/guest vector parity and trace/resource measurements for every address and its permitted input range, plus signatures and witness/state work. Introduce deterministic, conservative proving-cost charges and block admission limits backed by those measurements. Preserve contract-visible Osaka execution gas where practical. Merely adding a price without a hard capacity bound does not guarantee provability.
3. **Bound work before or during tracing**, rather than relying solely on a post-trace shape rejection. Add durable per-height success/failure state, explicit permanent/transient classifications, bounded recovery and archival backfill. Track generation failures separately from proof-submission acceptance; a successful proof clearing the last error must not erase evidence of earlier gaps.
4. **Implement height/version execution selection and a program transition before changing consensus or guest rules.** Preserve historical replay and define acceptance for the 30-day open-claim window. Queue/telemetry fixes can ship independently; changing gas, admission, randomness or accepted guest programs needs coordinated protocol/release handling.

For the beta policy that singles out **genesis-only Highs** (`docs/design/30-post-launch-fixability.md:3`), this review identifies **none**. That is not a certificate that all execution-valid beta blocks can already be proved: the quantified precompile capacity and fee validation remain missing. Until they exist, publish proof coverage as supplemental/best-effort and avoid promising universal proof availability or dependable per-block proof rewards.

**Verification limits:** conclusions are grounded in pinned source, failure-control flow and checked-in measurements/incident records. No new compilation, test-vector proof, hostile workload, cycle measurement, live failure or upgrade drill was run. The exact budget-breaking precompile/input combinations, present deployed ELF behavior and cheapest griefing cost remain unverified.
